# ADR-0076. Engine compatibility — a declared keeper version window per entity

- **Context.** A service definition is executed by **two** engines that are versioned and upgraded independently: **keeper** renders the DSL into `RenderedTask` (sensitive to the grammar of destiny/scenario), and **soul-agent** applies the rendered plan (sensitive to the module catalog and its parameters). Nothing in the system states which engine versions a given definition was authored against, so a mismatch is discovered by its symptoms:
  - old keeper + a DSL construct it does not implement → a **loud** reject at render, but with an opaque text: `render: DSL construct outside the pilot scope: …` ([`keeper/internal/render/render.go:51`](../../keeper/internal/render/render.go)) — it names the construct, never the version that would render it;
  - old keeper + a new parameter of a core module → a loud `unknown_param` at schema validation ([`shared/config/module_params.go`](../../shared/config/module_params.go)) — safe, and again version-blind;
  - old soul + unknown module → a loud `module.not_found` ([`soul/internal/runtime/plantask.go:65`](../../soul/internal/runtime/plantask.go)) — safe;
  - **old soul + a new parameter of a known module → a silent ignore**: the soul side reads params by key with no strict pass, so the task reports OK/CHANGED with no effect. This is the dangerous mode;
  - custom-plugin params are not statically validated at all (`validateModuleParams` covers namespace `core` only — the manifest of a custom module lives on disk beside its binary).

  Version provenance is likewise absent. Keeper's own version exists at build time (`-X main.version`, [`Makefile:69`](../../Makefile)) but is not exposed at runtime: `/healthz` is a static 200 ([`keeper/internal/api/health/health.go`](../../keeper/internal/api/health/health.go)), `HelloReply` carries `session_id`/`kid`/`server_time` and no version, and `PingReply.version` actually returns the KID ([`keeper/internal/grpc/bootstrap.go:136`](../../keeper/internal/grpc/bootstrap.go)). Soul's version is sent on every connect (`Hello.soul_version`) but only logged, never persisted.

  What is missing is not detection — it is a **declared contract**: which engine versions this definition is known to work with, checked before the run, with an error that names the version.

- **Decision.**

  - **(a) The primary contract is an author-declared version window, carried by every entity.** A `compat:` block in `service.yml` **and in every `destiny.yml`**:

    ```yaml
    compat:
      keeper: {min: "0.1.0", max: "0.3.0"}
    ```

    Per-entity, not per-service, because a destiny is a **separate git artifact pinned at its own ref** ([ADR-007](0007-versioning-git-ref.md)): it is authored, tested, and upgraded independently of the service that consumes it, so only it can state its own tested range. Precedents: Terraform `required_version`, Helm `kubeVersion`, Puppet `requirements`. The reverse direction (a deprecation policy on the keeper side — "keeper supports the last N definition generations") is **not decided here**; it lands as an amendment to this ADR under **NIM-163**.

  - **(b) The effective window is the intersection — the narrowest wins.** Over the manifest set resolved at the pinned refs: `min` = max of the declared mins, `max` = min of the declared maxes. An **empty** intersection (a service demanding `min: 0.3.0` while one of its destinies caps at `max: 0.3.0`) is an authoring error `compat_window_empty` — no keeper can ever satisfy it, so it is reported at lint / service registration rather than discovered at run time. A missing `compat:` block means **unbounded on that entity** — today's behavior is preserved with no migration of existing services (the nil-block-means-default precedent of `lifecycle:`/`telemetry:` in [`shared/config/service.go`](../../shared/config/service.go)).

  - **(c) Half-open `[min, max)`, plain `MAJOR.MINOR.PATCH`, no range grammar.** `min` inclusive, `max` **exclusive** — so `max` reads as "the first version I have **not** tested", which is the boundary an author can actually state, and `{min: "0.1.0", max: "0.3.0"}` means the whole `0.1.x`–`0.2.x` band without a bump on every patch. Both keys are optional; a block declaring neither is an error. No `v` prefix, no pre-release suffix, no `>=`/`<` operators, one syntax only.

    A free-form range string (`">=0.1.0 <0.3.0"`) was **rejected**: the ticket requires the *effective* window to be visible in API/UI, and an arbitrary constraint algebra is **not closed under intersection** — the AND of two range strings is checkable but not representable as one window, so there would be nothing to display. The explicit pair is closed by construction (max-of-mins / min-of-maxes).

  - **(d) A pre-release keeper version is compared by its release core.** `0.1.0-beta.1` sits inside `[0.1.0, 0.3.0)`. Strict semver precedence puts `0.1.0-beta.1` **below** `0.1.0`, and constraint libraries exclude pre-releases from a range unless the constraint itself carries one — under naive matching the entire public beta (the repo's only tag today is `v0.1.0-beta.1`) would fail every window ever written. Dropping the pre-release suffix for the **comparison** keeps the window at release granularity, which is the granularity an author tests at; the full version string is preserved verbatim in error text and in the provenance stamp.

  - **(e) A version that cannot be determined is not enforced — loudly.** The runtime version string is `git describe --tags --always --dirty` ([`Makefile:55`](../../Makefile)) and comes in five shapes:

    | How the binary was built | Version string | Compared as |
    |---|---|---|
    | release pipeline (`VERSION=v0.1.0-beta.1`) | `v0.1.0-beta.1` | `0.1.0` |
    | `make build` in a working tree past a tag | `v0.1.0-beta.1-12-gabc1234` | `0.1.0` |
    | the same with uncommitted changes | `…-gabc1234-dirty` | `0.1.0` |
    | `go build` / `go run` without ldflags | `0.0.0-dev` (`keeper/cmd/keeper/main.go:57`) | **not enforced** |
    | a checkout with no tags (`--always` fallback) | `abc1234` | **not enforced** |

    Normalization strips a leading `v`, the git-describe distance suffix `-<N>-g<sha>`, and `-dirty` — build metadata, not precedence — and then takes the release core per (d). A build standing past a tag is therefore **enforced as the release it is based on**: it genuinely lacks whatever a later version introduced, and exempting it would hide real breakage on the dev stand ([`dev/keeper-run.sh`](../../dev/keeper-run.sh)), which is where a version mismatch should surface first.

    The check is skipped **only when there is no version to compare**: the un-injected sentinel `0.0.0-dev`, an empty string, or a string that yields no release core after normalization (a bare commit hash). Then the window is not enforced but **said out loud** — a keeper-side log warning plus an explicit `not enforced (<raw string> carries no version)` in the API/UI window view — and the raw string is stamped into provenance regardless, so the audit trail records exactly what rendered.

    Rationale for the exemption: `0.0.0-dev` is valid semver and sorts **below every** declared `min`, so treating it as a real version would fail every window and break plain `go build`/`go run` outright, while treating it as a silent pass would hide the gap. A keeper-config switch making even the version-less case fail closed is deliberately **deferred** to a real request.

  - **(f) Enforcement belongs to the keeper instance that renders.** Keeper is a horizontally scalable stateless cluster ([ADR-002](0002-transport-grpc-ha.md)); during a rolling upgrade its instances run **different versions**, so a check performed when a service was registered says nothing about the instance that will actually render a run months later. Therefore: the render path is the **authority** — a fail-closed abort with reason `keeper_version_unsupported` before any dispatch, symmetric to the existing `soul_passage_unsupported` gate ([`keeper/internal/scenario/run.go:471`](../../keeper/internal/scenario/run.go)); service registration and the upgrade pin change are an **early convenience check** only (a fast, actionable 4xx at the moment the operator can still choose a different ref). There is **no** window check at soul dispatch — that is the other axis, see (i).

  - **(g) The error names the version.** Replacing the opaque render failure: which entity declared which window, what the effective window is, which version this keeper is, and what to do about it — "destiny `redis` (ref `v2.1.0`) supports keeper `[0.1.0, 0.3.0)`; this keeper is `0.4.1`; pin an older keeper or upgrade the destiny".

  - **(h) The window is visible before the run.** The effective window, the per-entity contributions that produced it, and the running keeper's version are served through the operator API so the UI can show the compatibility state of a service without attempting a run. This also requires surfacing keeper's version at runtime at all — `HelloReply` and a `/healthz` JSON body — and correcting the `PingReply.version`-carries-KID drift.

  - **(i) The secondary layer is a cross-check, not a replacement: capability + `introduced_in`.** Two independent directions, both **generalizations of contours that already exist**:
    - **soul axis** — generalize the [ADR-056](0056-staged-render-passage.md) §S5 capability set beyond the single `passage` entry (`shared/config/soul_capability.go`) so a soul announces its module registry and soul-side features; keeper computes the required set for a plan at render and reuses the already-generic per-host gate (`SoulsLackingCapability`, [`keeper/internal/redis/heartbeat.go:138`](../../keeper/internal/redis/heartbeat.go)) to fail closed **before** dispatch. This is what closes the silent-ignore mode; the Redis layer needs no change.
    - **keeper axis** — `introduced_in` metadata on DSL features and module states lets keeper compute the floor a given plan **actually** requires, and the existing catalog endpoint `GET /v1/modules` can carry it outward. Placement matters for forward-compat: **core** manifests are embedded in the binary ([`shared/coremanifest`](../../shared/coremanifest)), so metadata and parser always ship together and the addition is free; **plugin** manifests are external artifacts parsed with `yaml.Strict()` ([`shared/plugin/manifest.go:279`](../../shared/plugin/manifest.go)), so a newer manifest carrying the key fails on an older host — the same forward-compat shape as (m), to be handled when the key reaches plugin manifests rather than assumed away.

  - **(j) Inference can produce a floor, never a ceiling — which is exactly why the declaration is primary.** `max(introduced_in)` over a plan says "no keeper below X can render this". Nothing in the code can know that keeper `0.4.0` changed a behavior this definition depends on; only the author who tested it knows where the upper bound is. The automatic layer therefore verifies the **lower** half of the declaration and can never replace it.

  - **(k) A declared floor below the inferred floor is an authoring error, not a run-time block.** If a definition declares `min: 0.1.0` but uses a feature introduced in `0.3.0`, the declaration is too permissive — it would break on a `0.1.x` keeper. That is a `compat_floor_too_low` diagnostic in `soul-lint` and at service registration. It is **not** a render-time abort: on a `0.3.5` keeper such a run works correctly, and blocking a run that would succeed is a worse failure than the stale declaration it reports. The opposite direction — a declared floor above the inferred one — is a deliberate conservative choice by the author and is not diagnosed.

  - **(l) The rendered fact is stamped into state, not into the definition.** `apply_runs` (migration 018, per-host, written at dispatch) gains the keeper version that rendered and the soul version that applied; the effective window in force at render time is recorded alongside the incarnation / `state_history` so drift detection and DR-reincarnation (**NIM-40**) can see which engine contract produced the state. This is deployment history and belongs in Postgres ([ADR-005](0005-storage-postgres.md)) — never in `destiny.yml`. The [ADR-007](0007-versioning-git-ref.md) boundary holds in both directions: `compat` is **not** an artifact version (the version of a service/destiny remains its git ref, and the deliberate absence of a top-level `version:` field is untouched), and the stamp is not a manifest field.

  - **(m) The bootstrap paradox is accepted and bounded.** A keeper older than the release that introduces `compat:` will reject the key as `unknown_key` — the manifest walker checks every key against the Go struct's yaml tags ([`shared/config/walk.go:82`](../../shared/config/walk.go)). That is **fail-closed and safe** (an old keeper refuses a definition it cannot vouch for), but the message is generic; the clean versioned error exists only from this release forward. No retroactive fix is possible, and one must not be bought by relaxing the walker into a lenient unknown-key mode — that would trade a permanent strictness property for a one-time improvement in a message.

  - **(n) The soul axis stays capability-based, not numeric.** A numeric min-soul-version was rejected: the soul estate is large and heterogeneous, the capability contour is already built and fail-closed by design, and a version number cannot express "this binary has module X" for a fleet where module sets differ by host. `soul_version` remains audit-only — carried, persisted, and stamped, but never the gate.

- **Amendment 2026-07-26 (NIM-163) — param-level strictness on the soul side, and the deprecation policy.** Takes up the two items this ADR deferred to NIM-163 — param-level strictness with the custom-plugin param hole, and the deprecation policy promised in (a). The first is settled for core modules and deliberately left short of enforcement for custom ones (q); the second is settled outright (r). The capability gate (NIM-161) refuses a host that never announced a module; what stayed open is one level down — the module is there, but a **param** of it is not, so the soul reads the keys it knows and reports OK/CHANGED while the thing the author asked for never happened. A capability per param is not the answer (the announcement would grow by an order of magnitude and change on every schema edit); the answer is that the executing binary checks the task against its own contract before applying it.

  - **(o) The soul rejects a param its own manifest does not declare, before Apply.** `module.unknown_param`, FAILED, the module never runs — so the host is untouched when it fires ([`soul/internal/runtime/paramcheck.go`](../../soul/internal/runtime/paramcheck.go), on the Apply path and on the dry_run path alike; a `Plan` that skipped the check would answer "no drift" for a param it never reads, the false-clean [ADR-031](0031-scry-drift.md) forbids). The contract enforced is the one **compiled into that binary** (`shared/coremanifest`, go:embed) — never keeper's, and never a version number. That is what makes it work on a heterogeneous estate: what matters is what this host carries, and the manifest ships in the same artifact as the module, so declaration and implementation cannot drift. The message names the offending keys and what the binary does accept, so an operator fixes the definition or upgrades the agent without a second run to find out which.

    Only the **unknown** direction is enforced. A missing required param stays with keeper's static check ([`shared/config.validateModuleParams`](../../shared/config/module_params.go)), which sees the author's text with a line and column and runs before a run exists; re-deriving it on the soul would duplicate the rule where the error is worse and a manifest default could satisfy it anyway.

  - **(p) The wire form is not the author-facing form, and the check knows the difference.** For `core.file.rendered` keeper replaces the author's `template:`/`vars:` with `template_content`/`render_context` at render ([ADR-012](0012-keeper-soul-grpc.md)(d) variant A1) — keys deliberately absent from the manifest, which describes what an operator writes. A check that only knew the manifest would reject **every rendered-file task in the estate**. These engine-internal keys are therefore allowlisted per full address including state, so the carve-out is not a global amnesty: `template_content` on `core.file.present` is still unknown. A core module with no embedded manifest at all (`core.augur`) is **unchecked** rather than "accepts nothing" — absence of a declaration is not a declaration of absence.

  - **(q) Core is enforced; custom modules are advisory, and the reason is measured, not cautious.** The plugin param hole named in the Context is real, and this amendment does not close it. Two independent findings, both from the current tree:
    1. **Plugin manifests under-declare today.** They have never been enforced anywhere, so they were written as UI/lint material rather than as a contract. In the reference `community.redis` manifest the shared TLS params are promised in the header comment but omitted from `input:` on 4 of its 11 states; the shipped redis/dragonfly scenarios genuinely pass `tls`/`tls_ca`/`tls_cert`/`tls_key`/`topology`/`username` to exactly those states — **10 keys across 16 files**. Enforcing would fail scenarios that work correctly today, on hosts whose manifest ships beside the plugin binary and cannot be fixed by editing this repo.
    2. **An opt-in key would be its own forward-compat break.** The natural fix — a manifest flag meaning "my input is complete, enforce it" — cannot be added safely: plugin manifests are parsed with `yaml.Strict()` ([`shared/plugin/manifest.go`](../../shared/plugin/manifest.go)), so a manifest carrying any new key fails to load on an older soul. That is the hazard (i) said must be handled rather than assumed away, and the only lever that is already versioned for it, `protocol_version`, is the SoulModule **API** flag gated by the handshake against `SupportedProtocolVersions` — bumping it for a metadata concern would strand every pv-2 plugin on every current agent.

    So a custom module's undeclared param is **logged, not rejected** (`ParamsAdvisory`): the hole becomes visible where it was previously silent, which is the step that can be taken without breaking a working estate. The flip to enforcement needs manifests authored under the contract, and therefore needs (2) solved first — a follow-up, not a footnote. **Superseded by (t)** — the measurements stand, the deferral does not.

  - **(r) The deprecation policy — the answer to "how many generations back".** Strictness is only safe with a way to shrink a contract that does not break yesterday's definitions, so a param is **never removed outright**. It is first marked in the manifest:

    ```yaml
    address:
      type: string
      deprecated: { since: "0.4.0", removed_in: "0.6.0", use: "addr" }
    ```

    `removed_in` is **EXCLUSIVE** — the first release that no longer honors the param — so it reads exactly like `compat.keeper.max` (c) and one grammar covers both. Both bounds are required: an open-ended deprecation is a warning that never resolves, and an author cannot plan a migration against it.

    **The window is at least `DeprecationMinMinors = 2` minor releases**, enforced by the manifest validator (`deprecation_window_too_short`), not merely written down here. Deprecated in `X.Y.0` → removable no earlier than `X.(Y+2).0`, which is precisely the half-open window `{min: X.Y.0, max: X.(Y+2).0}` an author may declare in `compat:` — the guarantee they read off the policy and the interval they can write down are the same object, not two rules to reconcile. **Two rather than one** because an author who upgrades a minor at a time needs at least one release where the old param and its replacement both work; with a one-minor window there is no version they can stand on while migrating. A **major** bump is exempt from the count — a new major is the declared breaking-change boundary.

    Surfaces, in the order they reach someone who can act: the **author** gets a `deprecated_param` **warning** (never an error — the param still works, and an error would make deprecation indistinguishable from removal) from the same static check that reports `unknown_param`, carrying the deadline and the replacement; the **operator** gets a soul-side log line during a rollout. `use:` must name a param of the same state, or the validator rejects it (`deprecated_replacement_unknown`) rather than sending an author after something that does not exist. At `removed_in` the key leaves the manifest and the identical task text becomes `unknown_param` at both gates — deprecation first, rejection later, never rejection outright.

    > **Superseded in part by the 2026-07-28 amendment (u):** "the operator gets a soul-side log line" was the whole operator surface, and it was not one — see (u) for what replaced it. The author half stands unchanged.

  - **(s) Adding a param is a soul-side compat event, and the rollout order already covers it.** With (o) in force the directions are asymmetric and all of them are safe: an **older keeper** sends a subset of what a newer soul declares → passes untouched, so the only-add discipline of [ADR-012](0012-keeper-soul-grpc.md) keeps holding. A **newer keeper** sending a param an older soul does not implement → a loud per-host FAILED instead of a false success, which is the whole point. That does mean adding a param to a core module now breaks un-upgraded agents loudly rather than silently mis-applying — the correct trade, and it needs no new rule: it is the same **souls first, then keeper** order the fail-closed capability gate (NIM-161) already imposes. The bootstrap paradox of (m) applies unchanged — a soul older than this release has none of this code and goes on ignoring silently; the property exists from here forward.

- **Amendment 2026-07-28 (NIM-204) — the manifest is the contract in both homes.** Takes up the one thing the 2026-07-26 amendment deferred: enforcement for custom modules (q). The measurements in (q) stand — plugin manifests do under-declare, and the opt-in key it proposed is unsafe. What changes is the conclusion drawn from them.

  - **(t) Custom modules are enforced, on the same terms as core, and the one-time break is taken rather than scheduled.** `ParamStrictness` collapses to two values: either a manifest declares a state's input, or there is no manifest (`core.augur`). There is no third mode where a declaration exists and means nothing.

    **The opt-in key is rejected outright, and not only for the parsing reason.** (q)(2) named `yaml.Strict()`; the actual cost is worse than "the manifest fails to load". A decode error is an error-level diagnostic, and `DiscoverSlot` ([`shared/pluginhost/discovery.go`](../../shared/pluginhost/discovery.go)) skips the **whole slot** on the first one — so a manifest carrying an "enforce my input" key would not merely fail to gate on an older Soul, it would **delete the module**, turning every task for it into `module.not_found`. A key that closes a silent hole at the price of making the module vanish is not a fix. But even with a lenient parser the key is the wrong shape: it **never converges** (it would be set by the authors who already declare completely — the author who forgot `tls_ca` is exactly the one who will not set it, and the gate exists for what an author did not think of); it makes "a manifest may be a lie" permanent and legitimate (`input:` **is** the declaration, and a declaration that needs a second declaration saying "I mean it" is not one — core needed no such flag); and it is per-plugin while the risk is per-estate, so the operator inherits the author's choice with no say in it.

    **A deprecation window for the flip itself is likewise rejected as a mechanism** — a version threshold the Soul compares itself against ("enforced from X.Y.0") was considered and dropped. The advisory→enforced transition happens **exactly once in the life of the product**: after it, a plugin contract shrinks only through `deprecated:` (r), whose window is real and recurring. A self-scheduling mechanism for a one-shot event buys a single transition at the price of a permanent one — a dead branch in the checker and a constant carrying a promise that someone must remember to retire.

    **What makes the one-time break affordable, and what stops it recurring.** The only plugin manifests in existence are the ones this project ships (`examples/module/soul-mod-community-*` and their copies beside the binaries on hosts); the plugin SDK has had no public release, so there is no third-party author whose manifest can break. The blast radius is therefore one ticket — the under-declared `community.redis` manifest (**NIM-206**) — not an estate. That licence is spent here: from the first public SDK release onward, every further tightening of a plugin's param contract goes through the `deprecated:` window of (r), which is what makes strictness safe to keep.

    **Rollout order is manifests → souls → keeper**, the same order the fail-closed capability gate (NIM-161) already imposes and for the same reason: the gate lives on the Soul, so an agent carrying this code and a host carrying an old plugin manifest rejects the task. Manifests are fixed first — in this repo *and* beside the binaries on hosts, which are separate artifacts. The rejection message names which one to upgrade: for `core.*` the soul binary (its manifest is `go:embed`-ed into it), for a custom module the plugin itself, since its manifest travels with it and is upgraded independently of the agent.

    **Not addressed here:** the author still has no static, pre-run surface for plugin params — `validateModuleParams` covers namespace `core` only, so an under-declared plugin manifest is discovered when a task fails on a host rather than at lint time. Closing that means giving the linter the plugin manifests of a service's dependency set, which is a resolve-time concern, not a strictness one.

- **Amendment 2026-07-28 (NIM-205, NIM-237) — the deprecation has to reach the two people who can act on it.** The window of (r) is only worth what its surfaces are worth, and both were thinner than (r) claimed. Nothing about the policy changes; what changes is where it is visible.

  - **(u) The operator's surface is the run, not the agent's log.** (r) said the operator "gets a soul-side log line during a rollout", and treated that as a delivered notice. It is not one: the line goes to the `slog` of one agent, and reaching it means tailing the logs of a specific host at the moment a task runs. Nothing carried it into the run's event stream, the run's stored result, the audit, or any UI — so an operator learned about the deprecation at `removed_in`, when the param became `unknown_param`, exactly as abruptly as if there had been no window at all. The mechanism protected them from a break by giving them notice they could not receive.

    This is worse for a **plugin** module than for core, and the asymmetry is the reason it had to be fixed rather than documented. For `core.*` the author is warned statically, so someone in the chain is told; for a plugin `validateModuleParams` returns early on the namespace (still open, see (t) "not addressed here"), which left the invisible log line as the *only* notice a plugin deprecation ever produced.

    The notice now rides the wire the run already uses: `TaskEvent.notices` (`repeated TaskNotice{code, module, param, message}`, only-add per [ADR-012](0012-keeper-soul-grpc.md)(c)), collected before Apply and sent whatever the task's outcome — a deprecation is equally true on a task that failed for an unrelated reason, and dropping it there would hide it exactly when the operator is already reading the run. **It must originate on the Soul**: the contract is the manifest compiled into *that* binary (t), so no other party can state it, and a park mid-upgrade legitimately answers differently host to host. Keeper lands it in three places it already serves — the `task.executed` audit payload (durable, queryable), the SSE frame (live), and `apply_runs.notices` (read back by `GET /v1/incarnations/{name}/runs/{apply_id}`, per host, deduplicated by `(code, module, param)` because one param used by twenty tasks is one thing to migrate).

    Two details are deliberate. **Notices are not suppressed by `no_log`**, unlike `error.message` and `register_data`: a notice is rendered from the manifest — param name, versions, replacement — and never from a param *value* or task output, so the arbitrary-secret leak `no_log` exists to stop cannot travel this way, and suppressing it would blind the operator precisely on the tasks that handle secrets. And **the SSE frame carries the sentence**, where `error.message` is withheld, for the same reason: there is no stderr in it, and a frame saying only `deprecated_param` sends the operator hunting for which param and by when.

  - **(v) A fleet-wide rollup is sourced from DEFINITIONS, never from run history.** "Which incarnations still pass `address`?" is the question that turns a warning into a migration plan. The tempting source is the notices already stored on runs (u) — and it is the wrong one: an aggregate over stored runs answers *"who passed it in the runs we happened to observe"*, so an incarnation nobody has run this month is missing from it although its definition breaks at `removed_in`, and one fixed yesterday still appears because the old rows remain. The honest source is the text that will be rendered next time.

    **Built in NIM-268** as `GET /v1/deprecations`, once (x) made a plugin's manifest resolvable — which is precisely what this point had been waiting for: the incarnations the caller may see (narrowed by the *same* `resolveListScope` the incarnation list uses — a second implementation of a scope rule is how two of them drift into a leak), grouped by the `(service, ref)` they are pinned to so one snapshot serves all incarnations sharing it, each definition's scenarios walked and their tasks matched against the manifest — core from the embedded registry, plugin from the Sigil-backed catalog. **One catalog snapshot per survey**, not per definition, so every incarnation is judged against the same allow-list rather than one that moved mid-scan. Ordered by `removed_in`: what breaks first comes first.

    **The reply reports what it could NOT read, and that is the load-bearing part.** Plugin modules resolve through (x)'s catalog — keeper snapshots it from its Sigil grants, which is the same manifest set the render path checks params against, so the survey and the gate never disagree about what a module accepts. What stays unreadable is narrower than before but still real: a module the allow-list does not carry, a manifest that no longer parses, a keeper with no Sigil service at all. Without an explicit gap list, a service built on plugin modules yields an empty finding list, indistinguishable from one that is genuinely clean, and an operator reads "nothing to migrate" off "nothing was checked". So `gaps[]` carries the plugin modules, the unresolvable core modules, the definitions that failed to load and the scenarios that failed to parse — each naming the incarnations it affects — and coverage counters say how much of the estate the answer covers. **An empty `items` with a non-empty `gaps` is not a clean bill of health.** The scenario enumeration deliberately reads the snapshot's directory rather than reusing the catalogue helper, whose partial-success semantics drop an unparseable scenario with a log line: correct for a UI dropdown, and exactly wrong here, since the definition that cannot be parsed is the one whose silence would be mistaken for health.

  - **(w) The catalog publishes `deprecated` beside `introduced_in`.** (i) exposed `introduced_in` through `GET /v1/modules` while its counterpart stayed inside the manifest, so the catalog could say "this param arrived in 0.3.0" and not "this param leaves in 0.6.0, use `addr`". The block travels as an object (`{since, removed_in, use}`) rather than the rendered sentence: `use` is what a UI offers as the replacement and `removed_in` is what a migration is planned by, and prose would have to be parsed apart again to do either. This is the surface an author reads **before** writing the task; the `deprecated_param` warning of (r) only reaches them once the definition exists. Declarable on a param only — module- and state-level `deprecated` do not exist, which is settled in (aa) rather than assumed away.

- **Amendment 2026-07-29 (NIM-228) — the static check is given a resolver, and its silence is made audible.** Closes what (t) left open: an author writing a plugin task had no pre-run diagnostic at all. Nothing about strictness changes; what changes is who can answer "what does this module accept".

  - **(x) The check is namespace-agnostic; only the SOURCE of the manifest differs.** `validateModuleParams` returned `nil` on the first line for any namespace but `core`, and the four checks behind it (`unknown_param` / `missing_required_param` / `param_type_mismatch` / `module_state_unknown`) were never core-specific — they read a `plugin.StateDef`, which a plugin manifest supplies just as well. What core has is *availability*: its manifests are `go:embed`-ed, so they are present at the moment a task is decoded. A plugin manifest arrives with the caller, so it is resolved through `ValidateOptions.ModuleManifests` and applied in a post-pass over the parsed document. That split is the reason the two halves run in different phases, and the checks themselves stay one implementation.

    The walk deliberately knows nothing of task grammar: any mapping carrying a `module:` string is a module task, wherever it sits. Keying off `tasks:` / `block:` / `apply:` would silently stop checking the day the grammar grows another construct that holds tasks — the failure mode of (t)'s early return, one level up.

  - **(y) Two resolvers, because there are two moments an author can be told.** **Keeper** resolves from its Sigil grants, which hold the byte-exact `manifest.yaml` the signature was verified over — i.e. the very manifest that will gate the task on the host under (t). That matters beyond convenience: checking against any other copy risks refusing a run the Soul would have accepted, which (f) already names as the worse failure. The snapshot is taken per parse, so a plugin allow-listed a minute ago is visible and a revoked one stops being. **soul-lint** resolves from a directory of manifests (`--modules <dir>`), for the author on a laptop with no cluster, in a checkout that carries both halves. Indexing is by the address the manifest **declares**, never by the directory it sits in: a plugin directory is named after its binary (`soul-mod-community-redis`), while a task addresses `community.redis`.

    An unresolvable module is never an error. A definition's author usually cannot produce somebody else's plugin manifest, so failing them for its absence punishes the wrong person; and a keeper whose allow-list is briefly unreadable must not turn a storage blip into a refused render.

  - **(z) Not-checked is now said out loud.** This is the half that makes the rest worth having. Before it, "no diagnostics" meant *either* "checked and clean" *or* "never looked", and NIM-206's drift survived to be found by hand precisely because the two were the same output. Every plugin module whose manifest does not resolve now yields **`plugin_params_unchecked`** — a **hint**, one per module address rather than per task (one unresolvable module used by twenty tasks is one thing to fix, and twenty identical lines teach the reader to skip them). It never fails a lint, and it never blocks a render; it only removes the ambiguity.

  - **A deprecation window for this flip is not offered, and does not need to be.** The lint runs where the definition is authored, not on a host: a definition that starts failing is fixed in the editor that reported it, in the same session. Compare (t), where the same tightening had to be weighed against an estate of hosts. What this *does* break is a definition that linted clean while passing an undeclared key — but that definition already fails on the host under (t), so the change moves the failure earlier rather than creating one.

  - **Consequence for (v).** The fleet-wide "who still passes this deprecated param" rollup was deferred because the honest source is the definitions, and reading those needed a plugin-manifest resolve. That prerequisite now exists (**NIM-268**).

- **Amendment 2026-07-30 (NIM-308) — the catalog carries no deprecation, and that is the correct state, not a gap.**

  - **(bb) No param is marked deprecated to give the surfaces something to show.** The window of (r), the notices of (u) and the catalog field of (w) are all live, and the estate they describe is **empty**: no module in the catalog declares `deprecated`. That was read as a hole — the UI mark has nothing to render, and the survey of (v) returns an empty list for every caller. It is not a hole. Nothing has been deprecated yet, so an empty answer is the true one.

    Searched before deciding: 24 core manifests and all 138 params of the reference plugin carry no superseded parameter. The nearest-looking pair, `onlyif` / `unless` on `core.cmd` and `core.exec`, are **complementary rather than successive** — opposite polarities of the same guard — so marking either would be false. `core.noop` declares no input at all.

    Inventing one is therefore rejected, and for the same reason (t) rejected the opt-in key: `deprecated: {since, removed_in}` is a **promise to an operator about a removal date**. A manifest that carries a date nobody intends to honor is a manifest that lies, and it lies in the artifact shipped to hosts. A demo is not worth that; the mark will light up on its own the first time a contract really shrinks, which is what the window exists for.

    What the emptiness DOES cost is stated rather than hidden: until the first real deprecation, the chain manifest → catalog → UI is exercised only by fixtures, and the survey cannot distinguish "the estate is clean" from "the survey is broken" by its output alone. Both are covered by tests instead — the scanner on synthetic definitions, the catalog on a synthetic manifest, and the API's projection field-by-field — because a test fixture may state whatever the test needs without any operator ever reading it as a promise.

- **Amendment 2026-07-29 (NIM-244) — the deprecation axis stops at the parameter, deliberately.** (w) left "module- and state-level `deprecated` do not exist" as an open question. Answered here: they should not, and the reason is not cost.

  - **(aa) A parameter is the only level whose removal was ever SILENT, and the only one with no version of its own.** The three levels are not three sizes of the same thing:

    - **Parameter.** It has no separately addressable version — it lives inside a state's contract, and the engine (or the plugin) decides what that contract is. Before (o) its disappearance was *silent*: a Soul reads params by key, so a key it does not know is never read and the module reports OK while the author's intent never happened. That silence is the entire reason the policy exists, and `deprecated:` is the only way to shrink such a contract without breaking definitions that were valid yesterday.
    - **Module and state, `core.`** Removal here was **never** silent and cannot be made so: an unknown module is a loud `module.not_found` before dispatch, an unknown state is `module_state_unknown` from the static check — *with a line and column, before a run exists*. The failure mode the policy was built against is absent, and the author's warning surface is already better than a manifest note would be.
    - **Module and state, plugin.** The engine-version axis does not reach them **at all**, and this is enforced in code, not just intended: `config.coreModuleFeatures` returns early on any namespace but `core`, so a plugin's `introduced_in` contributes to no floor and is read by nothing — [`docs/keeper/plugins.md`](../keeper/plugins.md) already states the key "parses but states nothing about a keeper release". A plugin's version line is its git ref ([ADR-007](0007-versioning-git-ref.md)); a module leaves circulation there, where the author who pinned `ref:` controls when it reaches them.

    So a module-level `deprecated` would be **semantically empty on a plugin** — a second key that parses and means nothing, exactly like `introduced_in` there — and **redundant on core**, restating a signal that is already loud and already positioned. Neither is worth its price, and the price is real: any new key in a plugin manifest is a decode error on an older Soul, where `DiscoverSlot` skips the **whole slot** and the module *vanishes* (`module.not_found`) rather than merely losing a label (t). Paying "the module disappears on older agents" for a key that carries no meaning is the worst trade in this ADR.

    **What this is NOT.** It is not "deprecating a module is unsupported". It is that the mechanism differs by level: a **parameter** goes through `deprecated:` because nothing else can warn; a **core module or state** goes through the release notes plus the loud, positioned diagnostics that already exist; a **plugin module** goes through its own ref, which is what ADR-007 made the version of an artifact in the first place. Should a future case genuinely need a module-level window — a `core.` module being renamed, say — reopen this with that case in hand rather than building the key speculatively.

- **What it standardizes, what it defers.** **Standardizes:** the `compat:` block and its per-entity placement (a); intersection semantics and the empty-window error (b); the `[min, max)` grammar (c); the normalization and comparison rules, including which builds are exempt (d, e); the enforcement point and its reason code (f); the stamp's home (l); the role of the automatic layer as a cross-check (i, j, k); param-level strictness on the soul side and the deprecation policy, both added by the 2026-07-26 amendment (o–s); param strictness for custom modules on the same terms as core, and the rejection of both an opt-in manifest key and a version-scheduled flip, added by the 2026-07-28 amendment (t); the operator's deprecation surface — `TaskNotice` on the run, its three landing places, and its exemption from `no_log` — plus the catalog's publication of `deprecated`, added by the NIM-205/NIM-237 amendment (u, w); the static check of plugin params against a resolved manifest, its two resolvers, and the explicit `plugin_params_unchecked` where none resolves, added by the NIM-228 amendment (x–z); the decision that an empty deprecation catalog is the correct state, and that no param is marked merely to populate a surface, added by the NIM-308 amendment (bb); **settles** that `deprecated` stops at the parameter and does not extend to module or state level, with the per-level mechanism named for each (aa); the fleet-wide "who still passes this param" rollup, sourced from definitions rather than run history and required to report its own coverage gaps, built on (x)'s resolver — NIM-268 (v). **Defers:** `deprecated` at module and state level, where the axis is one-sided today (w, NIM-244); a strict-mode config switch for version-less builds (e); a `compat.soul` axis — the block is shaped to accept one, but the soul axis is capability-based today (n).

- **Trade-offs.**
  - **Author-declared vs inferred.** A declaration can go stale — an author bumps nothing and the window silently lies. Mitigated, not solved, by the cross-check (k): the floor is verifiable, the ceiling is not. The alternative (infer everything) cannot express a ceiling at all.
  - **Explicit pair vs range string.** The pair is less expressive than `>=`/`<`/`~`/`^` and cannot say "only 0.2.x and 0.4.x". It buys a displayable effective window and a trivial intersection; a disjoint set of allowed bands is not a real authoring need.
  - **Warned skip vs fail-closed on version-less builds.** A keeper built with no version injected can render a definition it was never tested against. Accepted deliberately, and kept as narrow as possible: builds that *do* carry a version — including every `make build` — are enforced by their release core, so the exemption covers only the case where there is genuinely nothing to compare, and it is loud in the log, in the API, and in the stamp rather than silent.
  - **Release-core comparison.** `0.1.0-beta.1` and `0.1.0-beta.7` are indistinguishable to a window. Accepted: the window's granularity is a release, and a pre-release band narrow enough to matter is better expressed by pinning the keeper build than by the manifest.
  - **Two surfaces, deliberately asymmetric (u, v).** The run notice is per-host and reports what a Soul observed; the fleet survey is per-definition and reports what will be rendered. They can legitimately disagree — a definition fixed after the last run shows clean in the survey and deprecated on the stored run — and that is the correct behaviour rather than an inconsistency to reconcile: one is history, the other is intent. The survey is also a **partial** view by construction (plugin contracts are unreadable from a definition until NIM-228), which is why it reports coverage instead of implying completeness.
  - **A break taken once vs a break scheduled.** Enforcing plugin params now fails any task whose manifest under-declares, with no notice period — a definition that worked yesterday stops working on upgrade. Accepted because the population that can be broken is enumerable today (our own shipped manifests) and stops being enumerable the moment the SDK is released publicly, so the choice is between paying once now and paying a permanent scheduling mechanism to pay the same price later. The guarantee that replaces the notice period is (r): from here on the contract shrinks only through a declared window.
  - **Per-entity windows vs one service-level window.** More places to keep current, and a single stale destiny narrows the whole service. That is the point — a definition assembled from independently-versioned artifacts is only as compatible as its narrowest part, and hiding that in one service-level field would make the bound unattributable.
