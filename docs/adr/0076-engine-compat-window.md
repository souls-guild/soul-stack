# ADR-0076. Engine compatibility — a declared keeper version window per entity

- **Context.** A service definition is executed by **two** engines that are versioned and upgraded independently: **keeper** renders the DSL into `RenderedTask` (sensitive to the grammar of destiny/scenario), and **soul-agent** applies the rendered plan (sensitive to the module catalog and its parameters). Nothing in the system states which engine versions a given definition was authored against, so a mismatch is discovered by its symptoms:
  - old keeper + a DSL construct it does not implement → a **loud** reject at render, but with an opaque text: `render: DSL construct outside the pilot scope: …` ([`keeper/internal/render/render.go:51`](../../keeper/internal/render/render.go)) — it names the construct, never the version that would render it;
  - old keeper + a new parameter of a core module → a loud `unknown_param` at schema validation ([`shared/config/module_params.go`](../../shared/config/module_params.go)) — safe, and again version-blind;
  - old soul + unknown module → a loud `module.not_found` ([`soul/internal/runtime/plantask.go:65`](../../soul/internal/runtime/plantask.go)) — safe;
  - **old soul + a new parameter of a known module → a silent ignore**: the soul side reads params by key with no strict pass, so the task reports OK/CHANGED with no effect. This is the dangerous mode;
  - custom-plugin params are not statically validated at all (`validateModuleParams` covers namespace `core` only — the manifest of a custom module lives on disk beside its binary).

  Version provenance is likewise absent. Keeper's own version exists at build time (`-X main.version`, [`Makefile:69`](../../Makefile)) but is not exposed at runtime: `/healthz` is a static 200 ([`keeper/internal/api/health/health.go`](../../keeper/internal/api/health/health.go)), `HelloReply` carries `session_id`/`kid`/`server_time` and no version, and `PingReply.version` actually returns the KID ([`keeper/internal/grpc/bootstrap.go:136`](../../keeper/internal/grpc/bootstrap.go)). Soul's version is sent on every connect (`Hello.soul_version`) but only logged, never persisted.

  What is missing is not detection — it is a **declared contract**: which engine versions this definition is known to work with, checked before the run, with an error that names the version.

- **Decision.**

  - **(a) The primary contract is an author-declared version window, carried by every entity.** A `compat:` block in `service.yml` **and in every `destiny.yml`**:

    ```yaml
    compat:
      keeper: {min: "0.1.0", max: "0.3.0"}
    ```

    Per-entity, not per-service, because a destiny is a **separate git artifact pinned at its own ref** ([ADR-007](0007-versioning-git-ref.md)): it is authored, tested, and upgraded independently of the service that consumes it, so only it can state its own tested range. Precedents: Terraform `required_version`, Helm `kubeVersion`, Puppet `requirements`. The reverse direction (a deprecation policy on the keeper side — "keeper supports the last N definition generations") is **not decided here**; it lands as an amendment to this ADR under **NIM-163**.

  - **(b) The effective window is the intersection — the narrowest wins.** Over the manifest set resolved at the pinned refs: `min` = max of the declared mins, `max` = min of the declared maxes. An **empty** intersection (a service demanding `min: 0.3.0` while one of its destinies caps at `max: 0.3.0`) is an authoring error `compat_window_empty` — no keeper can ever satisfy it, so it is reported at lint / service registration rather than discovered at run time. A missing `compat:` block means **unbounded on that entity** — today's behavior is preserved with no migration of existing services (the nil-block-means-default precedent of `lifecycle:`/`telemetry:` in [`shared/config/service.go`](../../shared/config/service.go)).

  - **(c) Half-open `[min, max)`, plain `MAJOR.MINOR.PATCH`, no range grammar.** `min` inclusive, `max` **exclusive** — so `max` reads as "the first version I have **not** tested", which is the boundary an author can actually state, and `{min: "0.1.0", max: "0.3.0"}` means the whole `0.1.x`–`0.2.x` band without a bump on every patch. Both keys are optional; a block declaring neither is an error. No `v` prefix, no pre-release suffix, no `>=`/`<` operators, one syntax only.

    A free-form range string (`">=0.1.0 <0.3.0"`) was **rejected**: the ticket requires the *effective* window to be visible in API/UI, and an arbitrary constraint algebra is **not closed under intersection** — the AND of two range strings is checkable but not representable as one window, so there would be nothing to display. The explicit pair is closed by construction (max-of-mins / min-of-maxes).

  - **(d) A pre-release keeper version is compared by its release core.** `0.1.0-beta.1` sits inside `[0.1.0, 0.3.0)`. Strict semver precedence puts `0.1.0-beta.1` **below** `0.1.0`, and constraint libraries exclude pre-releases from a range unless the constraint itself carries one — under naive matching the entire public beta (the repo's only tag today is `v0.1.0-beta.1`) would fail every window ever written. Dropping the pre-release suffix for the **comparison** keeps the window at release granularity, which is the granularity an author tests at; the full version string is preserved verbatim in error text and in the provenance stamp.

  - **(e) A version that cannot be determined is not enforced — loudly.** The runtime version string is `git describe --tags --always --dirty` ([`Makefile:55`](../../Makefile)) and comes in five shapes:

    | How the binary was built | Version string | Compared as |
    |---|---|---|
    | release pipeline (`VERSION=v0.1.0-beta.1`) | `v0.1.0-beta.1` | `0.1.0` |
    | `make build` in a working tree past a tag | `v0.1.0-beta.1-12-gabc1234` | `0.1.0` |
    | the same with uncommitted changes | `…-gabc1234-dirty` | `0.1.0` |
    | `go build` / `go run` without ldflags | `0.0.0-dev` (`keeper/cmd/keeper/main.go:57`) | **not enforced** |
    | a checkout with no tags (`--always` fallback) | `abc1234` | **not enforced** |

    Normalization strips a leading `v`, the git-describe distance suffix `-<N>-g<sha>`, and `-dirty` — build metadata, not precedence — and then takes the release core per (d). A build standing past a tag is therefore **enforced as the release it is based on**: it genuinely lacks whatever a later version introduced, and exempting it would hide real breakage on the dev stand ([`dev/keeper-run.sh`](../../dev/keeper-run.sh)), which is where a version mismatch should surface first.

    The check is skipped **only when there is no version to compare**: the un-injected sentinel `0.0.0-dev`, an empty string, or a string that yields no release core after normalization (a bare commit hash). Then the window is not enforced but **said out loud** — a keeper-side log warning plus an explicit `not enforced (<raw string> carries no version)` in the API/UI window view — and the raw string is stamped into provenance regardless, so the audit trail records exactly what rendered.

    Rationale for the exemption: `0.0.0-dev` is valid semver and sorts **below every** declared `min`, so treating it as a real version would fail every window and break plain `go build`/`go run` outright, while treating it as a silent pass would hide the gap. A keeper-config switch making even the version-less case fail closed is deliberately **deferred** to a real request.

  - **(f) Enforcement belongs to the keeper instance that renders.** Keeper is a horizontally scalable stateless cluster ([ADR-002](0002-transport-grpc-ha.md)); during a rolling upgrade its instances run **different versions**, so a check performed when a service was registered says nothing about the instance that will actually render a run months later. Therefore: the render path is the **authority** — a fail-closed abort with reason `keeper_version_unsupported` before any dispatch, symmetric to the existing `soul_passage_unsupported` gate ([`keeper/internal/scenario/run.go:471`](../../keeper/internal/scenario/run.go)); service registration and the upgrade pin change are an **early convenience check** only (a fast, actionable 4xx at the moment the operator can still choose a different ref). There is **no** window check at soul dispatch — that is the other axis, see (i).

  - **(g) The error names the version.** Replacing the opaque render failure: which entity declared which window, what the effective window is, which version this keeper is, and what to do about it — "destiny `redis` (ref `v2.1.0`) supports keeper `[0.1.0, 0.3.0)`; this keeper is `0.4.1`; pin an older keeper or upgrade the destiny".

  - **(h) The window is visible before the run.** The effective window, the per-entity contributions that produced it, and the running keeper's version are served through the operator API so the UI can show the compatibility state of a service without attempting a run. This also requires surfacing keeper's version at runtime at all — `HelloReply` and a `/healthz` JSON body — and correcting the `PingReply.version`-carries-KID drift.

  - **(i) The secondary layer is a cross-check, not a replacement: capability + `introduced_in`.** Two independent directions, both **generalizations of contours that already exist**:
    - **soul axis** — generalize the [ADR-056](0056-staged-render-passage.md) §S5 capability set beyond the single `passage` entry (`shared/config/soul_capability.go`) so a soul announces its module registry and soul-side features; keeper computes the required set for a plan at render and reuses the already-generic per-host gate (`SoulsLackingCapability`, [`keeper/internal/redis/heartbeat.go:138`](../../keeper/internal/redis/heartbeat.go)) to fail closed **before** dispatch. This is what closes the silent-ignore mode; the Redis layer needs no change.
    - **keeper axis** — `introduced_in` metadata on DSL features and module states lets keeper compute the floor a given plan **actually** requires, and the existing catalog endpoint `GET /v1/modules` can carry it outward. Placement matters for forward-compat: **core** manifests are embedded in the binary ([`shared/coremanifest`](../../shared/coremanifest)), so metadata and parser always ship together and the addition is free; **plugin** manifests are external artifacts parsed with `yaml.Strict()` ([`shared/plugin/manifest.go:279`](../../shared/plugin/manifest.go)), so a newer manifest carrying the key fails on an older host — the same forward-compat shape as (m), to be handled when the key reaches plugin manifests rather than assumed away.

  - **(j) Inference can produce a floor, never a ceiling — which is exactly why the declaration is primary.** `max(introduced_in)` over a plan says "no keeper below X can render this". Nothing in the code can know that keeper `0.4.0` changed a behavior this definition depends on; only the author who tested it knows where the upper bound is. The automatic layer therefore verifies the **lower** half of the declaration and can never replace it.

  - **(k) A declared floor below the inferred floor is an authoring error, not a run-time block.** If a definition declares `min: 0.1.0` but uses a feature introduced in `0.3.0`, the declaration is too permissive — it would break on a `0.1.x` keeper. That is a `compat_floor_too_low` diagnostic in `soul-lint` and at service registration. It is **not** a render-time abort: on a `0.3.5` keeper such a run works correctly, and blocking a run that would succeed is a worse failure than the stale declaration it reports. The opposite direction — a declared floor above the inferred one — is a deliberate conservative choice by the author and is not diagnosed.

  - **(l) The rendered fact is stamped into state, not into the definition.** `apply_runs` (migration 018, per-host, written at dispatch) gains the keeper version that rendered and the soul version that applied; the effective window in force at render time is recorded alongside the incarnation / `state_history` so drift detection and DR-reincarnation (**NIM-40**) can see which engine contract produced the state. This is deployment history and belongs in Postgres ([ADR-005](0005-storage-postgres.md)) — never in `destiny.yml`. The [ADR-007](0007-versioning-git-ref.md) boundary holds in both directions: `compat` is **not** an artifact version (the version of a service/destiny remains its git ref, and the deliberate absence of a top-level `version:` field is untouched), and the stamp is not a manifest field.

  - **(m) The bootstrap paradox is accepted and bounded.** A keeper older than the release that introduces `compat:` will reject the key as `unknown_key` — the manifest walker checks every key against the Go struct's yaml tags ([`shared/config/walk.go:82`](../../shared/config/walk.go)). That is **fail-closed and safe** (an old keeper refuses a definition it cannot vouch for), but the message is generic; the clean versioned error exists only from this release forward. No retroactive fix is possible, and one must not be bought by relaxing the walker into a lenient unknown-key mode — that would trade a permanent strictness property for a one-time improvement in a message.

  - **(n) The soul axis stays capability-based, not numeric.** A numeric min-soul-version was rejected: the soul estate is large and heterogeneous, the capability contour is already built and fail-closed by design, and a version number cannot express "this binary has module X" for a fleet where module sets differ by host. `soul_version` remains audit-only — carried, persisted, and stamped, but never the gate.

- **What it standardizes, what it defers.** **Standardizes:** the `compat:` block and its per-entity placement (a); intersection semantics and the empty-window error (b); the `[min, max)` grammar (c); the normalization and comparison rules, including which builds are exempt (d, e); the enforcement point and its reason code (f); the stamp's home (l); the role of the automatic layer as a cross-check (i, j, k). **Defers:** param-level strictness on the soul side and the custom-plugin param hole, together with the keeper-side deprecation policy — both land under **NIM-163**, the latter as an amendment to this ADR; a strict-mode config switch for version-less builds (e); a `compat.soul` axis — the block is shaped to accept one, but the soul axis is capability-based today (n).

- **Consequences.**
  - `compat:` on `ServiceManifest` and `DestinyManifest` ([`shared/config/service.go`](../../shared/config/service.go), [`shared/config/destiny.go`](../../shared/config/destiny.go)) + intersection and comparison helpers; `Masterminds/semver/v3` is promoted from an indirect to a direct dependency.
  - Keeper's version surfaced at runtime (`HelloReply`, `/healthz` JSON) and the `PingReply.version`-carries-KID drift corrected — **NIM-159**.
  - A window gate on the render path with reason `keeper_version_unsupported`, replacing the opaque `ErrUnsupportedDSL` text for version-caused failures, plus the early check at registration — **NIM-159**.
  - `introduced_in` on DSL features and module manifests, the `max(introduced_in)` computation over a plan, its cross-check against the declared window, and its exposure in `GET /v1/modules` — **NIM-160**.
  - Generalized soul capability announcement (modules from the registry + soul-side features), the required-set computation at render, the per-host fail-closed gate, and persisting `soul_version` next to `caps` in the heartbeat hash — **NIM-161**.
  - Provenance columns on `apply_runs` + the effective window on incarnation/`state_history`, with a migration — **NIM-162**.
  - `soul-lint` diagnostics `compat_window_empty` / `compat_floor_too_low`.
  - Manifest-spec documentation of the key lands with the implementation ([`docs/service/manifest.md`](../service/manifest.md), [`docs/destiny/manifest.md`](../destiny/manifest.md)) — this ADR does not document a key that does not parse yet ([ADR-0077](0077-docs-sourcing-drift-policy.md)).
  - New names in [naming-rules](../naming-rules.md): the `compat:` block, the terms *compat window* / *effective compat window*, and the reason codes.

- **Trade-offs.**
  - **Author-declared vs inferred.** A declaration can go stale — an author bumps nothing and the window silently lies. Mitigated, not solved, by the cross-check (k): the floor is verifiable, the ceiling is not. The alternative (infer everything) cannot express a ceiling at all.
  - **Explicit pair vs range string.** The pair is less expressive than `>=`/`<`/`~`/`^` and cannot say "only 0.2.x and 0.4.x". It buys a displayable effective window and a trivial intersection; a disjoint set of allowed bands is not a real authoring need.
  - **Warned skip vs fail-closed on version-less builds.** A keeper built with no version injected can render a definition it was never tested against. Accepted deliberately, and kept as narrow as possible: builds that *do* carry a version — including every `make build` — are enforced by their release core, so the exemption covers only the case where there is genuinely nothing to compare, and it is loud in the log, in the API, and in the stamp rather than silent.
  - **Release-core comparison.** `0.1.0-beta.1` and `0.1.0-beta.7` are indistinguishable to a window. Accepted: the window's granularity is a release, and a pre-release band narrow enough to matter is better expressed by pinning the keeper build than by the manifest.
  - **Per-entity windows vs one service-level window.** More places to keep current, and a single stale destiny narrows the whole service. That is the point — a definition assembled from independently-versioned artifacts is only as compatible as its narrowest part, and hiding that in one service-level field would make the bound unattributable.
