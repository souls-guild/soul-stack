# ADR-009. Scenario — the full destiny task DSL; the boundary with destiny is a recommendation

- **Context.** Initially an isolation invariant was in force: a scenario could only `apply: { destiny: … }` (plus `target`/orchestration), but **not** `module:` directly — all the "work" had to live in an isolated, versionable, molecule-testable destiny. In practice this forced creating a separate destiny repo for the sake of a one-or-two-step inline operation (role probe, one-off command, diagnostics) that is never reused. The invariant hindered even read-only steps (probe), without which the volatile role from [ADR-008](0008-coven-stable-tags.md#adr-008-coven--stable-logical-tags-only) cannot be implemented.
- **Decision.**
  - **The "scenario without `module:`" invariant is fully lifted** (not only for read-only). Scenario receives **the entire destiny task DSL core** from [`docs/destiny/tasks.md`](../destiny/tasks.md): `module:` (including mutating modules), `templates`, task-level `vars:`, `register:`, `loop:`, `block:`, `async:`, `onchanges:`/`onfail:`/`require:`, `changed_when:`/`failed_when:`, `retry:`, `timeout:` — plus an orchestration layer on top (`on:`/`where:` targeting, `apply: { destiny: … }`, `state_changes`).
  - **The DSL core is not duplicated.** The source of truth for the core is `docs/destiny/tasks.md`; the scenario delta is a separate normative document [`docs/scenario/orchestration.md`](../scenario/orchestration.md).
  - **destiny remains** a standalone entity: a reusable, independently versionable (git ref, [ADR-007](0007-versioning-git-ref.md#adr-007-artifact-versioning--via-git-ref-not-a-manifest-field)), isolated, molecule-testable brick.
  - **The destiny / scenario boundary is a recommendation, not a wall.** The criterion for extraction into a destiny is three "yes"es: (1) reuse, (2) molecule idempotency is needed, (3) it is isolable. All three → extract into a destiny via `apply:`; otherwise an inline `module:` implementation in the scenario is permissible.
  - **Barrier / state-commit invariant (not an option).** ⚠ **The state-commit half is removed by [ADR-0084](0084-explicit-state-capture.md) (see amendment below) — the barrier stays, the commit moves to the capture step.** The commit of `incarnation.state` (`state_changes`) is a **cross-host final-barrier AFTER an unconditional wait for all async tasks of all hosts of the run**. If even a single one is finally-failed → the state is **not** committed → `error_locked`. This is an extension of the final-barrier from [destiny/tasks.md §6](../destiny/tasks.md#6-asynchronous-tasks-async-true) from a single host to the cross-host scenario level. More details — [`docs/scenario/orchestration.md`](../scenario/orchestration.md#7-state-capture-and-the-cross-host-barrier).
  - **`state_changes` carries the source of the value, not only an allow-list.** `sets` is a map `<field> → <CEL expression>`: the declaration specifies **both** which `incarnation.state` field to update **and** where to take the value from (rendered Keeper-side in the scenario-CEL environment after the barrier). The former reading of `sets` as a flat allow-list of names (only "which fields are allowed to be written", without a source) is replaced: without a source, `incarnation.state` stayed empty on a successful run. The cross-host fold of `sets` is last-wins by `SID` sort order. **The context of `sets` is `input.* / incarnation.* / soulprint.self.* / register.*`.** `register.*` (the per-host probe result) is threaded through the back channel `TaskEvent.register_data` → table `apply_task_register` → a per-host register map after the barrier (slice 2 of the full grammar). `vars.* / essence.* / state.* / soulprint.hosts` and the keys `appends`/`modifies` (per-host collections) are a future extension of the full grammar, unavailable (render error → `error_locked`). **The grammar is extended by [ADR-057](0057-state-changes-crud-verbs.md) (see amendment below):** `state_changes` is an ordered list of CRUD verbs (`set`/`add`/`modify`/`remove`+`foreach`), the map form (`sets`/`appends`/`modifies`) is deprecated. **The block itself is removed by [ADR-0084](0084-explicit-state-capture.md) (see amendment below):** a state write is a `core.state.<verb>` keeper task standing at its own position in `tasks:`. Grammar — [`docs/scenario/orchestration.md §7.1`](../scenario/orchestration.md#71-the-capture-verbs).
  - **Isolation and destiny `output:`.** A destiny publishes its own result through a declared top-level `output:`; this is symmetric to `input:` and does **not** violate destiny isolation (a destiny does not read scenario scope — the parent's `essence`/`register`/`vars`/`input`, `incarnation.*`, the run topology). Specification — [`docs/destiny/output.md`](../destiny/output.md). ★ **The design is decided, the implementation is not:** the top-level block parses and validates, but nothing fills it — a task-level `output:` is refused (`output_unsupported`, NIM-334) and `register.<applier>.<field>` does not resolve. **Clarification (see Amendment 2026-06-18):** the target host's stable self-facts (`soulprint.self.*`) are **not** scenario scope but a per-host property of the host itself, therefore they are available to destiny-CEL; only cross-host (`soulprint.hosts`/`soulprint.where`) is forbidden.
- **Rationale.** One task language across both layers — no two dialects, the scenario author does not learn a second syntax. Probe (read-only `module:` + `register:`) becomes natural, which is exactly how the volatile role is implemented ([ADR-008](0008-coven-stable-tags.md#adr-008-coven--stable-logical-tags-only)). destiny does not lose its properties — it remains a choice by recommendation, not by compulsion.
- **Trade-off / risks.**
  - **Scope expansion of [ADR-003](0003-destiny-format.md#adr-003-destiny-format--yaml-with-a-typed-schema-cuejson-schema).** The safe templater as a separate phase now serves scenario as well (`where:` predicates, `on:` literals, templates). This question (choice of templater) is closed by [ADR-010](0010-templating.md#adr-010-templating-engine-cel-for-yaml-expressions-go-texttemplate-for-files). Prior to ADR-010 it blocked the implementation of scenario, not only destiny.
  - **Erosion risk of [ADR-007](0007-versioning-git-ref.md#adr-007-artifact-versioning--via-git-ref-not-a-manifest-field).** Inline `module:` mutations in a scenario bypass the independent git versioning of a destiny (a pinpoint edit of `scenario/<name>/main.yml` does not receive a tag and the review of a separate destiny repo). **Mitigation:** the boundary-recommendation above + a backlog lint-warn in [`docs/soul-lint.md`](../soul-lint.md) ("inline mutation in a scenario without extraction into a destiny"). A consciously accepted price for the simplicity of typical operations.
- **Related decisions.** [ADR-008](0008-coven-stable-tags.md#adr-008-coven--stable-logical-tags-only) (probe instead of role-as-Coven — implemented precisely by lifting this invariant). The full specification of the delta — [`docs/scenario/`](../scenario/README.md).

**Amendment 2026-05-27 (invocation-time scope chunking — Tide).** [ADR-040](0040-tide.md#adr-040-tide--invocation-time-scope-chunking--target-override) introduces a new top-level entity **Tide** — an invocation-instance that splits a mass scenario run into sequential waves (**Surges**) with an optional target/wave/concurrency override. Fundamentally:

- **Tide is NOT part of the scenario DSL** — it is not written into the scenario YAML, but rather parameterizes the **invocation** (HTTP/MCP request to `POST /v1/incarnations/{id}/scenarios/{scenario}`). The scenario DSL of ADR-009 stays unchanged; the new opt fields (`target` / `wave` / `concurrency`) live only in the request payload, not in `main.yml`.
- **Declaration vs invocation — two levels.** `serial:` / `run_once:` / `on:` / `where:` fix the split and the target **at the scenario declaration level** (the service's git repo, the author's intent). Tide adds an **invocation-level** orchestration layer **on top of** the scenario runner — the operator at launch time can split the scope into waves, narrow the target, override concurrency, without changing the scenario. See [`docs/scenario/orchestration.md §2.2.3`](../scenario/orchestration.md).
- **Compatibility with the scenario DSL:**
  - a scenario without `run_once:` is compatible with Tide unconditionally.
  - a scenario with `run_once: true` is **incompatible** with an invocation `wave` (`run_once` = exactly one target host, there is nothing to split into waves) — validation error `tide_run_once_conflict` (422), [`docs/keeper/operator-api.md`](../keeper/operator-api.md).
  - a scenario's `concurrency:` (`serial:`) may be **overridden** by the invocation's `concurrency:` (REPLACE semantics — a runtime knob, not a declared invariant).
- **Per-Surge barrier/state-commit — parity with §7.** Each Surge is a full-fledged scenario run with its own cross-host barrier and state-commit; the barrier invariant of §7 extends to each Surge independently, not to the whole Tide as a whole. Normatively — the mechanics of per-Surge state-commit for Tide (the separate file `docs/scenario/tide-state-commit.md` was not created; Tide is abolished — see [ADR-043](0043-voyage.md#adr-043-voyage--unified-batch-run), per-Surge → per-incarnation state-commit).
- **AND-merge target-override (security invariant).** The invocation's `target.coven[]` / `target.where` only **narrow** the scope (intersection with the scenario's `on:` / `where:`), they do not widen it. The operator cannot, via the invocation, go beyond the declared scenario target. Symmetric to the multi-label AND inside `on:` — a single source of truth for the DSL text [`docs/scenario/orchestration.md §3`](../scenario/orchestration.md).
- **`soulprint.hosts` / `incarnation.host_count` in Tide.** The scenario-context accessors are resolved per-Surge from the **target_resolved_souls** snapshot of the Tide (the AND-merge fixed at Tide start), not from the incarnation's original roster — each Surge sees only its own share.

Goals and rationale — [ADR-040](0040-tide.md#adr-040-tide--invocation-time-scope-chunking--target-override).

**Amendment 2026-05-29 (§7 — per-incarnation state-commit in Voyage = parity with per-Surge).** [ADR-043](0043-voyage.md#adr-043-voyage--unified-batch-run) (Voyage) absorbs Tide via the `kind=scenario` mode. Approach **B1**: a batch (**Leg**) = N **incarnations**, each incarnation = a full-fledged scenario run with its own cross-host barrier and **per-incarnation state-commit**. This is a **direct parity** with per-Surge state-commit ([ADR-040](0040-tide.md#adr-040-tide--invocation-time-scope-chunking--target-override)) and preserves the barrier invariant of §7 without weakening: `incarnation.state` is committed only after a successful barrier of **this** incarnation, a partial commit (part of the incarnation's hosts in one Leg, the rest in the next) is **forbidden**. Alternative B2 (a Leg slices the scope by hosts across several incarnations) is **rejected precisely because it breaks §7** — see [ADR-043](0043-voyage.md#adr-043-voyage--unified-batch-run) point 3. Intra-incarnation waves by hosts remain a separate axis via the scenario's `serial:` (declaration-level), as before.

**Amendment 2026-05-29 (Choir — additive `choirs[]` in scenario accessors).** [ADR-044](0044-choir.md#adr-044-choir--named-host-topology-within-an-incarnation) (Choir) adds an **additive** field `choirs[]` to the scenario context (the list of the host's Choir names in the current incarnation): `soulprint.self.choirs` (per-host, the current host) and `soulprint.hosts[].choirs` (cross-host accessor of the run's hosts, [`docs/scenario/orchestration.md §4.1`](../scenario/orchestration.md) — the site of a future normative edit at S-T4). This is an additive extension of the existing stable fields of `soulprint.hosts` (covens/sid/network/os) — it does not change the `on:`/`where:` grammar, and it is available in `where:` predicates **without a probe** (Choir is a stable declared fact, not a volatile role). `on: [choir]` is NOT introduced in the MVP (the `on:` resolver stays coven-only; narrowing by Choir is via `where:`). The absorbed declared role `soulprint.hosts[].role` ([ADR-044](0044-choir.md#adr-044-choir--named-host-topology-within-an-incarnation) point 2) is fed from Choir (via Voice), not from `spec.hosts[].role`. The normative edit to orchestration.md happens in slice S-T4; this amendment only declares it.

**Amendment 2026-06-12 (optional task field `id:` — a stable address for per-task-changed alerts).** A new **optional** task DSL-core field `id:` is introduced — a stable address of a task by which a subscription from [ADR-052](0052-herald-notifications.md#adr-052-herald--tiding--notifications-about-run-events) (§h) addresses the "this task changed state" event (per-task-changed alert). Decisions:

- **Value format = register format** (the same regex `^[a-z][a-z0-9_]*$` as `register:`): id and register live in **one address space** of the subscription to per-task-changed events, therefore the form is unified.
- **Optional.** The absence of `id:` on a task is normal; existing scenarios/destinies are not broken.
- **`id:` ⊕ `register:` are mutually exclusive.** A task with `register:` is already addressable by it → `id:` is redundant and creates address ambiguity. Both keys on one task is a validation error (`id_register_conflict`). `id:` is intended for tasks **without** `register:`.
- **Pilot restriction: `id:` only on a module task.** In the first pass `id:` is permitted only on a module task (it has its own changed signal). On a `block:`/`include:` task — a validation error (`id_unsupported_target`); lifting the restriction is a separate pass upon request.
- **Uniqueness of `id:` across the run** (after flattening `include`/`block`) is **not fixed in this amendment**; it is a lint cross-ref check (a flatten context is needed), a separate slice. Here — only the per-task format + mutual exclusion with register + the restriction to module.
- **Resolution of `id:` into RenderedTask, the formation of events, and the Tiding binding** are the next slices, not part of this edit (only the grammar of the field and form validation).

Per-task changed addressing (the address space `register ∪ id`) is fixed on the notifications side in [ADR-052](0052-herald-notifications.md#adr-052-herald--tiding--notifications-about-run-events) (§h). The source-of-truth document for the task field — [`docs/destiny/tasks.md §3`](../destiny/tasks.md#3-complete-list-of-task-blocks).

**Amendment 2026-06-18 (the destiny pass's CEL-env additionally registers read-only `soulprint.self.*`).** Jointly with [ADR-010](0010-templating.md#adr-010-templating-engine-cel-for-yaml-expressions-go-texttemplate-for-files) (an amendment of the same date). The destiny isolation invariant is **weakened**:

- **The destiny pass's CEL-env additionally registers read-only `soulprint.self.*`** — the stable layer `SoulprintFacts` ([ADR-018](0018-soulprint-typed.md#adr-018-soulprint-typed-schema-mvp)): `os.*` (including `arch`), `kernel`/`cpu`/`memory`/`network`, the root `sid`/`hostname` and the registry projections (`covens`/`choirs`/`role`). The source is the same per-host soulprint of the target host that Keeper already collects for the render_context of the `.tmpl` phase.
- **`soulprint.hosts` / `soulprint.where(...)` remain scenario-only** (run topology is cross-host) — a reference to them in the destiny pass is still an **isolation error**. The boundary: the target host's self-facts — yes; the run topology — no.
- **Symmetry with the `.tmpl` render_context** ([ADR-012(d)](0012-keeper-soul-grpc.md#adr-012-keepersoul-grpc-contract-one-eventstream-with-oneof-keeper-side-render-forward-compat-only-add)): `self` already flows into `core.file.rendered.render_context` per-host; now `soulprint.self.<path>` in CEL `.yml` ≡ `.self.<path>` in `.tmpl` — a single point of truth for self.
- **`apply: input:` remains a valid channel** (it is not removed): passing the run topology (`soulprint.hosts.where(...)`) into a destiny is still done only via an explicit `apply: input:` forwarding. The bootstrap-create idiom (master discovery via apply:input) is not broken.
- **Rationale.** `soulprint.self.*` is a per-host property of the very host on which the destiny is executed (and not scenario scope: not the parent's `essence`/`register`/`vars`/`input`). A destiny is applied to a concrete host anyway; seeing its stable facts (arch for choosing a package/archive, family for paths) is natural and removes the extra boilerplate `apply: input: { arch: "${ soulprint.self.os.arch }" }`. Security is not harmed: self is read-only, without I/O, without cross-host.

Normative edits — [`docs/templating.md §3.2/§7`](../templating.md), [`docs/destiny/tasks.md §10`](../destiny/tasks.md#10-template-context) (already reflected self in the destiny context). Implementation: `soulprint.self` in the destiny pass is available through the render pipeline (`keeper/internal/render`, `Vars.SoulprintSelf`), `soulprint.hosts`/`soulprint.where` are cut off by `AllowHosts=false` (`shared/cel`).

**Amendment ([ADR-056](0056-staged-render-passage.md), staged-render — Passage). Status → amended.** The per-RUN min-width `serial:` (§2.2.1 orchestration.md) and open Q §8 "per-task granularity" were formulated on the restriction "one `ApplyRequest` per host with all tasks in bulk" — per-task dispatch was not implemented. [ADR-056](0056-staged-render-passage.md) introduces **Passage**: a run = N ordered stages (render→dispatch→barrier→collection of register) along the task axis; per-task dispatch is implemented as N `ApplyRequest`s / `apply_runs` rows per host (per Passage). The main driver is the actual probe→where work (a task with `register.X` in `where:`/`apply: input:`/`params:`/`vars:` is stratified into a Passage **after** the probe that emits `X`), which this ADR promised as canon ([orchestration.md §4/§5](../scenario/orchestration.md#4-volatile-predicate---where)) but keeper executed up-front before the probe. **The barrier/state-commit invariant of §7 is NOT weakened** — `incarnation.state` is committed once after the **last** Passage (a Passage is the task axis, not the commit axis). Decisions and slice map — [ADR-056](0056-staged-render-passage.md).

**Amendment (S-2D1, 2D serial×passage). min-width `serial:` (§2.2.1 orchestration.md) — per-RUN → per-Passage.** With the implementation of Passage, `serial:` turns jointly with the task axis: each Passage rolls its own serial waves over the hosts of THAT Passage, the width is derived from the tasks of a **single Passage**, not the whole run. A probe Passage without `serial:` runs as a single wave, even when another Passage carries `serial:N` (the narrow window of one Passage does not leak into another — a destructive throttle of the probe pass is eliminated). **At N=1 (a single Passage) per-Passage and per-RUN are identical bit-for-bit** — the wording of §2.2.1 for a single-pass run does not change. The pilot restriction `serial_staged_unsupported` is lifted. Details — [ADR-056 §serial / §S4](0056-staged-render-passage.md).

**Amendment ([ADR-061](0061-onboarding-await-and-midrun-reresolve.md) §7, mid-run re-resolve of the roster). Status → amended.** The former §7 invariant — "the run's roster is resolved up-front before the first Passage and does NOT grow mid-run" (`soulprint.hosts` / `on: [incarnation.name]` fixed for the whole run). [ADR-061](0061-onboarding-await-and-midrun-reresolve.md) §S3 **weakens** it to **"the roster is stable WITHIN a Passage; at a refresh boundary it is re-resolved"**. A refresh boundary is a successful `core.soul.registered` step with `refresh_soulprint: true` (a new class of passage-defining edge, "roster-refresh", [ADR-056](0056-staged-render-passage.md)): before the next Passage the scenario-runner re-resolves the roster with a **live snapshot** of the incarnation's current online set (`topology.LoadIncarnationHosts`). This is NOT a monotonic growth `roster ∪ newly_online`, but a fresh snapshot: onboarded VMs become visible, while a host that went offline by the boundary is excluded (targeting the actually-online set). The target case is a single create run provision→onboarding→role. **The barrier/state-commit invariant of §7 is NOT weakened** — `incarnation.state` is committed once after the last Passage (re-resolve is the roster axis, not the commit axis). Details — [ADR-061 §S2/§S3](0061-onboarding-await-and-midrun-reresolve.md).

**Amendment ([ADR-057](0057-state-changes-crud-verbs.md), `state_changes` → an ordered list of CRUD verbs). Status → amended.** The `state_changes` grammar (§7.1) is extended: instead of an unordered map with the keys `sets`/`appends`/`modifies` — an **ordered list of operations**, each element = one CRUD verb `set`/`add`/`modify`/`remove` + a structural `foreach` (reuse of the migration DSL [ADR-019](0019-state-migration-dsl.md#adr-019-state_schema-migration-dsl)). Multiplicity of `modify`/`remove` is via a `match` predicate (all-by-default), not flags; the bindings `elem`/`key`/`value`; an optional `expect` (one/at_most_one/any) — a runtime assertion of cardinality; `add` with `on_conflict` (skip/replace/error, default skip = idempotent). It closes a **latent bug**: `appends`/`modifies` were no-op placeholders without a value source — `incarnation.state` did not grow (`add_replica`/`add_user`/`update_acl`). The barrier/state-commit invariant of §7 is **NOT weakened** (operations are applied after the cross-host barrier, one PG transaction, one `state_history` snapshot, a failure → `error_locked`). Transit: the map form is parsed for one release as DEPRECATED (dual-parse + soul-lint warn), then removed. Normative spec at the time — `docs/scenario/orchestration.md` §7.1, fixed by — [ADR-057](0057-state-changes-crud-verbs.md). Superseded by the [ADR-0084](0084-explicit-state-capture.md) amendment below: the verbs survive, the block does not.

**Amendment 2026-06-20 (read-only `incarnation.state.<path>` in the scenario-render CEL — Variant A).** Jointly with [ADR-010](0010-templating.md#adr-010-templating-engine-cel-for-yaml-expressions-go-texttemplate-for-files) (an amendment of the same date). It closes a gap: a scenario that reads the current `incarnation.state` for a diff (e.g. `update_acl`: `current: ${ incarnation.state.redis_users }`) had no way to reference the state — `state.*` in the scenario-CEL is **not declared** (only the migration-CEL declares it), and `incarnation`, although present in the context, did not materialize `.state`. Decisions:

- **The canonical form is `incarnation.state.<path>`** (not the bare `state.<path>`): the root `incarnation` is already in the scenario context, `state` becomes its subkey. Bare `state.*` in scenario/destiny → a `soul-lint` validation error (`state_naked_reference`) with a hint "use `incarnation.state.*`" — symmetric to how bare `soulprint.<path>` without `.self` is cut. The former wording (§5/§7: `state.*` is a future extension, unavailable) is **replaced**: access is opened under the `incarnation.` prefix.
- **Read-only snapshot.** `incarnation.state.<path>` is a snapshot of `incarnation.state` at the moment the run acquires the row-lock (`stateBefore` under `FOR UPDATE`). CEL **only reads** it, there is no path to mutate state via CEL (mutation is exclusively via `state_changes` after the barrier, §7). Destiny isolation is preserved: a destiny does NOT see `incarnation.state` (it receives values only via `apply: input:`, like the parent's `essence`/`register`/`vars`/`input`).
- **Invariant across all Passages (staged-render).** The snapshot is fixed **once** (`stateBefore`) and is identical at P0 and P1+ — it does **NOT** accumulate between Passages, unlike `register` (which is collected by the barriers of previous Passages). This is a deliberate distinction: `incarnation.state` is the pre-run state from the DB (last known-good), not an intermediate result of the current run.
- **Access.** `incarnation.state.<path>` is visible in `params:`/`where:`/`apply: input:`/`vars:` AND in the `state_changes` context (one projection point — `incarnationVars`). It is available in an ordinary scenario run and a failover-claim (Acolyte); in push mode and L0-trial without state, `incarnation.state.x` yields a regular no-such-key (backward-compat, not a compile-error).

**ADR-019 (migration DSL) is NOT affected**: migration isolation is preserved — there `state.*` stays **bare and mutable** (only `state` is declared, `incarnation`/`input`/… undeclared), Variant A did not leak into the migration-env. Implementation — `keeper/internal/render` (`RenderInput.State`, `incarnationVars`), `keeper/internal/scenario/run.go` (`State: stateBefore`), `shared/config` (`state_naked_reference` in `soul-lint`).

**Amendment 2026-06-23 (new task-level key `assert:` — a keeper-side render-time precondition). Pilot.** A new task-level key of the scenario DSL core `assert:` is introduced:

```yaml
- name: cluster topology matches
  when: "input.redis_type == 'cluster'"
  assert:
    that:
      - "size(soulprint.hosts) == (has(input.shards) ? int(input.shards) : 0) * (1 + int(input.replicas_per_shard))"
    message: "topology mismatch: hosts != shards*(1+replicas_per_shard)"
```

Decisions:

- **Keeper-side render-time precondition.** `assert:` is evaluated **at the model stage** (Keeper's render phase), like `where:` — in the full scenario-CEL context, **including `soulprint.hosts`** (`AllowHosts=true`: assert sees the run's roster, unlike the Soul-side flow-control sandbox where topology is unavailable). All predicates `that[]` must be `true`; **the first `false` aborts the render with a clear error** (`message` + the text of the predicate that failed), and **not a single task is sent to a Soul** — the run does not start. This is "fail at the model stage" (the main goal): an incorrect topology/invariant is rejected BEFORE dispatch, rather than being caught by a shell command on the host.
- **`assert:` is NOT a wire entity.** The Keeper↔Soul proto and the Soul contract **do not change** (like `block:` — it is a render construct). assert does **not** emit a RenderedTask (it is a check, not a task): after a successful assert the task "disappears" from the plan, and the indices of subsequent tasks do NOT reserve a position for it.
- **Discriminator.** `assert:` is the fifth member of the task discriminator (alongside `module:`/`apply:`/`include:`/`block:`): mutually exclusive with them (assert is a check, not executable work). `that` is a non-empty list of CEL-bool strings; `message` is optional (a default message if empty).
- **Gated by `when:`.** assert is subordinate to `when:`: a statically-false `when:` (placeholder-skip ADR-012(d), e.g. `when: input.redis_type == 'cluster'` on a standalone run) → assert is **not** evaluated. On an inactive mode the cluster-assert stays silent.
- **Run-level.** assert is evaluated **once per run** (it uses the roster `soulprint.hosts`), not per-host: it is a run-topology invariant, not a per-host predicate.
- **Motivation.** To remove the `core.cmd.shell`-guard hack (arbitrary shell on a Soul for the sake of control-flow: `test "${ <cel> }" = "true" || { echo ...; exit 1; }`) → a declarative keeper-side check. It reduces the attack surface (no shell execution for the sake of a check) and moves the rejection from the host to the model.
- **Pilot — one use-site.** The cluster size-guard is replaced (`examples/service/redis/scenario/create/cluster.yml`, the size-guard task). The shards-guard (conditional-required) is NOT touched — it is a separate feature `required_when` (the next slice). The rollout to sentinel/sentinel_only is after the pilot review.

Normative edits — [`docs/templating.md §2.1`](../templating.md) (assert.that[] into the table of expression keys, the Keeper side), [`docs/scenario/orchestration.md §2.3`](../scenario/orchestration.md), [`docs/naming-rules.md`](../naming-rules.md). Implementation — `shared/config/scenario_task.go` (the `AssertSpec` grammar), `keeper/internal/render` (run-level eval, abort on false), `soul-lint` (static validation of `that[]`), `keeper/internal/trial` (the harness `expect_render_error` for the fail case, [ADR-023](0023-trial-test-runner.md) amendment).

**Amendment 2026-06-23 (assert is evaluated at TWO points — pre-flight + render fail-safe; form A). Pilot.** The original edition of `assert:` evaluated the predicate ONLY at the async render phase of the run: the failure occurred already AFTER the incarnation was moved to `applying`, which dropped the run into **`error_locked`** — that is, "rejection at the model stage" turned into a fail status and a post-factum analysis (unlock), even though the topology invariant can be checked BEFORE any mutation. The amendment introduces a **two-point evaluation** (the user's choice — form A):

- **(1) Pre-flight at run creation (the main UX).** The assert predicates of the `create` scenario are evaluated SYNCHRONOUSLY in the **request path** of the create handler (`POST /v1/incarnations`), **AFTER** synchronous input validation and **BEFORE** the commit of the incarnation / entry into `applying`. Any `false` → **422 `assert-failed`** to the operator with `message` + the text of the predicate that failed; **the incarnation is NOT created, no fail status (`error_locked`) is set, the run does not start**. This moves the rejection from the async phase (post-factum `error_locked`) to the synchronous request path — symmetric to how [`ValidateInput`](../keeper/operator-api.md) already moved input validation out of the run goroutine into the request path (closing the "created → error_locked" hole).
- **(2) Render fail-safe (a TOCTOU safeguard).** The render branch of `assert:` is NOT removed. Between pre-flight (the request path) and the actual start of the scenario goroutine the roster could have changed (connected souls dropped off/were added — TOCTOU). The render-assert at run start catches this rare case: a failure at render = `error_locked` via the same async-abort as before. Pre-flight is the main UX (422, without a record); the render-assert is a fail-safe (a rare `error_locked`).
- **Single source of eval (no dialect).** Both points evaluate the predicate with ONE function (`render.evalAssertTask`): pre-flight calls the public `render.Pipeline.EvalAsserts` (iterates only the assert tasks, without emitting a RenderedTask), the render branch calls the same `evalAssertTask` inside `Render`. The reuse invariant is covered by a test (one input through both points → a matching verdict). Duplicating the eval is forbidden — otherwise a render↔pre-flight dialect.
- **Roster-at-create.** Pre-flight resolves the roster of connected souls by the incarnation's root Coven label (= `incarnation.name`, ADR-008) — `topology.LoadIncarnationHosts` does NOT require an existing incarnation record (a filter by `souls.coven[]`, the declared roles are empty for a not-yet-created one — not an error). This is the roster of the imminent run (create Start-s immediately). 0 connected souls → a topology-assert (`size==N`) honestly does not hold → 422 (correct: you cannot create+start an N-shard cluster without N hosts). **[SUPERSEDED 2026-07-28 (NIM-235): after NIM-124 a roster cannot pre-date its incarnation, so at create there is nothing to resolve — see the amendment "a roster-reading assert has no pre-flight point at create" below.](#amendment-2026-07-28-nim-235-a-roster-reading-assert-has-no-pre-flight-point-at-create)**
- **Pilot scope — only the create path** (`POST /v1/incarnations`). The paths `incarnation.run` on an existing one / `destroy` / Voyage are follow-up (the render-assert fail-safe is their only gate for now). Use case — the redis cluster size-guard.
- **Error code — `assert-failed` (422), not `precondition-failed`.** 422 Unprocessable Entity (parity with `validation-failed`/input_invalid: the same class "the input semantics do not add up"), NOT 412 Precondition Failed (reserved for the conditional headers `If-Match`/`If-None-Match`). A separate URN from `validation-failed` — the UI/SDK distinguishes "the topology does not add up" from "an input field does not match the schema".

Normative edits — [`docs/keeper/operator-api.md`](../keeper/operator-api.md) (error catalog: `assert-failed` 422), [`docs/naming-rules.md`](../naming-rules.md) (HTTP error type + the two-point eval in the description of `assert:`), [ADR-027](0027-apply-work-queue.md#adr-027-apply-execution-model--work-queue--claim-acolyte-pool-ward-claim) amendment (the pre-flight gate in the run lifecycle BEFORE `applying`). Implementation — `keeper/internal/render` (`Pipeline.EvalAsserts`), `keeper/internal/scenario` (`Runner.PreflightAssert`), `keeper/internal/api/handlers/incarnation_typed.go` (pre-flight in `CreateTyped`), `keeper/internal/api/problem` (`TypeAssertFailed`).

### Amendment 2026-07-28 (NIM-235): a roster-reading assert has no pre-flight point at create

**Context.** The "Roster-at-create" bullet above rests on a fact that [ADR-008 amendment 2026-07-17 (NIM-124)](0008-coven-stable-tags.md#amendment-2026-07-17-nim-124-incarnationname-is-not-a-coven--membership-is-a-first-class-relation) removed: souls carried `incarnation.name` in `souls.coven[]`, so an operator could tag the hosts first and the roster genuinely pre-dated its incarnation. Membership is now the relation `incarnation_membership`, whose FK requires the incarnation row (migration 099), and pre-flight runs BEFORE `incarnation.Create`. At that point the roster is not empty by circumstance but **impossible**.

The bullet's conclusion inverted with it. "0 connected souls → the assert honestly does not hold" was true when 0 meant "nobody is there"; it now means "nobody could be there yet". Every create starter carrying a topology assert answered **422 `assert-failed` unconditionally**, with no input the operator could supply to get past it — a roster cannot be bound before the row exists, and the row is inserted by the very call being rejected. That includes the provision-from-zero shape the gate was least entitled to reject: a create that would have built its own roster mid-run never got to start.

Among the shipped examples nothing was left visibly broken, and the reason is worth stating because it is not reassuring. `examples/service/redis` escaped only because its size-guards carry a hand-written `when: "!(has(input.provision) && input.provision.enabled)"` — protection an author is under no obligation to write, aimed at a different problem (the provision path has no roster invariant to check at all). `examples/service/dragonfly::create` was never exposed for an unrelated reason: it does not declare `create: true`, so the service has an empty create set and `POST /v1/incarnations` treats it as bare — the gate never ran. Neither is a property of the system, which is why the reproduction is a fixture (`examples/service/create-roster-guard`) rather than a shipped service.

**Decision.**

1. **Pre-flight evaluates an assert only if it can read what the assert reads.** An assert whose `when:` or `that[]` references the roster layer (`soulprint.*` — `config.AssertReadsRoster`) is **not evaluated** when the incarnation row does not exist; it is deferred to the render fail-safe, point (2) of the 2026-06-23 amendment. Asserts reading only `input.` / `essence.` / `incarnation.` are unaffected by the row's absence and **keep their pre-flight 422**. The gate is narrowed to what it can answer, not switched off.

2. **The condition is "the incarnation has no row", not "this is the create path."** `topology.Resolver.IncarnationExists` un-collapses the two cases `LoadIncarnationHosts` deliberately merges (PM-decision #3: nonexistent incarnation and empty roster both yield an empty slice). Keying on the row keeps the gate honest for any future caller: give `PreflightAssert` an incarnation that exists and its topology asserts evaluate against the real roster, as they always did.

3. **Deferral is the correct answer, not a concession — the roster is a product of some runs.** A provision-from-zero create (`core.cloud.provisioned` → `core.soul.registered` with `refresh_soulprint: true`) builds its roster mid-run; `Stratify` places roster consumers strictly after the refresh boundary precisely so the size-guard measures the hosts the run created. Such an assert has no pre-flight point under ANY design, which is the same reason `run.go` §3 lets those two plan classes start on an empty roster. The `when:`-gates redis hand-writes on its size-guards remain valid but stop being load-bearing for reachability.

4. **What is genuinely lost, and where it returns.** For a create over a roster that already exists, the 422-before-mutation promise of point (1) is not merely deferred — it never fired, because that flow does not go through `POST /v1/incarnations` at all. Since [ADR-008 amendment 2026-07-28 (NIM-209)](0008-coven-stable-tags.md#amendment-2026-07-28-nim-209-membership-has-an-operator-path--bind--unbind--read) it is: create the incarnation without a bootstrap run (bare, or `lifecycle.auto_create: false`) → bind members → run the create scenario explicitly. `RunTyped` has no assert pre-flight (only `ValidateInput`), so on that path a topology mismatch has always ended in `error_locked`. **Extending the pre-flight gate to the run path** — where the roster is real, excluding the two roster-building plan classes — restores the amendment's intent for the flow that can actually keep it; that is done in the [2026-07-28 (NIM-270) amendment](#amendment-2026-07-28-nim-270-the-pre-flight-gate-moves-to-where-the-roster-is-real) below.

**Trade-off.** A topology mismatch declared at create is now reported by the render fail-safe (`error_locked` + unlock) instead of a synchronous 422 — the pre-amendment behavior, for the one case where the synchronous answer was never available. We accept it: a false 422 that no operator can satisfy is worse than a truthful late failure, and the alternative — resolving the roster from a declared `incarnation.spec.hosts[]` — was rejected. That field was never a roster (it was intent, and its `role` was already degenerate per [ADR-044](0044-choir.md#adr-044-choir--named-host-topology-within-an-incarnation) item 2), `POST /v1/incarnations` did not accept it, adding a SID list to that body was weighed and rejected by the NIM-209 amendment, and it was empty on the provision path anyway — so it would not have fixed the case that motivated this. The field has since been **removed outright** ([ADR-044 amendment 2026-07-30, NIM-330](0044-choir.md#amendment-2026-07-30-nim-330-spechosts-is-removed-voice-is-the-only-source-of-a-declared-role)); the rejected alternative is now not merely unattractive but unavailable, and this trade-off is unaffected — the roster it resolves from was `incarnation_membership` before that change and is `incarnation_membership` after it.

Implementation — `shared/config` (`AssertReadsRoster`), `keeper/internal/scenario` (`Runner.PreflightAssert`, `partitionRosterAsserts`). Guards — `tests/e2e/create_roster_guard_test.go` (the product path: `POST /v1/incarnations` on `examples/service/create-roster-guard`, an ungated topology assert over a roster the run binds itself) and `keeper/internal/scenario/preflight_integration_test.go` (`ResolveCreatePlan` with and without the row; an input-only assert still 422s).

### Amendment 2026-07-28 (NIM-270): the pre-flight gate moves to where the roster IS real

**Context.** The amendment above establishes that a topology assert has no pre-flight point on the create path. That left the form-A promise of the 2026-06-23 amendment — "422 to the operator, the incarnation is not created, no `error_locked`" — with nowhere to live, because the flow that HAS a bound roster does not go through `POST /v1/incarnations` at all. Since [ADR-008 amendment (NIM-209)](0008-coven-stable-tags.md#amendment-2026-07-28-nim-209-membership-has-an-operator-path--bind--unbind--read) that flow is: create the incarnation without a bootstrap run → bind members → run the scenario explicitly. `RunTyped` called only `ValidateInput`, so a topology mismatch there always became an `error_locked` plus a manual `unlock` — precisely what the 2026-06-23 amendment came to remove.

**Decision.**

1. **The gate runs on the explicit-run path too** — `POST /v1/incarnations/{id}/scenarios/{scenario}` and its MCP twin `keeper.incarnation.run`, AFTER `ValidateInput` and BEFORE `Runner.Start`, mirroring its position on the create path. A failure is **422 `assert-failed`** and the run does not start: no `apply_id`, no `applying`, nothing to unlock.

2. **One predicate decides where a roster assert may be answered, and it is shared with the no_hosts gate.** `planBuildsRoster` = all-keeper **or** carries a refresh emitter — the union of the two bypass classes of the [ADR-0061 amendment 2026-06-28](0061-onboarding-await-and-midrun-reresolve.md), now named once and read by both `run.go` §3 and `PreflightAssert`. Both are asking the same question in different words: *is the roster I can see right now the roster this plan is about?* Splitting it in two would be a bug waiting to happen — a false 422 at the gate is the exact mirror of the false `no_hosts` abort those classes were introduced to prevent.

3. **This is a contract change on an existing endpoint, and it is stated as one.** `POST .../scenarios/{scenario}` previously answered 202 and surfaced a topology mismatch asynchronously; it can now answer 422 synchronously. The error catalogue in [`docs/keeper/operator-api.md`](../keeper/operator-api.md) and the `assert:` entry in [`docs/naming-rules.md`](../naming-rules.md) are amended accordingly, and the "pilot scope — only the create path" line of the 2026-06-23 amendment is superseded for the run path (`destroy` / Voyage-spawn remain follow-ups).

4. **The essence a pre-flight assert reads is now the run's own** (NIM-271). Pre-flight used to resolve essence against an incarnation it invented from the request and a zero-value host, which is not what `run()` step 4 will use. It now takes the same input the run will: the real incarnation with `essenceInput` over the first roster host, or `keeperEssenceInput` when the roster is empty; the synthetic form survives only for the create path, where there is no row. Verified empirically before changing anything: on the reachable paths the two already agreed — but only by coincidence of the label-inheritance rule then in force ([ADR-080](0080-label-inheritance-union.md), which made `hosts[0].Coven` carry the incarnation's tags as well as the host's own). [NIM-281](0008-coven-stable-tags.md#amendment-2026-08-05-nim-281-a-label-is-never-inherited) has since removed inheritance, so the roster host carries only what an operator tagged it with and that coincidence is gone. Nothing here regresses, because the fix did not rely on it: pre-flight and the run take the *same* input by construction now, and a test pins it.

5. **`soul-lint` names the boundary at authoring time** (NIM-272). A roster-reading `assert:` in a `create: true` scenario gets `assert_roster_deferred_on_create` — a WARNING, not an error: the construct is legal, does what it says, and IS answered pre-flight when the same scenario is run explicitly. What is wrong is only the author's likely expectation of a 422 on create, and that expectation came from this ADR. The hint points at `validate:` when the invariant fits input alone. Scope is the scenario's own top-level task list, matching `EvalAsserts` — a guard kept in an `include:` branch is not seen, and that gap is stated rather than papered over.

**Trade-off.** An endpoint that answered 202 can now answer 422, so a client that treated "accepted" as "the request was well-formed" sees a new failure mode. We accept it: the alternative is the operator learning about a topology mismatch from an `error_locked` they have to clear by hand, which is the problem form A was chosen to solve. The risk of over-reach — gating a run whose roster does not exist yet — is carried entirely by point 2, which is why that predicate is shared rather than reimplemented.

Implementation — `keeper/internal/scenario` (`planBuildsRoster`, `Runner.PreflightAssert`, `Runner.resolvePreflightEssence`), `keeper/internal/api/handlers` + `keeper/internal/mcp` (the gate on both run surfaces), `shared/config` (`validateAssertReachability`). Guards — `tests/e2e/run_roster_guard_test.go` (mismatch → 422 with the incarnation still `ready`; converging → 202 and success; a roster-building plan on an empty roster → 202), `keeper/internal/scenario/preflight_essence_integration_test.go`, `shared/config/assert_reachability_test.go`. The operator-facing summary of where each assert is answered lives in [`docs/scenario/orchestration.md §2.3.1`](../scenario/orchestration.md).

**Amendment 2026-06-23 (new input-schema key `required_when` — conditional requiredness of a field).** An **optional** input-DSL key `required_when: "<CEL predicate over input.*>"` is introduced (the standard [`docs/input.md`](../input.md), common to destiny / scenario / the module manifest). The parameter becomes required **when** the predicate is true; when the predicate is false the absence of the parameter is permissible. This closes the gap between the unconditional `required: true` (always required) and "required only in one mode". Decisions:

- **Validated at Keeper's input stage** (`config.requireInputValues`, AFTER merging defaults, BEFORE the render phase and dispatch) — the same place as the unconditional `required`. Absence when the predicate is true = an input error (422 `input_invalid` / sync-`ValidateInput`); in L0-trial — an abort at input resolution (caught by `expect_render_error`, ADR-023). The error message carries the same recognizable form as `required` ("required … not provided"), plus the text of the condition.
- **The predicate context is only `input.*`.** This is input validation, not render: `essence.*` / `soulprint.*` / `register.*` / `incarnation.*` / `vault()` / `now()` are unavailable (the predicate is a pure function of other input values of the same run). The sandbox is provided by a **narrow CEL environment** (the single variable `input` is declared) — a reference to other names = a compile error undeclared reference, symmetric to the migration-CEL sandbox ([ADR-019](0019-state-migration-dsl.md#adr-019-state_schema-migration-dsl)).
- **Layering.** `shared/config` (where the input-DSL and its resolution live) does NOT depend on `shared/cel` (the full engine with vault/glob/merge/coverage). A direct import `config → cel` is rejected (it would bloat the base config with the heavy engine and its surface). Instead — a **narrow standalone evaluator inside `shared/config`** on top of `cel-go` (the library is already in the `shared` module), an env with the single variable `input`. There is no cycle (`cel` also does not import `config`); the full Engine is not duplicated (the narrow evaluator carries less surface — exactly the input-only predicate).
- **Additive / forward-compat.** The field is optional; existing schemas are not broken. `soul-lint` validates `required_when` statically (CEL parsability).
- **Motivation.** It removes shell guards of conditional requiredness (`core.cmd.shell` with `test "${ has(input.X) }" = true || exit 1`) — arbitrary shell for control-flow on a Soul is replaced by declarative keeper-side input validation: the operator gets a rejection before the run starts, the attack surface does not grow. Use case — the `redis` service: `shards` when `redis_type == 'cluster'`, `master_ip` when `redis_type == 'sentinel_only'`.

Normative spec — [`docs/input.md`](../input.md) ("Conditional requiredness: `required_when`"). Implementation — `shared/config` (`InputSchema.RequiredWhen`, `requireInputValues`, the narrow input-CEL evaluator), a static parse-check in `validateInputSchemaNode` (`soul-lint`).

**Amendment 2026-06-23 (new top-level scenario key `compute:` — computed run vars).** An **optional** top-level scenario block `compute:` is introduced (next to `input:`/`state_changes:`/`tasks:`) — a map `<name>: <CEL expression>` which Keeper resolves **ONCE per run** and makes available as `compute.<name>` in `apply: input:` **and** in `state_changes`. It closes a duplication: `apply: input:` and `state_changes` are different CEL contexts, neither sees the task-level `vars:`, therefore a common expression (for example, a large `merge()` translation of simple input into `redis.conf`) had to be written twice and synchronized by hand. Decisions:

- **Resolution context — run-level, WITHOUT `soulprint`.** `compute:` is evaluated in `input.* / essence.* / incarnation.* / register.*` — **without** `soulprint.self` / `soulprint.hosts`. This is a **structural host-invariance barrier** (undeclaredness, not a textual guard): a reference to `soulprint.*` → CEL no-such-key. Consequence — `compute.<name>` is identical for all hosts, therefore a single value correctly goes both into `apply: input:` (resolution on the first host by `SID`) and into `state_changes` (per-RUN, not per-host). Per-host values, as before, are expressed by direct per-host CEL in `params:` / templated `.self`, not via `compute:`.
- **Declaration order matters.** `compute[i]` may reference a previously declared `compute[j]` (j<i); a forward reference → no-such-key. Therefore it is stored as an ordered list (the decode preserves the YAML key order), not a map.
- **Isolation from destiny (V2).** `compute:` is a scenario entity: it does **not** leak into the isolated destiny pass (`apply: { destiny: … }`). A destiny sees only the result via `apply: input:`; inside a destiny `compute.<name>` → no-such-key (like `register.*`/`essence.*`).
- **Names.** A compute-var name is a CEL-field-accessible identifier (`^[A-Za-z_][A-Za-z0-9_]*$`); it must not shadow the root context names (`input`/`register`/`incarnation`/`soulprint`/`essence`/`vars`/`compute`).
- **Additive / forward-compat.** The field is optional; existing scenarios are not broken. `soul-lint` validates `compute:` structurally (name/format/reserved/non-emptiness via `LoadScenarioManifest`); the CEL syntax is checked at the render phase uniformly with the other expressions (`where:`/`sets:`).
- **Motivation.** Use case — the `redis` service: `compute.redis_config` (a merge-translation of simple input into a `redis.conf` map, branching by `input.redis_type`) is declared once and used as `${ compute.redis_config }` in `apply: input: config:` of the standalone/cluster/sentinel branches **and** in `state_changes.redis_config` — the "state ≡ live config" drift is removed by the mechanism itself.

Normative spec — [`docs/scenario/orchestration.md §2.4`](../scenario/orchestration.md#24-compute---calculated-vars-of-the-run). Implementation — `shared/config` (`ScenarioManifest.Compute`/`ComputeBlock`, `validateComputeBlock`), `shared/cel` (the context name `compute`, `Vars.Compute`), `keeper/internal/render` (`Pipeline.resolveCompute` — one resolution in `Render`/`EvalAsserts`, injection into `hostVars`/`keeperVars`; the third call site, `RenderStateOps`, went with `state_changes:` in [ADR-0084](0084-explicit-state-capture.md)).

**Amendment 2026-06-23 (new top-level scenario section `validate:` — declarative input invariants).** An **optional** top-level scenario section `validate:` is introduced (next to `input:`) — a list of rules `[{that: <CEL-bool>, message: <str>}]`. Each rule declares an **input invariant** that must be true; the first `false` rejects the run to the operator **before the incarnation commit and before applying**. It closes the "must be X, not Y" gap for **cross-field preconditions** not expressible by a single schema key (`enum`/`min`/`max` — about one field) and not covered by `required_when` (about the **presence** of a field, not about the **relation** of values). Decisions:

- **The rule context is INPUT-ONLY** (the user's choice). The `that` predicate sees **only `input.*`** — the same narrow cel-go sandbox as `required_when` (the single variable `input` is declared). A reference to `essence.*`/`soulprint.*`/`register.*`/`vault()`/`now()` → a compile error undeclared reference: a **structural input-only barrier by undeclaredness**, not a textual guard. `validate:` covers invariants of the INPUT; topology/roster checks (`size(soulprint.hosts) == …`) remain the domain of `assert:` — it has the full scenario-CEL context with `soulprint.hosts`.
- **It COMPLEMENTS, does not replace.** `validate:` coexists with `assert:` and `required_when` (all three remain). The boundary "which mechanism when":

  | Mechanism | CEL context | What it checks | When it fires | Error code |
  |---|---|---|---|---|
  | `required_when` (input-schema key) | input-only | the **presence** of a field under a condition over other input | input stage (request path) | 422 `validation-failed` (`input_invalid`) |
  | `validate:` (top-level section) | input-only | a **cross-field invariant** of the INPUT (relation of values) | pre-flight (request path), BEFORE commit/applying | 422 `validation-failed` |
  | `assert:` (task discriminator) | full scenario context (`soulprint.hosts`) | an invariant of the run's TOPOLOGY (roster) | pre-flight create + render fail-safe | 422 `assert-failed` |

- **When — pre-flight on the request path.** `validate:` is evaluated in `scenario.ValidateInput` (the same phase as `required_when`: AFTER merge/required/type validation over the **merged** input, BEFORE the incarnation commit and entry into `applying`). The first `false` → **422 `validation-failed`** to the operator with the rule's `message`; the incarnation is NOT created, `error_locked` is NOT set. It covers both request paths — `CreateTyped` (`POST /v1/incarnations`) and `RunTyped` (`POST .../scenarios/{scenario}`).
- **A render fail-safe is NOT needed** (in contrast with `assert:`, form A). `assert:` holds a two-point eval because the roster (`soulprint.hosts`) could have changed between pre-flight and the goroutine start (TOCTOU). `validate:` is deterministic from `input.*`, which between the request path and the run start **does not change** — a single point (pre-flight) is sufficient.
- **A separate sentinel from the input schema.** A `validate:` failure → `scenario.ErrValidateFailed` (distinguished from `ErrInputInvalid`); both map to 422 `validation-failed`, but are distinguishable for the handler (different detail text: "input does not match the schema" vs "a scenario input invariant is violated"). The order is strict: first schema/required/type, then validate invariants (the `that` rule is written on the assumption of correct types).
- **The element form = bit-for-bit `assert.that`+`message`** (reuse of the eval machine). `that` is a mandatory non-empty CEL-bool string (the whole string = CEL without a wrapper, like `where:`); `message` is a mandatory non-empty string (unlike `assert.message`, which is optional: assert has the task name as a fallback, a validate rule has no name → an anonymous 422). Without a second CEL engine: `that` is compiled by the same `compileRequiredWhen` (input-env) as `required_when`.
- **Additive / forward-compat.** The section is optional; existing scenarios are not broken. `soul-lint` validates `validate:` statically (structure + parsability of `that` input-only via `LoadScenarioManifest`). In L0-trial a validate failure aborts the case via the same channel as `required_when` (caught by `expect_render_error`, [ADR-023](0023-trial-test-runner.md)).
- **Motivation / pilot.** Use case — the `redis` service, `sentinel` mode: `sentinel_quorum <= 1 + replicas` (the quorum cannot exceed the number of sentinel daemons, otherwise failover is unreachable). This is a relation of two input fields — not `min/max` (the ceiling = another field) and not `required_when` (not about presence); before `validate:` it would have had to be cobbled together with a keeper-side shell guard or dropped as an obscure runtime failure. The first production consumer after the pilot is slice B ("TLS or port").

**Amendment 2026-06-24 (a conditional `when:` on an include task — conditional-include = a render-phase group-drop). Pilot.** On an include task (`- include: <file>`) a **static** `when:` (next to `name:`) is now permitted — a conditional include. Previously `when:` on an include was rejected as `include_modifier_unsupported` (the expansion whitelist was only `include:`/`name:`). A conditional include is a **real exclusion of a group of tasks from the plan**, not masking: when the include-when is false, ALL tasks of the included file are physically absent from the plan (not emitted, the index is not reserved). It closes the case "the cluster part is included only when `input.topology == 'cluster'`" without smearing a single `when:` across every task of the include file. Decisions:

- **The predicate scope — only static.** include is expanded into a flat list **BEFORE** the stratification phase ([ADR-056](0056-staged-render-passage.md)): the register of previous tasks is not yet collected, the per-host `soulprint` is unknown. Therefore the include-when must be **static** — depending only on `input.*`/`essence.*`/`incarnation.*`/`vars.*` (the same `isStaticWhen` criterion as for the static-when placeholder-skip [ADR-012(d)](0012-keeper-soul-grpc.md)). A dynamic predicate (`register.*`/`soulprint.*`) → the error `include_when_dynamic_unsupported` (the expansion rejects it; `soul-lint` catches it offline by static validation of the include node without resolving the target). A dynamic include-when is **deferred** (an open Q, see below): it requires the decision "defer the include expansion until the post-probe Passage", which changes the phase model.
- **The carry-through + group-drop mechanism.** `config.ExpandIncludes`, when expanding a conditional include, threads the include-when and the **group id** into EVERY spliced task through the NON-YAML fields `Task.IncludeWhen`/`Task.IncludeGroupID` (set ONLY by the expansion, forward-compat like `RenderInput.destinyIsolated` — not parsed from YAML, not included in `taskKnownKeys`). Each conditional include gets its own monotonic group-id (`0` is reserved for "outside a conditional include"); a nested conditional include preserves ITS OWN (more specific) group-id — `stampIncludeGroup` does not overwrite an already-stamped nested group. Render, at the start of the loop, **BEFORE** `emitStaticWhenSkip`, for a task with `IncludeGroupID != 0` computes the include-when ONCE per group (a cache by group-id) with the same `evalStaticWhen`; false → `continue` without emitting a `RenderedTask` and without `idx++`.
- **Coexistence with block-static-skip (the discriminator `IncludeGroupID` vs `block`).** This is a **separate** mechanism from the placeholder-skip of a block with a static-false `when:` (the block-static-skip amendment above): block-static-skip **reserves** the index and emits a per-child placeholder with its own `register:` (holds the in-file register visibility); group-drop does **not** reserve the index and physically removes the tasks. The split is strict by `IncludeGroupID`: a conditional-include task goes through the group-drop branch, a block task through the former placeholder-skip branch. Both coexist in one plan.
- **Safety (no `ErrOnChangesUnknownRegister`).** Dropping a group could leave a "dangling" external `onchanges:` referencing the `register:` of a dropped task (`resolveOnChanges` → `ErrOnChangesUnknownRegister`). This does not happen: a **cross-file register reference is already lint-forbidden offline** — the per-file `validateTaskRefs` validates the register-scope of each file separately, therefore an `onchanges:` of the main file on a register of an included file is rejected as `unknown_register_reference` at load (and an unexpanded include before render → `ErrUnexpandedInclude`). An external consumer of a dropped group's register is impossible in a valid scenario → `resolveOnChanges` after a group-drop does not encounter a dangling reference.
- **Both include-expansion paths (scenario + destiny), the per-pass cache is separate.** The group-drop works on **both** render paths that expand include into a flat plan: the scenario pass `Pipeline.Render` (`keeper/internal/render/pipeline.go`) and the isolated destiny pass `renderApplyDestiny` (`keeper/internal/render/destiny.go`). The mechanics are identical (the carry-through `Task.IncludeWhen`/`IncludeGroupID` is set by the same `config.ExpandIncludes`, called for destiny at `keeper/internal/artifact/destiny.go` and in the Trial-fixture resolver; the group-drop branch stands first in the loop, BEFORE `emitStaticWhenSkip` and block handling), but with two invariants of the destiny path: (1) the include-when of a destiny group is computed in the **isolated destiny-env** (`evalIncludeWhen(destinyIn, …)` — `destinyIn.Input` = the resolved `apply.input` + schema-defaults, WITHOUT scenario-scope: the scenario-input/vars/register are not visible), NOT in `parentIn`; (2) the cache `includeGroupKeep` is a **separate map per pass** (the scenario loop and each destiny pass hold their own), the destiny group ids do not intersect with scenario's. The register-isolation is identical to scenario (a cross-file register of a dropped destiny group is lint-forbidden per-file by the same `validateTaskRefs`, therefore `resolveOnChanges` does not encounter a dangling reference). The discriminator `IncludeGroupID` is orthogonal to block: at `keep=false` the whole group is dropped (including the destiny-block task and its children) BEFORE the `renderDestinyBlock` branch.

The declaration is **per-scenario in the flag**, NOT a list in `service.yml` (scenarios are auto-discovered by directory anyway, [`docs/service/manifest.md`](../service/manifest.md); a centralized list would duplicate them). `destroy` is NOT marked with this flag (teardown is a special flow `DELETE /v1/incarnations/{id}`, not a run).

A duplicate top key (one input field declared both in the covenant and in the scenario; one compute name; an intersection of `set` fields of `state_changes`) → the error `section_key_conflict` (**fail-closed**: NOT last-wins, NOT override). The intent "the base = the common, the scenario = only its own additional" is made explicit: a collision = an author's error, not a silent overwrite. Deep merging (merging nested map values) is rejected — it hides which part of the schema came from the covenant, and reproduces the "diverging override" footgun from [ADR-062](0062-input-types.md) (the same logic there: `$type` is either a reference or inline, not their merge).
  - **The delta of the create variants.** `create` adds the provision specifics (`+provision`: the provision section/fields), `create_from_souls` — a **zero delta** (fully covered by the covenant, it carries no sections of its own above the base). This is exactly the target gain: the common contract lives in one file.
- **`form:` is NOT merged (local-only).** A scenario's UI `form:` block ([ADR-045](0045-param-dsl.md)/[ADR-042](0042-backend-driven-ui.md)) is **not** inherited from the covenant — it remains a property of the specific scenario (the form layout for a specific operation). A covenant carries the data contract, not the presentation.

The reason: a local `compute[i]` is entitled to reference a covenant `compute[j]` (`compute` resolves left to right, §2.4 "the declaration order matters"), a local `state_changes`/`validate` — to rely on what has already been applied from the covenant. The reverse order (locals first) would break the forward-reference covenant→local.
- **The resolution point — `LoadScenarioManifestResolved` (BEFORE input validation/render).** The merge is performed at a **single manifest resolution point** (the working name `LoadScenarioManifestResolved`) — isomorphic to how the `$type` resolution ([ADR-062](0062-input-types.md)) and the `include` expansion (`config.ExpandIncludes`, §6) are unfolded BEFORE the consumers: load the service's `covenant.yml` → merge the 4 sections into the scenario manifest (add-only, fail-closed on a conflict) → then the **ordinary** pipeline on the ALREADY-merged manifest (input-merge → required → render → dispatch). The downstream consumers (`ValidateInput`, `Pipeline.Render`, `EvalAsserts`, `EvalValidateRules`, soul-lint) see a whole manifest — there is **no fragment-aware code outside the resolution point** (just as `$type` does not reach the render phase, the covenant does not reach the section consumers as a separate entity).
- **MVP restrictions.**
  - **One `extends:` per scenario** (not a list of covenants): multiple inheritance would introduce an order-dependent merge and cross-covenant conflicts — disproportionate to the goal of wave 1.
  - **A covenant does NOT extend a covenant** (no recursion/chain): a covenant is a flat leaf, it does not inherit another covenant. This removes the need for cycle-detection at this layer (unlike `$type`, where type→type is legal and cycle-detection is mandatory).
  - **A covenant carries ONLY 4 sections** — `input:` / `compute:` / `state_changes:` / `validate:`. ⚠ **Three since [ADR-0084](0084-explicit-state-capture.md) (see amendment below): `state_changes:` is gone from the grammar and a covenant carrying it is rejected as any other foreign key; a shared write travels as a step through service-level `include:`.** **NOT** `tasks:` / `name:` / `create:` / `form:` / `extends:` (any other top key in a covenant file → a validation error). A covenant is the contract of a run's **data**, not its steps/identity: tasks (`tasks:`) are shared via the service-level `include:` (§6, the filename fallback), not via a covenant.
  - **One `covenant.yml` per service is a convention (not a hard restriction).** The mechanism resolves `extends: <name>` → `<name>.yml`, therefore a service can technically have several covenant files; but it is **recommended** to keep one common section contract in `covenant.yml` (`extends: covenant`). Several covenant files are justified only for unrelated families of scenarios with different common contracts — for a typical service this is unnecessary fragmentation.
- **form validation under `extends:` — a POST-merge invariant (S2b).** The pilot uncovered a phase contradiction: the invariant "`form:` ⊆ input" (the form fields reference only existing input parameters) was checked at the **schema phase** (`LoadScenarioManifestFromBytes`, NO-I/O), but under `extends:` the **effective** input exists only **after** the covenant-merge (covenant ∪ local), and the merge requires reading the covenant file from FS (keeper-side). The decision: under `extends:` form validation is **moved** from the schema phase to the **Resolved stage** — after `MergeCovenant`, against the effective input. A scenario **without** `extends:` — form validation stays at the schema phase, **bit-for-bit as now**. This is the same phase logic as with `$type` ([ADR-062](0062-input-types.md)): the schema is not final until the Resolved resolution, invariants "over the final schema" are computed after it.
- **A single covenant resolver in `shared/config` (S2b, no dialect).** An FS wrapper over `MergeCovenant` + `LoadCovenantFragmentFromBytes` + the post-merge form validation — **one** resolution path called by **all three** consumers: the keeper request-path (via `artifact`), the trial-harness, and `soul-lint`. Duplicating the merge/validation per consumer is forbidden — otherwise a dialect "how the lint merges/validates a covenant" ≠ "how prod does" ≠ "how trial does", i.e. **the same drift class** that this feature eliminates (the single source of the contract would be devalued by three diverging resolvers). **The layer invariant:** the `*FromBytes` functions (`LoadScenarioManifestFromBytes`, `LoadCovenantFragmentFromBytes`) stay **NO-I/O** (a pure parse of bytes); reading a covenant file from FS lives **strictly** in the Resolved layer (the FS wrapper), it does not leak into the byte parsers — this conforms to the invariant "the resolution point is BEFORE the consumers, there is no fragment-aware code outside it" above.
- **Forward-compat.** The key `extends:` is **optional**; a scenario **without** `extends:` behaves **bit-for-bit as now** (the resolution point, in the absence of `extends:`, is a no-op pass-through, the manifest is not touched; form validation stays at the schema phase). Existing services without a `covenant.yml` are not broken.
- **Relation to `types.yml`/`$type` and `IncludeResolver`.** A covenant is the **third** service-level shared mechanism in the same row: `types.yml` shares **named input schemas** ([ADR-062](0062-input-types.md)), the service-level `include:` (the two-level `IncludeResolver`, §6) shares **sets of tasks**, `covenant.yml` shares the **common section contract** between scenarios. All three resolve BEFORE the consumers and remove copy-paste of a different nature (type / tasks / section-contract); none of them introduces a wire entity.

Normative edits — [`docs/scenario/orchestration.md`](../scenario/orchestration.md) (a § about `extends:`/covenant next to the task-include §6), [`docs/service/manifest.md`](../service/manifest.md) (`covenant.yml` in the root of the service repo). Implementation (plan) — `shared/config` (the `extends:` grammar + loading/validation of `covenant.yml` with a 4-section sub-schema), the resolution point `LoadScenarioManifestResolved` (add-only merge, `section_key_conflict`), the consumers (`ValidateInput`/`Pipeline.Render`/soul-lint) call the resolution point without knowledge of the fragment. The Redis service is the pilot (`create`/`create_from_souls` via `extends: <covenant>`, the create↔create_from_souls drift is eliminated).

**Amendment 2026-07-26 (destiny-input parity: `validate:` and full value validation on the destiny contract).** The `input:` contract of a **destiny** is now enforced with the **same** validator, in the **same** order, as a scenario's — closing an asymmetry in which a rich input-validation mechanism existed in `shared/config` but only scenario used it. Previously the destiny render pass checked unconditional `required:` plus `default:` merge and nothing else: `required_when:` was parsed into the schema but **never evaluated**, values were **never** checked against their own `type`/`enum`/`pattern`/`format`/length, and `destiny.yml` had no `validate:` key at all. The only way to express a destiny input invariant was an `assert`-style guard task per case — a runtime task over the full context, which is the wrong instrument for a pure input precondition. Decisions:

- **`validate:` becomes a top-level key of `destiny.yml`**, with the grammar, the input-only CEL sandbox and the schema validator already defined for scenario (the amendment 2026-06-23 above): a list of `[{that: <CEL-bool>, message: <str>}]`, `that` compiled against the single declared variable `input`, `message` mandatory, first `false` wins. `ValidateRule` and `validateValidateBlock` are **reused, not duplicated** — the same single source that already serves scenario and the covenant fragment.
- **One shared composition, three callers.** The order "schema first (defaults → `required`/`required_when` → value validation), invariants second" is factored into a single function (`config.ResolveInputContract`) called by the scenario pre-flight gate, the destiny render pass and the L0 trial harness. The order is load-bearing: a `that` predicate is authored assuming correct types, so a type violation must surface as a schema error, never as a CEL blow-up inside a rule. Re-implementing the sequence per caller is forbidden for the same reason the covenant resolver is single-sourced (the amendment 2026-06-29 above): three copies mean three dialects of "what a contract means".
- **The destiny gate sits at RENDER, not on the request path.** Scenario input is typed by an operator, so it is gated pre-flight (422 `validation-failed`, before the incarnation commit). Destiny input is **computed by the scenario** from its own input/vars/state, so the equivalent point is the render of the calling `apply:` task, when those values first exist. This makes it defense-in-depth in the literal sense: it catches a **scenario** handing its destiny values the destiny's own contract forbids — a class of bug no operator-facing validation can see.
- **Strict immediately, no warn-first phase.** A contract violation is a render error from the first release; there is no transitional mode that logs a warning and proceeds. A destiny that declares a contract and is handed values violating it must fail loudly and name the offending field (or quote the failing rule's `message:`) rather than deploy something the contract ruled out. This is **breaking** for any destiny whose callers were silently out of contract — see the migration note in [`docs/destiny/input.md`](../destiny/input.md).
- **`validate:` complements `assert:`, it does not replace it.** A destiny `validate:` rule is input-only by construction (referencing `essence`/`soulprint`/`register`/`vault()` is an undeclared-reference compile error), which matches destiny isolation exactly — a destiny sees only its own input anyway. Topology, roster and register checks remain the province of `assert:`, which is a **scenario** construct: render-time `assert:` inside a destiny's `tasks/main.yml` is not supported (`guardDestinyTask` rejects it as a non-module task), and this amendment does not change that boundary.
- **Defense in depth offline too.** `soul-lint validate-destiny` runs the same schema validation, so an unparsable `required_when`, a `that` referencing scenario scope, a missing `message` or an empty `validate: []` are caught before any run.

Normative edits — [`docs/destiny/manifest.md`](../destiny/manifest.md) (the `validate:` field), [`docs/destiny/input.md`](../destiny/input.md) (what the Keeper round checks, `required_when`/`validate:` in destiny, the migration note), [`docs/input.md`](../input.md) (`required_when`/`validate:` are artifact-agnostic; only the enforcement point differs). Implementation — `shared/config/input_contract.go` (`ResolveInputContract`, `ErrValidateRuleEval`), `shared/config/destiny.go` (`DestinyManifest.Validate` + `validateValidateBlock` in `schemaValidateDestiny`), `keeper/internal/render/destiny.go` (`ResolvedDestiny.Validate`, `resolveApplyInput` over the shared contract, `ErrDestinyInputInvalid`/`ErrDestinyValidateFailed`), the three destiny resolvers (`scenario`/`pushorch`/`trial`) carrying `Validate` through. Guard tests — `shared/config/input_contract_test.go` (table over the shared validator), `shared/config/destiny_test.go` (the `validate:` block schema), `keeper/internal/render/destiny_input_contract_test.go` (render-level enforcement of each rule class). The pilot `examples/destiny/redis` gained a `validate:` block; two contract drifts the check surfaced in `examples/` are recorded in the migration note.

**Amendment 2026-07-26 (within-block `include:` — the block pilot restriction is lifted, both layers).** An `include:` among a `block:`'s children was **not** expanded: `config.ExpandIncludes` walked the top-level list and passed a block through untouched, and both render layers rejected a surviving include child (`guardPilotBlockChild` / `guardDestinyBlockChild`). This was a deliberate deferral of the block pilot ("the design intent is preserved, pilot C1 does not implement it" — [`docs/destiny/tasks.md §6.5`](../destiny/tasks.md)), not a design boundary: everything around it was already recursive through `block:` (the conditional-include stamping, the flat `register ∪ id` uniqueness check, the offline dynamic-when detector). The restriction is **lifted**. Decisions:

- **A block is not an expansion boundary.** `expand()` recurses into `Block.Block` with the **same** visited-stack and accumulated ancestor-when, so an include child splices in place and everything derived from the chain works unchanged at any nesting depth: `include_cycle` and `include_depth_exceeded` fire through a block exactly as at the top level, and the nested conditional-include conjunction (`(ancestor) && (own)`) cascades across the block boundary. Nesting is unlimited (`block` → `include` → `block` → `include`) — one mutual recursion `expand ↔ expandOne`, no separate within-block dialect.
- **Both layers, because the expander is shared.** `config.ExpandIncludes` is the single expansion point for every caller (the destiny artifact loader, the scenario runner's run/pre-flight/render-host paths, both trial harnesses), so the fix lands in destiny **and** scenario at once. That is also the required outcome, not a convenience: this ADR grants scenario the full destiny task DSL, so a construct legal in one layer and rejected in the other would be a contradiction of §1.
- **Expansion copies the block, it does not splice in place.** `BlockTask` is copied before its children are rewritten: a parsed manifest outlives expansion (Trial re-renders the same manifest per case, the loaders cache artifacts), so an in-place splice would leak expanded state across runs.
- **The two gates compose in a fixed order — group-drop, then static-when skip.** A conditional include inside a block stamps its group onto the spliced children, which then also inherit the block's `when:` via AND (`mergeBlockInheritance`). These stay independent axes: `walkBlockChildren` decides group-drop **first** (physical removal, no placeholder, no index), then the static-when skip (placeholder that keeps index and `register:`) — mirroring the top-level loops. So "the include was not taken" and "the block is off" remain distinguishable in the plan, and a child of a dropped group never consumes an index.
- **One group decision per pass.** The three copies of the group-drop branch (scenario loop, destiny loop, assert pre-flight) are factored into `Pipeline.keepIncludeGroup` over a per-pass `includeGroupCache`, which is now threaded into the block walk. A group spliced inside a block is therefore evaluated once for the whole pass, in that pass's env (isolated destiny input for a destiny pass) — the same single-source-per-mechanism rule as `ResolveInputContract` in the amendment above.
- **The render guards stay, reframed as defense-in-depth.** `guardPilotBlockChild` / `guardDestinyBlockChild` keep rejecting an include child with `ErrUnexpandedInclude`. After this change no include child should ever reach render, so the case no longer means "outside pilot scope" — it means the expander was skipped or is broken, and failing loudly beats rendering a silently incomplete block.

Normative edits — [`docs/destiny/tasks.md §4`](../destiny/tasks.md) (an include may sit inside a block), [`docs/destiny/tasks.md §6.5`](../destiny/tasks.md) (block contents, the conditional-include composition, the post-pilot list and the destiny-block key boundary). Implementation — `shared/config/include_expand.go` (block recursion in `expand`), `keeper/internal/render/pipeline.go` (`includeGroupCache`/`keepIncludeGroup`), `keeper/internal/render/block.go` (group-drop in `walkBlockChildren`, cache threaded through `renderBlockTask`), `keeper/internal/render/destiny.go` (same through `renderDestinyBlock`). Guard tests — `shared/config/include_expand_block_test.go` (splice/nesting/cycle/depth/conditional cascade/address uniqueness/source not mutated), `keeper/internal/render/include_block_test.go` (expand→render end-to-end in both layers: inheritance, the four-cell group-drop × block-when matrix, nested blocks).

**Amendment 2026-07-27 (the task DSL-core concurrency key is `async:`; `parallel:` is reserved).** [ADR-0075](0075-intra-host-async-tasks.md) settles the intra-host concurrency construct that this ADR's task core carried as a specification with no implementation. The key is **`async: true`** — fire-and-forget, a flag on an ordinary task, not a grouping mechanism — and **`parallel:` becomes reserved and unrecognized** (`unknown_key`), held for a future concurrent group with a join, which is a different construct rather than a synonym. Barriers are the explicit `require:` (preferred, statically readable), an implicit reference to `register.<name>`, and the mandatory final barrier at the end of the run; a failure is observed at the barrier that awaits it and in-flight siblings are never cancelled. Two boundaries the earlier text got wrong are now stated normatively: an implicit register reference is a **local** wait only from the Soul-side keys (`when`/`changed_when`/`failed_when`/`until`/`onchanges`/`onfail`/`require`) and a **full** Passage barrier from the Keeper-side ones (`where`/`vars`/`params`/`apply.input`/`output`/`loop.items`/`loop.when`, per [ADR-056](0056-staged-render-passage.md)); and an async task never outlives its Passage, so the final barrier coincides with "the end of the destiny" only on an unstratified plan. The rename is free of migration — the key had no consumer anywhere in `examples/` and no run could carry it (both render guards rejected it and `RenderedTask` had no field). Normative edits — [`docs/destiny/tasks.md`](../destiny/tasks.md) §6 (rewritten), §4/§6.5/§7/§8/§12, [`docs/scenario/orchestration.md`](../scenario/orchestration.md) §2.2/§7, [`docs/naming-rules.md`](../naming-rules.md).

**Amendment 2026-07-30 (NIM-287): a group construct's requisites compose as OR and widen; `when:` composes as AND and narrows.** Both constructs that expand into a group — `block:` (since pilot C1) and `apply:` (since NIM-245) — pass their own `onchanges:`/`onfail:`/`require:` down to every task of the group, merged with the task's own as a **union of names** (`unionNames`). On the wire that is one flat `repeated int32`, and `skipOnChanges`/`skipOnFail` read it as OR. `when:` on the very same construct is merged by `andMergePredicate` into `(<outer>) && (<inner>)`. The two axes therefore compose in **opposite directions**, and until now neither document said so.

**Decision — the OR/union semantics is normative, and the asymmetry is stated rather than removed.** A group-level requisite is a pure narrowing for a descendant that declares none of its own — the case the key was built for — and a **widening** for one that does: `onchanges: [inner]` under a group carrying `onchanges: [outer]` becomes `[outer, inner]` and runs when either changed, so the descendant runs *more* often than its own line reads. Consequences we accept and now write down: there is no way to spell "outer AND inner", and no workaround reproduces it (`when:` on an applier must be static; `where:` selects hosts rather than reacting to an outcome). The advice is to keep the requisite off the group when a descendant's own must stay authoritative.

**Why not AND now.** Flipping the operator is not available: `onchanges: [a, b]` on a single task means OR by design ([destiny/tasks.md §8](../destiny/tasks.md#8-requisites---inter-task-dependencies)), and since NIM-246 one register name resolves to *several* indices (a `loop:` fans out N tasks under one `register:`), where "any iteration changed" is the only sensible reading. AND is therefore only definable **between inheritance levels**, which makes the wire shape a conjunction of disjunctions — one bracket per declaration site — that the flat `onchanges_idx` cannot carry. Three costs follow: an only-add grouped field ([ADR-012](0012-keeper-soul-grpc.md) forward-compat), a capability gate so an old Soul does not silently keep applying OR ([ADR-0075](0075-intra-host-async-tasks.md) precedent, NIM-161), and an explicit rule for a bracket whose sources are all filtered out on a host — `remapRequisites` encodes those as the sentinel `-1`, a zero contribution under OR but "nothing changed" under AND, which would silently extinguish the task (the NIM-150 class). That is a change of contract, and R5 is cut to a minimum ahead of integration.

**Alternatives weighed.** *Refusing the overlap fail-closed* — an error when a group construct carries a requisite **and** a descendant declares its own — was considered, and has the property that it would keep a later move to AND non-breaking. It was not taken: the combination has **no user** (a scan of the tree on 2026-07-29 found 0 of 603 YAML files carrying a requisite on any of 31 appliers or 13 blocks), so the gate would only invalidate configurations that were valid in the public beta `v0.1.0-beta.1` without fixing anything real. *Introducing AND* is deferred to **NIM-351** with the design above recorded there; because this amendment fixes OR as normative, that change is a breaking one and must be announced as such.

Normative edits — [`docs/destiny/tasks.md §6.5`](../destiny/tasks.md#65-block---inline-task-group) (the requisite-inheritance bullet corrected — it claimed the whole group is skipped when the condition is not met, which is only true for descendants with no requisite of their own — plus the composition rule), [`docs/scenario/orchestration.md §2.1.2`](../scenario/orchestration.md#212-the-appliers-own-keys---what-reaches-the-group-and-what-decides-before-it) (the union note expanded with a worked example). No code change: `unionNames`, `mergeBlockInheritance`, `mergeApplierInheritance`, `skipOnChanges` and `skipOnFail` already implement this. Guard tests pin the decision so it cannot drift silently — `keeper/internal/render/block_test.go`, `keeper/internal/render/applier_inheritance_test.go` (the union at render, both constructs) and `soul/internal/runtime/applyrunner_test.go` (the OR at the runner, including the widening case: an inherited requisite makes a task run when only the descendant's own source changed).

### Amendment 2026-08-03 (NIM-410, [ADR-0082](0082-service-vars.md)): the scenario context loses the `essence` root — one flat `vars.*`

The scenario template context this ADR fixed listed `essence` beside `input` / `incarnation` /
`soulprint` / `register` / `vars`. **It no longer does.** A service's own defaults move from
`essence/` into `vars/` and are read as `vars.*`, at the bottom of one flat namespace:

```
<service>/vars/*.yaml  →  destiny vars.yml  →  block: vars:  →  task vars:
```

The file rung exists only in the destiny pass — a scenario has no file layer, since
`scenario/<name>/vars.yml` is documented but read by nothing. The upper rungs already composed this
way (`resolveTaskVars` for file-under-task, `mergeBlockInheritance` for a block's); the service
layer joins the bottom of that stack. A layer may now reference the layers BELOW it, because a task
var used to reach the service layer as `${ essence.X }` and would otherwise get `var_unknown_ref`
for the same expression spelled `${ vars.X }`; sideways stays refused. There is no operator rung — `incarnation.spec.essence` is removed with
no successor, which is what made the merge possible: the one property that distinguished the two
namespaces was that essence could be overridden from outside and a `vars` local could not.

Consequences inside this ADR's grammar:

- **`essence` leaves four name lists**, and it is worth naming them precisely because they are not
  all the same kind of list: the reserved bindings for `loop:` `as:`/`index_as:`
  (`loopReservedNames`, `shared/config/scenario_task.go`) and for a `state_changes` `foreach:`
  (`foreachReservedBindings`, `scenario.go`); the reserved names for `compute:`
  (`computeReservedNames`, `scenario.go`); the declared CEL context itself (`contextVars` and
  `flowControlVars`, `shared/cel/engine.go`); and the roots left unqualified inside a
  `soulprint.hosts.where(...)` predicate (`predicateContextRoots`, `shared/cel/hosts.go`). There is
  no reserved-name list for task `vars:` — a task var shadowing a context root was never rejected,
  which is exactly the gap `vars_shadows_service_var` now WARNs about. `vars` is already present in
  every one of these, so the set of rejected names shrinks by one and nothing that used to validate
  starts failing.
- **A static `when:` predicate** may read `input.` / `vars.` / `incarnation.` as before; the
  `essence.` form simply ceases to exist. The `include_when_dynamic_unsupported` and
  `apply_when_dynamic_unsupported` refusals are unchanged in substance.
- **The `apply:` boundary asymmetry is now visible rather than camouflaged.** In a scenario `vars.*`
  means service vars plus locals; in a destiny it means that destiny's own `vars.yml` plus its task
  locals, and nothing crosses except through `apply: input:`. This is the same asymmetry that
  already forced `apply_when_dynamic_unsupported` (§2.1.2) — one word now names both sides of it,
  and [`docs/destiny/vars.md`](../destiny/vars.md) states it head-on.
- **A soul-lint WARNING `vars_shadows_service_var` is to be added (NIM-416)** — a scenario or
  task var taking over a service var's name. Modelled on the existing `vars_collision`, which reports exactly this shape
  for the file↔task pair; without it the merge would let one silently win.

### Amendment 2026-08-17 (NIM-694): `include:` and `extends:` take one subdirectory level; a `_`-prefixed directory under `scenario/` is not a scenario

A service with several scenarios of one family — Redis today has `create` and
`create_from_souls`, `update` and `destroy` follow — had **nowhere to put the shared pieces**.
Both service-level sharing mechanisms this ADR introduced accepted a single flat name:
`include:` matched `^[a-z][a-z0-9_-]*\.yml$` and `extends:` matched `^[a-z][a-z0-9-]*$`, so
everything shared landed side by side in the service root and in `scenario/`, with the family
encoded in the filename (`redis-provision.yml`) rather than in the tree. The amendment 2026-06-29
above created this pressure itself: it made several create scenarios per service normal, and then
gave their common tasks one flat namespace to live in.

**Decision — widen the reference grammar by exactly one directory level, in one place.**

- **One shared segment alphabet, `[a-z_][a-z0-9_-]*`, and at most one directory**
  (`refPathSegment`, `shared/config/scenario_task.go`). `include:` accepts
  `<file>.yml` or `<dir>/<file>.yml`; `extends:` accepts `<name>` or `<dir>/<name>`. `_` joins
  the alphabet — a leading `_` is what marks a shared directory, and a service is free to use it
  in filenames too.
- **`.` stays outside the alphabet, which is the whole traversal defence at the grammar layer.**
  `..`, absolute paths and hidden names are not "rejected"; they are **unrepresentable**. The
  securejoin clamps in `readCovenantFile` and `ServiceLoader.ReadFile` remain as the second line
  and are guard-tested against a real file planted outside the snapshot — a defence that depends on
  one regexp is a defence one refactor away from gone.
- **Why one level and not N.** The cap is the point, not a limitation to lift later: `include:`
  resolves through **two tiers** (local, then service-level, §6), and every extra directory level
  multiplies the places a reader must check to answer "which file is this". One level splits a
  family from a flat list; two would let a service build a private tree with two-tier shadowing
  inside it.
- **A directory under `scenario/` (or `upgrade/`) whose name starts with `_` or `.` is NOT a
  scenario** (`config.IsSharedDirName`). It is skipped by discovery **explicitly and silently**,
  **even when it contains `main.yml`** — the prefix is the signal. The previous behaviour was an
  accident of implementation: a directory without `main.yml` was skipped by *failing to load*, so
  the convention would have been a side effect of an error path, and every listing logged a
  `scenario skipped — no main.yml` warning for a directory that was never a scenario. Both scenario
  walkers implement it — `artifact.listFromDir` (the API/lint listing) and
  `scenario.scenarioDirs` (the deprecation walk, which deliberately keeps *unparseable* scenarios
  and would otherwise report a shared directory as a permanent phantom coverage gap).
- **soul-lint resolves the service level offline instead of deferring it.** Inside a service tree
  (`<root>/service.yml` + `<root>/scenario/<name>/main.yml`) the linter now resolves both tiers
  from disk and reports the expander's own diagnostics at their own level — an include that
  resolves at neither tier is an **ERROR** (`include_resolve_failed`), not the old
  `stage_include_unresolved` hint that let a broken reference exit OK. Outside a service tree the
  second tier genuinely does not exist offline, and the hint is kept. Deferring to the keeper was
  tolerable while a service had a handful of flat includes; with a family directory per scenario
  group it would have left the majority of references unchecked at authoring time.
  **The kept hint covers a target that was not FOUND, and nothing else** (amendment 2026-09-02 /
  NIM-716). It used to cover every error out of an expansion, tested by level and severity alone,
  so a body that resolved **locally** and was read — the same bytes, checked by the same code as
  inside a service tree — came back as `include does not resolve offline (<its real code>)` with
  exit 0: a sentence whose every clause is false, over a real defect. The membership question is
  asked of the producer (`config.IsIncludeResolveDiag`) rather than answered from a second copy of
  the list. A cycle or an overlong chain is not downgraded either: outside a service tree strictly
  *fewer* includes resolve, so such a finding is a subset of the real one, never an artefact of the
  missing tier.

**Backward compatibility is total.** The grammar is a strict superset and the discovery skip keys
on a prefix no existing directory carries, so a service in the flat layout — `examples/service/redis`
and the downstream redis service both are — loads bit-for-bit as before. There is no migration: the new
layout is available, not required.

Normative edits — [`docs/scenario/orchestration.md`](../scenario/orchestration.md) §1 (the layout
tree + the `_`-prefix rule), §6 (one subdirectory in `include:`), §6.1 (one subdirectory in
`extends:`), §8 (the open question "service-level location of include targets" is closed),
[`docs/destiny/tasks.md §4`](../destiny/tasks.md) (the same target grammar reaches destiny
`include:` through the shared validator; resolution stays inside `tasks/`).

## Amendment 2026-08-19 (NIM-698, [ADR-0083](0083-declared-secret-state-fields.md)): a secret is declared in `state_schema`, and `no_log` is removed

A `state_schema` field may carry **`type: secret`** — scalar, or on a property inside `items` next to the `key:` naming which sibling property is the collection's identity. The value lives in Vault at a path Keeper **derives** from `(service, incarnation, state field, key)`; the author writes no path anywhere. Distinct from the pre-existing `secret: true` marker, which says the value lives in state and is masked on output.

Two grammar consequences for a scenario:

- **`no_log:` is removed from the task grammar**, not deprecated. It was all-or-nothing and set by the task author rather than by the module that knows its own output shape; per-field `secret: true` on module output replaces it ([ADR-0083](0083-declared-secret-state-fields.md) §8).
- **An author-written path into the service's own namespace `<mount>/<service>/` is an error** in all four spellings — `${ vault(...) }`, a `vault:` ref in `params:`, and the `path:` of `core.vault.kv-read` / `core.vault.kv-present`. All four keep working **outside** that prefix, where the cross-namespace read (a shared TLS CA, another service's credential) has no replacement yet.

## Amendment 2026-08-25 (NIM-699, [ADR-0084](0084-explicit-state-capture.md)): the `state_changes:` block is removed — a state write is a task

The orchestration delta of §1 loses `state_changes`. A scenario writes `incarnation.state` with a
keeper-side task, `module: core.state.<verb>` + `on: keeper`, standing at its own position in
`tasks:` — one address per verb, `set` / `present` / `add` / `append` / `modify` / `remove` /
`unset`. The verbs and their parameters are exactly the ones [ADR-057](0057-state-changes-crud-verbs.md)
fixed (`match:` predicate, `key:`, `on_conflict:`, `expect:`, `patch:`); what is retired is the
**block**, not the grammar. `state_changes:` at the top level of a scenario is now a foreign key
(`unknown_key`), and in a covenant it is `covenant_unexpected_key` — the covenant keeps three
sections (`input:` / `compute:` / `validate:`) and a shared write travels as a step through
service-level `include:` ([ADR-0084](0084-explicit-state-capture.md) F-B).

Three consequences worth stating separately:

- **The write lands at the step, not at the end of the run.** The former block dropped every
  operation after the cross-host barrier, in one transaction; a capture applies where the author
  put it and is visible to everything after it. The cross-host barrier itself is unchanged — a
  Passage still waits for every host before the next one begins, and a finally-failed host still
  ends the run in `error_locked`. What moved is the commit, not the barrier: a run that dies after
  a capture keeps what that capture recorded, which is the point for a field like
  `provisioned_vm_ids` where losing the record leaks the resource.
- **Ordering is now the author's, so it is linted.** `soul-lint` reports `state_store_after_use`
  (a field read before the capture that writes it) and `state_stale_same_passage_read` as ERRORs,
  and `state_wide_match` (a `modify`/`remove` with no `match:`) as a WARN — see
  [`docs/scenario/orchestration.md §7.1`](../scenario/orchestration.md#71-the-capture-verbs).
- **A capture sees no per-host data at all.** As an `on: keeper` task it renders through the
  keeper context (`keeperVars`), so `register.<name>` resolves against **keeper-side** tasks only
  and no soulprint root is bound — neither `soulprint.self` (there is no host) nor the scenario-only
  `soulprint.hosts` (never available to a state write; the former block rendered per-host with
  `AllowHosts=false`). The block folded the per-host register map last-wins by SID; a capture
  cannot. What a capture can read is what a **keeper** task produced — which is what the corpus
  actually does (`register.provision` from `core.cloud.created`). A value that exists only per-host
  has no route into `incarnation.state` today; nothing in the corpus needs one, and closing that is
  a separate decision, not a silent widening here.

`foreach` is dropped with the block and does **not** return as a task-level key: a step already has
`loop:`. The pilot does not yet render `loop:` on an `on: keeper` task, so until that lifts a
capture over a runtime-sized collection has to be written out one task per element.

Normative edits — [`docs/scenario/orchestration.md §7`](../scenario/orchestration.md#7-state-capture-and-the-cross-host-barrier)
(the barrier is restated without the state commit) and
[§7.1](../scenario/orchestration.md#71-the-capture-verbs) (the capture verbs, the normative spec),
plus the covenant section of the same file.

## Amendment 2026-09-01 (NIM-748, [ADR-0087](0087-task-side-derived-from-module-address.md)): `on:` returns to one meaning — the scalar `keeper` leaves the key on core addresses

**Not implemented.** Recorded here because the decision is accepted; the code is NIM-749 / NIM-750.

The orchestration delta above lists `on:` in two roles at once — a coven filter for a Soul task, and
the magic scalar `keeper` meaning "do not send this to hosts at all". [ADR-0087](0087-task-side-derived-from-module-address.md)
removes the second: a task's side is **derived from its module address**, the two core registries
being disjoint, and `on:` becomes a coven list and nothing else.

What changes for an author: on a **core** address `on: keeper` becomes an error
(`on_keeper_redundant`), a coven list on a keeper-side core address becomes an error that is never
silently dropped (`on_covens_on_keeper_module`), and `on: keeper` on a Soul-side core address gets
its own separate code (`on_keeper_on_soul_module`). On a **plugin** address `on: keeper` stays legal —
permanently, since a plugin's side is declared in its schema document, which the Keeper reads at
dispatch (NIM-758) and a scenario cannot read at all. There is **no transition window** — the break
lands in one release.

Everything else in this ADR is untouched: `where:`, `serial:`, `run_once:`, `apply:` and the
`core.state.<verb>` capture step all keep their semantics. Until NIM-749 / NIM-750 land, the text
above describes the engine that ships.

## Amendment 2026-09-01 (NIM-741, [One schema dialect](0086-one-schema-dialect.md)): `state_schema` is written in the input DSL, so the 2026-08-19 declaration changes spelling

The 2026-08-19 amendment above put `type: secret` into `state_schema` while `state_schema` was
still JSON Schema. It no longer is: `state_schema` becomes a map `<field name>` → schema in the
**same dialect as `input:`** — no `type: object` / `properties:` wrapper at the root, no root
`required: [names]` list (requiredness is `required: true` on the field), and a snake_case
vocabulary. The secret declaration itself is untouched — the two supported shapes, the `key:`
sibling, the derived path and the closed node grammar all stand — but every corpus site that
spells it moves:

```yaml
# service.yml — state_schema in the input dialect (design; NIM-742…744)
state_schema:
  redis_type:
    type: string
    required: true
    enum: [sentinel, cluster]
  redis_users:
    type: array
    items:
      type: object                      # a NESTED object still declares type/properties
      additional_properties: false      # was additionalProperties
      properties:
        name:  { type: string, required: true }   # was a sibling `required: [name, perms, state]`
        perms: { type: string, required: true }
        state: { type: string, required: true, enum: [on, off] }
        password:
          type: secret
          key: name
          label: "Redis user password"
```

Two boundaries worth keeping straight, because both are easy to over-read. The wrapper is refused
**at the root only** — the element schema under `items:` above is an ordinary nested object and
still carries `type: object` with its fields under `properties:`. The list form `required: [names]`,
by contrast, leaves the **whole** dialect: nested objects and `types.yml` included, which is what
makes `required: true` on a `type: secret` property newly expressible and therefore newly worth
refusing ([ADR-0083](0083-declared-secret-state-fields.md), `secret_field_required`).

The list form's removal is the **wider** of the two migrations, and it does not stop at state
schemas: 28 flow-form `required: [...]` sites are authored across both dialects — `service.yml`
state schemas, `types.yml` catalogs, and destiny/scenario `input:` blocks alike. The block form is
authored nowhere in the DSL.

**Breaking, no transition window.** The old envelope is refused **by name**
(`state_schema_legacy_json_schema_form`) rather than left to parse: read as the new dialect it is
two state fields called `type` and `properties`, which moves every real field a level down and
loses every declared secret with no error raised. **Design only, not implemented** — engine
NIM-742, `soul-lint list-secret-paths` NIM-743, `examples/` and the downstream redis service NIM-744.

## Amendment 2026-09-05 (NIM-833): `validate:` is the static check over the request — its context is `input` + `incarnation`, and the block is published

The 2026-06-23 amendment introduced `validate:` with an **input-only** context, on the reasoning
that a declarative invariant is a pure function of what the operator typed. That was too narrow by
one root, and the gap has a name: a service could not declare a constraint on the **incarnation
identifier**, because the identifier is not an `input:` field. The constraint therefore moved into
an `assert:` task, which runs in the RUN — after the row is written. An operator got a half-created
entity and an error about the cloud (NIM-832 is that report, from a downstream redis service).

**The definition this settles on.** `validate:` is the **static check over the request**:
everything decidable from what arrived on the request is decided here, and **before a single task
runs**. Two roots follow from that and no more:

- `input` — what the operator sent, after the schema phase;
- `incarnation` — the entity the request is about, to the extent this point on the path knows it.

`vars` are deliberately **not** added: they are the service's parameters, not the request, so a rule
that needs them is not checking the request and does not live here. `compute` is not added either —
it resolves inside the run, which is later than this point by construction.

**The create/day-2 difference is expressed, not smoothed over.** On day-2 the row is loaded and a
rule reads it. On create the incarnation does not exist yet: only the identity the request itself
carries is knowable, and for a scenario with `id_template:` not even that, since the id is composed
from the very input the gate is still resolving. Each path declares what it knows
(`config.ValidateContext`), and a rule reaching outside that set is **refused at compile**:

| Path | `incarnation.*` carries |
|---|---|
| day-2 run | `id` (+ the `name` window alias), `service`, `service_version`, `state` — a subset of the run's own namespace |
| create, operator-supplied id | `id` / `name` |
| create, `id_template:` scenario | nothing |
| isolated destiny pass, L0 trial case | nothing |

Refusing rather than substituting an empty map is the whole point, and the reason is the one NIM-619
recorded for `compute` ([ADR-0009 §2.4 scoping](0009-scenario-dsl.md)): an empty namespace is **silent** in exactly
the forms a defensive rule is written in. `has(incarnation.state)` answers `false` and
`size(incarnation)` answers `0`, so `!has(incarnation.state) || <check>` reports success having
checked nothing — worse than no rule, because it is believed. The refusal is classified as a
pre-flight malfunction (5xx, `config.ErrIncarnationNotInScope`) and **not** a 422: the operator's
input is not what is wrong, so a 422 would send them to fix a value that is correct.

**The block becomes a published contract.** `that` and `message` travel in the scenario listing
(`GET /v1/services/{id}/scenarios` → `scenarios[].validate[]`) beside `input_schema`, covenant rules
first, so an operator form can show the requirements before anything is submitted rather than
surfacing them as a 422 afterwards. Only the **text** travels. Evaluating CEL in the client was
considered and rejected: it is a second implementation of one rule, and two of those diverge — the
question is only when. A client that wants a verdict rather than the requirements asks the server,
which is the same evaluator the run uses.

**Three consequences that are easy to get wrong, and are settled here.** What a path ANSWERS FOR is
fixed and does not depend on the row: `incarnation.state` is in scope on every day-2 request, and a
NULL state column gives the ordinary `no such key` the run gives — deriving the answerable set from
the row instead reports the same scenario broken for one incarnation and fine for its sibling. The
check is a PRE-PASS over every rule, not a step inside the eval loop, or it would sit behind the
first-false short-circuit and a scenario's brokenness would depend on what the operator typed. And a
`create: true` scenario is judged OFFLINE against the create stance (`validate_rule_out_of_scope`,
ERROR, covenant-inherited rules included, post-merge) through that same runtime guard — otherwise a
rule that can never run ships green and 5xx's once per request.

**What this does NOT close.** A create scenario that composes its id still cannot constrain it
through `incarnation.*` — there the id *is* its input components, and the rule belongs on
`input.*`. A service-level declaration of the identifier's grammar, applied by the keeper on every
create however the id arrives, is NIM-832 and is not decided here. The L0 trial harness has no
incarnation either, so a create scenario's identifier rule has no offline test surface beyond
`expect_render_error`; giving a case one is its own ticket.
