# ADR-0075. Intra-host task concurrency — `async:` tasks and named barriers

- **Context.** Two tasks on one host that do not depend on each other still run one after the other. The apply cycle is a strict loop over `ApplyRequest.tasks[]` ([`soul/internal/runtime/applyrunner.go:398`](../../soul/internal/runtime/applyrunner.go)), and everything above it — requisite gating by index, fail-stop, register accumulation — is written against that order. Rendering twenty templates costs the sum of twenty renders, not the longest one.

  The DSL appears to have an answer already. `parallel:` is a declared task key, it parses (`Task.Parallel`, [`shared/config/scenario_task.go:32`](../../shared/config/scenario_task.go)) and [destiny/tasks.md §6](../destiny/tasks.md) specifies it in full. **Nothing executes it.** Render rejects any task carrying it with `ErrUnsupportedDSL` — on the scenario side ([`keeper/internal/render/pipeline.go:1919`](../../keeper/internal/render/pipeline.go)) and inside a destiny pass ([`keeper/internal/render/destiny.go:473`](../../keeper/internal/render/destiny.go)) — and the config validator rejects it on a `block:` ahead of render (`parallel_on_block_invalid`, [`shared/config/scenario_task.go:894`](../../shared/config/scenario_task.go)). `RenderedTask` carries no field for it, so it could not reach a Soul even with the guards lifted. The one gap in the wall is deliberate: a statically-false `when:` gates a task off **before** the guard runs ([tasks.md §7](../destiny/tasks.md)), so a `parallel:` task on an inactive branch renders silently and fails only when its branch is selected.

  So the key is a specification with no implementation — which makes this the last cheap moment to decide what it actually means, and there were two incompatible candidates. §6 as written is **fire-and-forget**: a flag on an ordinary task, explicitly *not* a grouping mechanism, with the flow moving on immediately and waiting only at a barrier. The competing shape was a **join block**: a container holding N tasks, run concurrently, followed by a barrier, after which dependent work proceeds. Neither is a reading of the other — fire-and-forget cannot express "wait for exactly this set", a join block cannot express "start it and never wait" — so building one while the specification described the other was not an option.

  Two properties of the implemented architecture bound whichever model is chosen, and both contradict §6 as it stands today.

  **A "local barrier on register access" is only realizable for half the reference sites.** Passage stratification ([ADR-056](0056-staged-render-passage.md), [`shared/config/passage.go`](../../shared/config/passage.go)) already partitions register references into two classes. Passage-defining sources — `where` · `vars` · `params` · `apply.input` · `output` · `loop.items` · `loop.when` — resolve **Keeper-side before dispatch**, so a task reading one is moved into the next Passage and the stage loop (render → dispatch → barrier → repeat) will not start it until the previous Passage is closed on every host. That is a plan-wide barrier, not the per-register wait §6 promises. Only the other class — the requisites `onchanges`/`onfail`/`require` and the flow-control predicates `when`/`changed_when`/`failed_when`/`until`, all evaluated Soul-side inside one `ApplyRequest` — can wait for one named task while others keep running. §6's own worked example sits in the first class (`output: { ping: "${ register.ping.stdout }" }`), so the example illustrating a local barrier is in fact a full join.

  **Background work cannot outlive a Passage.** §6 states that parallel tasks flow across `include:`/`block:` boundaries and are awaited only at the end of the destiny. The unit of dispatch is one `ApplyRequest` per host **per Passage**, closed by its `RunResult`, with `apply_runs` keyed `(apply_id, sid, passage)`. A thread cannot survive the message that carried it.

  What the architecture does *not* obstruct bounds the cost. Concurrent sends on the Keeper↔Soul stream are already serialized ([`soul/internal/grpc/client.go:488`](../../soul/internal/grpc/client.go)), so emitting `TaskEvent`s from several goroutines is wire-safe. Keeper's register accumulator is an upsert keyed `(apply_id, sid, plan_index)` ([`keeper/internal/applyrun/taskregister.go:48`](../../keeper/internal/applyrun/taskregister.go)), so out-of-order arrival changes nothing. The cross-host state-commit barrier ([orchestration.md §7](../scenario/orchestration.md)) is untouched — `state_changes` commit after all hosts finish, above this decision entirely.

  There is no installed base to protect: `parallel:` has no consumer anywhere in `examples/` and no run can carry it today, so both the semantics and the spelling are still free.

- **Decision.**

  - **(a) The construct is `async: true` — a flag on an ordinary task, fire-and-forget, not a grouping mechanism.** The task starts, the flow moves on without waiting. `async: true` on two adjacent tasks does **not** mean "execute together": each runs independently, and neighbours may be anything — other async tasks, ordinary tasks, `include:`, `block:`.

    The **name states the semantics**. What is being introduced is asynchrony — start now, collect the result later at a point of your choosing — and not a thread-group primitive. A concurrently-executed **group with a join** remains a plausible future construct with genuinely different behaviour (a bounded set, a group-scoped outcome, a group-scoped error boundary), and `parallel:` is reserved for it. Spelling today's asynchrony `parallel:` would spend the better name on the weaker meaning and force a rename later, with consumers in the field; renaming now costs nothing, because there are none. **`parallel:` therefore becomes an unrecognized key** — rejected fail-closed by the strict manifest walker like any other (`unknown_key`) — and is not re-introduced until the group construct is specified.

  - **(b) Three barriers, and the explicit one is primary.**

    1. **Explicit — `require: [<register>, …]` or `require: all`** ([tasks.md §8](../destiny/tasks.md)). The task does not start until the named async tasks have finished; `all` waits for every async task started earlier in this run. This is the author-visible, statically-readable dependency: **the plan says what waits for what**, so a reader, a linter and a diff can all see it. It is the form to reach for.
    2. **Implicit — a reference to an async task's `register.<name>`.** Works, with the class rule in (d): a reference from `when:`/`onchanges:`/`onfail:` is a **local** wait (only that task; the rest keep running), a reference from `params:`/`output:`/`vars:`/`where:` is a Passage boundary and therefore a **full** barrier.
    3. **Final — the end of the run.** The run does not complete until every async task is finalized. This is required behaviour, not an option: if any async task ends failed, the run is failed.

    Ordering and condition stay separate keys and combine by AND, unchanged: `require:` answers *when*, `onchanges:`/`onfail:`/`when:` answer *whether*.

  - **(c) A failure is observed where it is awaited; siblings are never cancelled.** An async task that fails writes `failed = true` into its register and **does not break the main flow at the moment it fails**. The flow learns about it exactly where it reaches for it — at an explicit `require:`, at an implicit register reference, or at the final barrier — and at that point the ordinary fail-stop engages: the run is irreversibly `FAILED`, subsequent ordinary tasks are skipped, and only the `onfail:` rescue tail runs ([tasks.md §8](../destiny/tasks.md)). Async tasks already in flight are **not** cancelled: they run to completion and are collected by the final barrier.

    Not cancelling is the deterministic choice. A cancel-on-first-failure policy makes the set of tasks that actually ran depend on scheduling timing, and leaves a host in a state no one declared — half of an interrupted operation. The cost is accepted: a doomed run may keep working for as long as its slowest in-flight task. A future opt-in cancel field is possible and is not built here.

  - **(d) The two architectural boundaries are stated in the specification, not discovered at run time.** Both correct §6 as it stands:

    | Where the reference sits | Resolution | Barrier |
    |---|---|---|
    | `when` · `changed_when` · `failed_when` · `until` · `onchanges` · `onfail` · `require` | Soul-side, inside one `ApplyRequest` | **local** — waits for that task only |
    | `where` · `vars` · `params` · `apply.input` · `output` · `loop.items` · `loop.when` | Keeper-side, before dispatch ([ADR-056](0056-staged-render-passage.md)) | **full** — the next Passage waits for the whole previous one, on every host |

    And: **an async task never outlives its Passage.** The final barrier is the end of the `ApplyRequest`, which on a stratified plan is the end of the current Passage, not the end of the destiny. On an unstratified plan (`Count == 1`, the common case) the two coincide, which is why the distinction is invisible until a probe splits the run. Authors are told this rather than left to infer it from a latency anomaly.

  - **(e) No concurrency limit in the DSL; a host-side ceiling in `soul.yml`, unlimited unless set.** Real fan-out is small (a handful of renders, a handful of fetches), so a mandatory limit would be ceremony around a non-problem, and a per-task DSL field would invite tuning a number the author cannot evaluate — the author knows the plan, not the machine it lands on. The ceiling therefore lives where the knowledge is, mirroring the console's host-side `max_sessions` ([ADR-0074(d)](0074-interactive-console-pty.md)):

    ```yaml
    # soul.yml
    async:
      max_concurrent: 0     # 0 / unset = unlimited; >0 = at most N async tasks in flight
    ```

    Above the ceiling an async task waits for a slot; it is never dropped and never fails for want of one. Nothing about the plan changes when the ceiling does — a run is correct at any setting, only slower.

  - **(f) Safety against shared OS resources is the author's, stated concretely.** Modules are not required to be safe under concurrency and the framework does not serialize them. What the framework owes the author is a **specific** warning rather than a generic caution, because the most obvious use — installing packages concurrently — is exactly the case that does not work:

    `core.pkg.installed` takes a single `name` ([`soul/internal/coremod/pkg/pkg.go:98`](../../soul/internal/coremod/pkg/pkg.go)), so N packages are N tasks, and on Debian/Ubuntu apt is invoked with `-o DPkg::Lock::Timeout=300` ([`pkg.go:35`](../../soul/internal/coremod/pkg/pkg.go)) — concurrent installs do not fail, they **queue on the dpkg lock**. The result is the original serial duration plus lock-wait overhead, and outright failures once the queue exceeds the timeout. `dnf`/`yum`/`apk` are invoked without a wait flag, so there contention surfaces as an error instead. Independent-path work — `core.file.rendered`, `core.url.fetched`, read-only probes via `core.exec.run` — is where the win actually is.

    A declared per-module concurrency class was considered and deferred: the closed `side_effects` resource enum exists only in the **plugin** manifest ([`shared/plugin/manifest.go:47`](../../shared/plugin/manifest.go)) and the 18 statically-built core modules have no manifest at all, so making the validator resource-aware is its own ADR and its own sweep. Until then this is documentation plus author discipline, and it is recorded as a known sharp edge rather than implied.

  - **(g) The wire contract is three only-add fields on `RenderedTask`** ([ADR-012(c)](0012-keeper-soul-grpc.md), `proto/keeper/v1/apply.proto`, next free numbers **18-20**): `async` (bool), `require_idx` (repeated int32) and `require_all` (bool). `require:` is resolved **Keeper-side from register names into task indices**, the same Variant A already used by `onchanges_idx`/`onfail_idx`/`aggregate_of` — Soul deals only in indices, and the same global→local remap (`remapRequisites`, sentinel `-1` for a source filtered out by `where:` or living in another Passage) applies unchanged. This closes the existing gap where `require:` is parsed and reference-checked ([`shared/config/task_refs.go:314`](../../shared/config/task_refs.go)) but reaches no runtime.

  - **(h) Determinism is preserved where it is observable, and given up only in the apply log.** An async task's own gating (`when:`/`onchanges:`/`onfail:`) is evaluated **in the main flow at its position in the plan**, before it is launched — so *whether* a task runs never depends on timing, only *when* it finishes does. Register correlation on Keeper is order-insensitive by construction (the upsert in the Context). What genuinely changes is that `TaskEvent`s interleave, so the operator's apply log is no longer in plan order; events carry `plan_index` and the UI orders by it rather than by arrival. Cancellation (`CancelApply`) must reach in-flight async goroutines, not only the main loop.

- **What it standardizes, what it defers.** **Standardizes:** the key and its fire-and-forget semantics (a); the three barriers and the primacy of the explicit one (b); failure observation and the no-cancel rule (c); the reference-class table and the Passage lifetime (d); where the ceiling lives (e); the resource-safety position (f); the wire fields and the Keeper-side name→index resolution (g); gating determinism (h). **Defers:** a concurrently-executed **group with a join** under the reserved `parallel:` spelling; `async:` on a construct that expands into a group — `block:`/`include:` (`async_on_block_invalid`) and `apply:` (`async_on_apply_invalid`, NIM-152); design intent in §6 preserved — the whole group runs in one flow — but gated fail-closed until a slice implements it; an opt-in cancel-on-first-failure field (c); a final-barrier timeout; a declared per-module concurrency class over an extended `side_effects` (f); addressing a single iteration of `loop:` + `async:`.

- **Consequences.**
  - `parallel:` disappears as a valid key; `Task.Parallel` becomes `Task.Async` (yaml `async`), and `parallel_on_block_invalid` becomes `async_on_block_invalid`. No migration for anyone: the key has no consumer in `examples/` and no run could carry it.
  - The two render guards stop rejecting the key and start honouring it; the statically-false-`when:` precedence ([tasks.md §7](../destiny/tasks.md)) is unchanged, so an inactive branch still renders regardless.
  - `require:` becomes load-bearing instead of decorative, and its existing per-file reference validation ([task_refs.go](../../shared/config/task_refs.go)) becomes a correctness gate rather than a nicety. It stays **non-passage-defining** ([`shared/config/passage.go:619`](../../shared/config/passage.go)): it expresses order within a Passage, not a Keeper-side data dependency.
  - The Soul runner gains real concurrency: `registerByIdx`/`registerByName` ([`applyrunner.go:382`](../../soul/internal/runtime/applyrunner.go)) need synchronization, and fail-stop grows a second trigger (a barrier observing a failed async task) beside the existing in-line one.
  - Operators see an interleaved apply log on any run using `async:`. This is new and worth saying in release notes: nothing is missing, the order is no longer the plan's.

- **Trade-offs.** The best word is spent on the construct not yet built — deliberate, because a group with a join is the one that will need it. A doomed run can keep working after it is already lost (c), traded for a deterministic set of executed tasks. The most intuitive use of concurrency is the one that does not pay off (f), and the specification says so instead of letting each author rediscover it. The local-versus-full barrier distinction (d) is a genuine wart: the author must know which key a reference sits in to predict the wait. It is inherent to rendering Keeper-side ([ADR-012(d)](0012-keeper-soul-grpc.md)) and is documented rather than papered over.

- **Rejected.** **A join block as the R5 construct** — expressible, cheaper in places (it reuses `renderBlockTask` fan-out, the `aggregate_of` synthetic terminal and block atomicity in Passage stratification), but it cannot express background work overlapping later unrelated tasks, which is the requested behaviour; it stays reserved under `parallel:` rather than dropped. **Keeping the spelling `parallel:` for asynchrony** — sets up a rename with consumers in the field. **Grouping adjacent `async:` neighbours implicitly** — makes an invisible boundary out of YAML adjacency, and §6 already forbade it. **Cancel-on-first-failure by default** (c). **A per-task DSL concurrency field** (e). **Serializing modules by resource inside the runner** — the resource declaration does not exist for core modules (f).

- **Deferred.** The `parallel:` group-with-join construct; `async:` on `block:`/`include:`/`apply:`; opt-in sibling cancellation; a final-barrier timeout; a per-module concurrency class; the exact scope of `require: all` with respect to already-finished tasks (today: those still in flight) — carried over from [tasks.md §12](../destiny/tasks.md).

- **Impl.** **NIM-149 (this ADR + the DSL specification)** · NIM-150 (proto fields + render: lift both guards, resolve `require:` names into indices; carried the `parallel:`→`async:` rename and `async_on_block_invalid` with it) · NIM-151 (Soul runner concurrency, barriers, fail-stop second trigger, cancellation) · NIM-152 (validator + `soul-lint`: `require_forward_reference` — which subsumes the requisite-cycle check, since a cycle needs a forward edge — plus `async_on_apply_invalid` and `require:` inheritance from `block:`).
