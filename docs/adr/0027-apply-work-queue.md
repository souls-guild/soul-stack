# ADR-027. Apply execution model — work-queue + claim (Acolyte-pool, Ward-claim)

> **Phase 0 / 1 / 2 + GATE-1 (deliver-once recovery) implemented; Phase 3 (distributed serial) — deferred.** Acolyte-pool, Ward-claim (`FOR UPDATE SKIP LOCKED`), Summons (`apply:summons` + poll-fallback), re-render on claim (`keeper/internal/scenario/claim.go`, `keeper/internal/applyrun`), Reaper recovery scan (`reclaim_apply_runs`, `keeper/internal/reaper`), two-sided attempt-fencing (proto `ApplyRequest.attempt` + `RunResult.attempt` field 4 + Soul-guard + epoch-check on receive), single-winner state-commit — in the code. **Lifecycle after GATE-1: `planned → claimed → dispatched → terminal`** (the `dispatched` phase is written before SendApply; `running` is vestigial, only the old synchronous path; see the "GATE-1: deliver-once recovery" amend at the end of the ADR). **Recovery scan `reclaim_apply_runs` is DISABLED by default** (`enabled:false`): enabling it is an operational step behind a gate (after GATE-1 — fencing-Soul rollout + S2–S5 done; see Consequences + amend (e)). The distributed serial barrier (Phase 3) is not covered by code — a serial run is claimed whole by a single Acolyte.

- **Context.** Currently a run is executed by a **run-goroutine in the memory of a single Keeper instance** — the one that accepted the dispatch. The barrier / serial / cancel-polling state lives in this goroutine; Postgres holds only the correlation (`apply_runs`, `apply_task_register`, [storage.md](../keeper/storage.md)). This creates the **"hanging applying" hole**: if the owner instance dies mid-run, `incarnation.status` stays `applying` forever, `apply_runs` rows hang in `running`, and **nobody** picks up the run — other instances don't know about this goroutine. Execution ownership is not persistent and is not handed off. We need a model where ownership of each per-host task is **materialized in Postgres** and can be taken over by a live instance after the owner's death.
- **Decision.** Apply execution is moved to a **work-queue + claim**: tasks (per-host `apply_runs` rows) sit in Postgres, and a pool of workers on each instance atomically claims them.
  - **(a) Entities.** **Acolyte** — the execution worker pool on each Keeper instance (`keeper.acolytes:N`), replacing the single run-goroutine; an Acolyte claims a task, resolves and renders it just-in-time, drives apply, and holds the barrier for its slice. **Ward** — the claim (sub-guardianship) of a task: the set of columns `claim_by_kid` / `claim_at` / `claim_expires_at` / `attempt` + the statuses `planned` / `claimed` on `apply_runs`; "take a Ward" = capture the task. **Summons** — a pub/sub signal "planned tasks have appeared" (Redis, best-effort) + a periodic poll fallback (the Acolyte still periodically scans `planned`, so losing the signal does not lose the task). The names are recorded in [naming-rules.md](../naming-rules.md), propose-and-wait passed.
  - **(b) Run record.** The scenario-runner, on dispatch, writes `apply_runs` rows in the `planned` status (instead of directly `running`) and sends a `Summons`. There is no in-memory ownership at this step — the task is already persistent and available to any Acolyte on any instance.
  - **(c) Just-in-time render.** The Acolyte renders the task **at the moment of claim**, not at dispatch. Postgres stores the **recipe** of the run (scenario-ref + `input` with vault-refs **as-is**), not the unwrapped secrets — see invariant A.
  - **(d) Claim — atomic capture.** The Acolyte takes a Ward via `UPDATE apply_runs SET status='claimed', claim_by_kid=$me, claim_at=NOW(), claim_expires_at=NOW()+lease, attempt=attempt+1 WHERE status='planned' … ` with **`SELECT … FOR UPDATE SKIP LOCKED`** semantics (capture without blocking competitors; busy rows are skipped). `RETURNING` hands the captured tasks to this Acolyte. Competing Acolytes on different instances do not fight over the same row.
  - **(e) claimed → running.** Having received a Ward, the Acolyte resolves secrets + renders (invariant A), sends an `ApplyRequest` to the Soul, and moves the task `claimed → running`. The RunResult handler, as before, moves `running` to a terminal (`success` / `failed` / `cancelled`).
  - **(f) Invariant A — no plaintext secrets.** Postgres holds the **recipe** (scenario-ref + `input` with vault-refs as-is), **not** the unwrapped values. Resolution (`vault(...)`, CEL) and render are done **just-in-time at claim**; unwrapped secrets live only in the Acolyte's RAM and on the wire (mTLS) to the Soul. On a **Ward takeover** (recovery) the new Acolyte **re-renders** the task anew from the recipe — the old unwrapped material is nowhere persisted and does not migrate. This **refines [ADR-012(d)](0012-keeper-soul-grpc.md#adr-012-keepersoul-grpc-contract-one-eventstream-with-oneof-keeper-side-render-forward-compat-only-add)**: render stays Keeper-side but is bound to the moment of claim, not dispatch, and is repeated on recovery.
  - **(g) Invariant B — no double execution (fencing).** Taking over a stale Ward must not produce **two** live applies on one host. Protection is two-layered: (1) **SID-lease** — a single Keeper instance owns the stream of a given Soul ([ADR-006](0006-cache-redis.md#adr-006-cache-and-coordination--redis)), and apply to a host goes only through the stream owner; (2) **Soul-side guard** — the Soul rejects a duplicate / stale `ApplyRequest` by `apply_id` + `attempt`-epoch. **We do not rely on module idempotency.** The Soul-guard requires an **only-add proto field `attempt`** in `ApplyRequest` ([ADR-012(c)](0012-keeper-soul-grpc.md#adr-012-keepersoul-grpc-contract-one-eventstream-with-oneof-keeper-side-render-forward-compat-only-add) forward-compat only-add, Phase 2); without it fencing degrades to protection by `apply_id` (which cuts off a duplicate of the same attempt but does not distinguish a stale-attempt).
  - **(h) Invariant C — serial.** A non-serial run → **per-host claim** (each host is a separate Ward, parallelized across the whole pool). A serial run → the task is claimed **whole by a single Acolyte** (the barrier / serial window is held by that one, like the run-goroutine today). **Distributed serial** (several Acolytes cooperatively holding one serial barrier) — a **separate ADR**, deferred (Phase 3). The barrier / serial semantics of [ADR-009](0009-scenario-dsl.md#adr-009-scenario--the-full-destiny-task-dsl-the-boundary-with-destiny-is-a-recommendation) are preserved.
  - **(i) Recovery scan by the Reaper leader.** ⚠️ *Pre-GATE-1 wording; the predicate is narrowed — see amend (c)/(b).* The Reaper leader ([ADR-006](0006-cache-redis.md#adr-006-cache-and-coordination--redis), [reaper.md](../keeper/reaper.md)) periodically scans `apply_runs` for **stale Wards** (after GATE-1: `status='claimed'`, was `IN ('claimed','running')`) `AND claim_expires_at < NOW()` → returns them to `planned` (resetting `claim_by_kid` / `claim_at` / `claim_expires_at`). This **closes the "hanging applying" hole** at the **pre-delivery** phase (an undelivered task): the dead owner's row goes back into the queue and is picked up by a live Acolyte; `attempt++` on the next claim cuts off the stale `ApplyRequest` on the Soul (invariant B). **`dispatched` (delivered) is NOT reclaimed** (amend (c)). The Reaper rule name is `reclaim_apply_runs` (propose-and-wait passed).
  - **(j) Single-winner state-commit.** Moving an `incarnation` from `applying` to a terminal at the end of a run is an atomic single-winner: `UPDATE incarnation SET status=… WHERE status='applying' RETURNING …`. Only one handler "wins" the row; on a recovery / RunResult race there is no double state commit.
  - **(k) Case 2 — isolated Keeper.** An instance that has lost connectivity to PG / Redis but is still alive for some Souls: its **health-probe becomes unhealthy** → the LB steers traffic away; **soul-shedding** — the instance drops its Soul streams, the Souls reconnect to a working Keeper (connection algorithm [ADR-002](0002-transport-grpc-ha.md#adr-002-transport-keeper--souls--grpc-bidirectional-stream-over-mtls-ha-keeper-cluster)) + retry. **Promoting a DB replica is OUTSIDE Soul Stack** (Patroni / cloud failover, [ADR-005](0005-storage-postgres.md#adr-005-keeper-state-storage--postgres)). The option "ask replicas to switch over" (DB failover by Keeper itself) is **rejected**; soul-shedding is adopted (Keeper does not manage its own DB topology). — **IMPLEMENTED 2026-05-25** (propose-and-wait names closed by the user): (1) **Conclave** — a Redis registry of live Keeper instances (`keeper:instance:<kid>`, TTL 30s + renew 10s, lease.go pattern; the presence→Redis invariant, [ADR-006](0006-cache-redis.md#adr-006-cache-and-coordination--redis)); provides `CountLive` for the refuse-guard. (2) **Watchman** — isolation detection: a periodic ping of PG+Redis (the `/readyz` set) + debounce (isolation after N consecutive failures, default 3) → **hard-close** of local EventStream streams (`StreamManager.CloseAll` cancels the per-stream ctx; the receive-loop is moved into a goroutine so that `stream.Recv()` is cancellable) → the Soul gets an EOF → reconnect via the failback-list ([ADR-002](0002-transport-grpc-ha.md#adr-002-transport-keeper--souls--grpc-bidirectional-stream-over-mtls-ha-keeper-cluster); Soul-failback is already implemented). (3) **refuse-guard** — when `acolytes:0` + `Conclave.CountLive>1` Keeper refuses to start (explicit opt-out `allow_unsafe_single_path_multi_keeper` / env), closing Finding-A (see (h)). **go-away rejected** — a clean EOF is sufficient, the Keeper↔Soul proto is not touched. Soul multi-endpoint failback — dev-config (the mega-test stand hardcoded a single endpoint). The names Sentinel (collision with Redis Sentinel) and Vigil (taken) are rejected.
- **ADR reconciliation.** [ADR-002](0002-transport-grpc-ha.md#adr-002-transport-keeper--souls--grpc-bidirectional-stream-over-mtls-ha-keeper-cluster) is **strengthened** — the stateless cluster now also distributes **execution** (not only stream reception): any instance, through an Acolyte, picks up any task. [ADR-005](0005-storage-postgres.md#adr-005-keeper-state-storage--postgres) — execution ownership is materialized in a **PG row** (`apply_runs` Ward columns), not in memory. [ADR-006](0006-cache-redis.md#adr-006-cache-and-coordination--redis) — Summons over pub/sub, recovery scan on the Reaper leader; **the claim-lease lives in Postgres**, not in Redis (a task lease is cold persistent ownership, unlike the SID-lease). [ADR-009](0009-scenario-dsl.md#adr-009-scenario--the-full-destiny-task-dsl-the-boundary-with-destiny-is-a-recommendation) — barrier / serial preserved; serial is claimed whole. [ADR-012(d)](0012-keeper-soul-grpc.md#adr-012-keepersoul-grpc-contract-one-eventstream-with-oneof-keeper-side-render-forward-compat-only-add) — refined: render is bound to claim and is re-rendered on recovery.
- **Consequences.**
  - **`apply_runs` migration** — additive: new statuses `planned` / `claimed`, new columns `claim_by_kid` / `claim_at` / `claim_expires_at` / `attempt`, plus a **`recipe jsonb`** column (see below). The old path (direct `running`) keeps working until Phase 1 (Phase 0).
  - **Acolyte-pool** on each instance (`keeper.acolytes:N` in [config.md](../keeper/config.md)) — replaces the single run-goroutine.
  - **Re-render on claim / recovery** — render moves from dispatch to claim; recovery re-renders from the recipe. The **run recipe** (scenario-ref + `input` with vault-refs **as-is**, without unwrapped secrets) is materialized in the **`apply_runs.recipe jsonb`** column (G4, propose-and-wait passed — a column was chosen rather than a separate table: the recipe is 1:1 with the task, and claim already pulls the row). Invariant A: secrets are resolved only in the Acolyte's RAM at claim; in `recipe` — the vault-ref as-is.
  - **Only-add proto field `attempt`** in `ApplyRequest` (`proto/keeper/v1/apply.proto`, **field 4** — implemented, Phase 2) — the fencing-epoch for the Soul-guard ([ADR-012(c)](0012-keeper-soul-grpc.md#adr-012-keepersoul-grpc-contract-one-eventstream-with-oneof-keeper-side-render-forward-compat-only-add) forward-compat only-add). Echoed from `apply_runs.attempt` at the moment of claim: `ClaimNext` increments it on every Ward capture (`scenario/claim.go` puts `run.Attempt` into `ApplyRequest`), so a re-claim of a stale task arrives with a **larger** attempt than the original. The Soul-guard (`runtime.ApplyRunner`, `lastSeenAttempt map[apply_id]int32`, per-process) rejects an `ApplyRequest` with `attempt < lastSeenAttempt` — cutting off the stale duplicate of a dead Ward whose apply is still in flight; the rejected duplicate is silently dropped (barrier-B1), and the original (the larger attempt) closes with its own `RunResult`. **`attempt = 0`/empty = an old Keeper without fencing** (forward-compat): the guard does not reject such a request, and fencing degrades to protection by `apply_id` + SID-lease. The never-reuse of field numbers is preserved. Metric `soul_apply_fenced_total`.
  - **The Reaper recovery-scan rule — `reclaim_apply_runs`** (name fixed, propose-and-wait passed; implemented in `keeper/internal/reaper`): `UPDATE apply_runs SET status='planned' … WHERE status='claimed' AND claim_expires_at < NOW()` (after GATE-1; it **was** `status IN ('claimed','running')` — see amend (c)) (resetting `claim_by_kid`/`claim_at`/`claim_expires_at`; **`attempt` is NOT reset** — the next `ClaimNext` increments it). **Requires no migration** — the `claim_expires_at`/`attempt` columns and the partial index `apply_runs_claim_scan_idx` came with migration 025. **`enabled:false` by default** (see below). Metric — via `ObserveRule` (`keeper/internal/reaper`).
  - **Single-winner state-commit — variant W1 (implemented).** Moving `incarnation` `applying`→terminal stays in the run-goroutine but is protected by an SQL guard: `UPDATE incarnation SET status=… WHERE name=$1 AND status IN ('applying','destroying') RETURNING …` (0 rows = the row is already finalized/deleted → no-op, like destroy-S-D3). Additionally the `apply_runs` terminal is append-only (a terminal is not overwritten by a terminal). On a recovery/RunResult race there is no double state commit. **Variant W2** (moving the commit into the Acolyte) is **tied to Phase 3** distributed barrier — not now.
  - **Lease invariant (recovery applicability boundary).** ⚠️ *Pre-GATE-1 wording — WEAKENED, see amend (e).* Before GATE-1, correct recovery required `acolyte_lease > max(single-host apply time, runTimeout)`, otherwise reclaim would return a **live** Ward (`running`) to `planned` → a second SendApply. **After GATE-1 this is moot**: reclaim takes only `claimed` (the render/claim phase, BEFORE delivery), while a live long-running apply sits in `dispatched` (reclaim does not touch it). It suffices that `acolyte_lease > max-RENDER` — the current default of **30s is fine**, and revising the lease and Acolyte lease-renew **are not required for the recovery boundary**.
  - **Enabling recovery — a gate (an operational step, not a lone `enabled:true`).** ⚠️ *Pre-GATE-1: a 3-condition gate — RELAXED, see amend (e).* After GATE-1 the gate is: (a) **fencing-Soul rolled out across all Souls** (all Soul agents understand `ApplyRequest.attempt` — the guard on execution + echoing `RunResult.attempt` for the epoch-check on receive) + (b) **slices S2–S5 (`dispatched` phase + mark-before-send + reclaim-only-claimed + epoch-on-receive) done** (present). The condition "`acolyte_lease > max-apply` OR Acolyte lease-renew" is **dropped** (the lease invariant is weakened). Before enabling — a separate architect re-review of the assembly. Until the gate is satisfied, a lone `enabled:true` is dangerous (the old non-fenced path, see amend (f)).
  - **Three layers of protection against double execution (normative).** Safe recovery rests on three independent layers, each covering its own stage: **fencing** (`attempt`-epoch) — protection of **EXECUTION** on the Soul against a *smaller* (stale) attempt; **SID-lease** ([ADR-006](0006-cache-redis.md#adr-006-cache-and-coordination--redis)) — dedup of **DELIVERY** of one and the same epoch (apply to a host goes only through the stream owner); **single-winner** — protection of the state **COMMIT** (one handler wins the `incarnation` row). All three are needed simultaneously — none covers another's stage: fencing does not dedup delivery, SID-lease does not distinguish attempt, single-winner does not prevent a double apply to a host.
  - **Summons** — a Redis pub/sub topic for the planned-tasks signal; the topic is **`apply:summons`** (fixed, propose-and-wait passed).
  - **Names in [naming-rules.md](../naming-rules.md)** — Acolyte / Ward / Summons (+ definitions).
  - **Update of [storage.md](../keeper/storage.md)** — description of `apply_runs` (statuses + Ward columns + lifecycle; after GATE-1 — `planned → claimed → dispatched → terminal`, `running` vestigial, see amend (a)).
  - **Full-roster render on claim (Phase 1 cutover).** On claim the Acolyte renders the **full run roster** (like the run-goroutine: `LoadIncarnationHosts` → the whole roster → `Render` with `Hosts`=the whole roster), then takes its own host's slice `groupByHost(tasks, plans)[sid]`. This eliminates the per-host↔full-roster dialect: single-host render (`Hosts`=[host]) silently diverged from the old path — `run_once` was not trimmed (`applyRunOnce` with `len(targeted)≤1` returns the target as-is → the task on ALL hosts instead of one), `soulprint.hosts`/`.where` and `incarnation.host_count` collapsed to a roster of a single host, and cross-host `state_changes.sets` lost their neighbors (the same collapse now hits a `core.state.<verb>` capture reading `soulprint.hosts`, [ADR-0084](0084-explicit-state-capture.md)). The list of full-roster dependencies is **open** — that is why the full roster is reproduced rather than pointwise guards. The SID validation "host still in the roster" (disconnected/revoked between dispatch and claim → error) is preserved BEFORE the render. Invariant A does not change: input secrets are scenario-level (resolved once, not per-host), so the full roster does NOT increase the secret material in RAM.
  - **KNOWN GAP "stuck-claimed" (Phase 1).** SendApply went through, but `MarkClaimedRunning` (claimed → running) failed (PG error) — the task sticks in `claimed` forever. It **cannot be fixed locally**: without attempt-fencing (Phase 2), re-sending / resetting to `planned` risks a **double SendApply** (the apply already went to the Soul). **Closed by Phase 2**: the Reaper recovery scan (stale Ward `claimed` → `planned`, (i)) + the attempt-epoch cuts off the stale `ApplyRequest` on the Soul ((g)).
  - **KNOWN GAP "`lastSeenAttempt` unbounded".** The Soul-guard keeps `lastSeenAttempt map[apply_id]int32` per-process without eviction — the map grows on every new `apply_id` over the lifetime of the Soul process. Acceptable for the MVP (applies are rare relative to the process lifetime, a restart zeroes it — and after a restart there is physically no duplicate). Candidate for closure — TTL/LRU eviction of entries. Deferred.
  - **KNOWN GAP "Acolyte lease-renew missing".** ⚠️ *Not relevant to the recovery boundary after GATE-1 (amend (e)).* The Acolyte does not extend `claim_expires_at` during a long apply — a Ward holds a fixed lease from the moment of claim. Before GATE-1 this was the root of the lease invariant; **after GATE-1** reclaim takes only `claimed` (the render/claim phase, not the whole apply), so a fixed lease **does not affect** recovery correctness (a long apply sits in `dispatched`, which reclaim does not touch). Renew is no longer a recovery blocker; it remains an optional improvement for the predictability of claim timings.
- **Amendment 2026-05-29 / refined by the Voyage epic 2026-05-30 (run↔apply_run back-link).** [ADR-043](0043-voyage.md#adr-043-voyage--unified-batch-run) (Voyage) `kind=scenario` spawns `apply_runs` the same way Tide did before. The sketch model of the `apply_runs.run_id` back-link (FK on `runs(run_id)`) from the first revision of this amendment is **not implemented and cancelled**: during the Voyage epic the `runs`/`run_targets` entity was refined to `voyages`/`voyage_targets` (migration `059`), and the direction of the link was **inverted** — the back-link lives not in `apply_runs` but in the orchestrator table. `apply_runs` stays orchestrator-agnostic (a direct `incarnation.run` / a standalone errand exist without Voyage) and carries no column pointing to the parent run. The actual link: **`voyage_targets.apply_id → apply_runs(apply_id)`** for `kind=scenario` (and **`voyage_targets.errand_id → errands(errand_id)`** for `kind=command`), partial-UNIQUE indexes (migration `063`) guarantee "one apply_id/errand_id → at most one `voyage_targets` row". The history-timeline resolves `voyage_id` via `LEFT JOIN voyage_targets` on apply_id/errand_id (`keeper/internal/soul/history.go`), and the back-link write is `MarkTargetRunning(...)` in `voyageorch`. The columns `apply_runs.tide_id`/`apply_runs.run_id` are **absent** from the schema (the `tides` table was dropped by migration `061`). The spawn same-tx invariant (`apply_run`/`errand` + UPDATE of the parent in one PG-tx) and attempt-fencing are inherited unchanged.

- **Deferred (post-MVP).** **Distributed serial** (several Acolytes on one serial barrier) — a separate ADR. **Durable Summons / outbox** (guaranteed signal delivery instead of best-effort pub/sub + poll) — if needed; the poll-fallback covers signal loss in the MVP.
- **Trade-offs.**
  - **Re-render on claim / recovery** — the price for the invariant "no plaintext secrets in PG": render is more expensive (repeated on takeover), but the unwrapped material is nowhere persisted. Accepted.
  - **claim-lease in Postgres, not in Redis** — task ownership is cold and must survive a Redis restart; the price is that claim operations hit PG (but this is `UPDATE … SKIP LOCKED`, cheap) rather than hot Redis.
  - **serial = claimed whole by a single Acolyte in the MVP** — we lose parallelism within a serial run; accepted as a deliberate simplification, distributed serial deferred to Phase 3.
  - **Soul-fencing depends on the proto field `attempt`** — before Phase 2 fencing degrades to protection by `apply_id`; accepted (SID-lease already cuts off most duplicates, `attempt` closes the stale-attempt).
  - **Full-roster render on claim — O(N²) per-host CEL + N×per-host vault per run.** Each of the N claims renders the **full** roster (N hosts), so the total render cost of a run = O(N²) CEL evaluations and N×per-host vault resolutions vs O(N) of the old path (the run-goroutine renders the roster once). The price for eliminating the per-host↔full-roster dialect (see Consequences "Full-roster render on claim"): the list of full-roster dependencies is open, pointwise guards fail-open. Acceptable in **Phase 1** (a handful to a few dozen hosts); **hundreds of hosts** → a candidate for optimization (symmetrically to "distributed serial — Phase 3"). Accepted.

> **Amend (GATE-1: deliver-once recovery, 2026-05-25).** Redesign of the recovery phase (implemented, passed architect + review). Closes the double-apply window discovered in Phase 2: claimed→running was marked **after** SendApply — a crash between sending and marking left a `claimed` row that the recovery scan re-claimed → a second apply on the same host. Below is the final model; the wordings of (i), (j), the lease invariant, and the recovery-enable gate above are **replaced** by the following (the old text is kept marked as pre-GATE-1 to avoid losing history; on divergence the source of truth is this amend).
>
> - **(a) apply_runs lifecycle updated.** Phase chain: **`planned → claimed → dispatched → terminal`** (`success` / `failed` / `cancelled`). The new phase **`dispatched`** is an intent marker "the task has been handed to the Soul"; it is written **ATOMICALLY** (a commit to PG) **STRICTLY BEFORE SendApply** (`MarkDispatched` before sending, not after). The **`running` status is PRESERVED** in the CHECK (there is no no-backcompat cleanup), but in the Acolyte flow it is **NO LONGER used** (vestigial): only the old synchronous path writes it (`acolytes:0`, `dispatchWave → Insert(running)`). Migration **040** extends the CHECK (`status IN (… , dispatched)`); `down-040` is correct. The name `dispatched` is fixed (propose-and-wait closed by the user 2026-05-25; the motive — it coincides with the `dispatch`/`grpc.apply_dispatch` already used in the code, zero cognitive gap) — recorded in [naming-rules.md](../naming-rules.md).
> - **(b) Moving the mark before sending (the root of the fix).** Previously claimed→running was marked **AFTER** SendApply → a race: a crash in the window between send and mark left a `claimed` row, and the recovery scan re-claimed it → a **DOUBLE apply**. Now claimed→`dispatched` **BEFORE** SendApply eliminates this. The death windows of the Acolyte path after the fix: **W-a** (`MarkDispatched` ok, crash **before** SendApply) → a `dispatched` row, the task is not delivered, reclaim **does not touch** it → a **safe HANG** (NOT a double apply); closure — Soul-reconcile, post-MVP (see (g)). **W-b** (the old "mark after send" gap) — **ELIMINATED**.
> - **(c) reclaim narrowed to `claimed`.** `reclaim_apply_runs` is now `WHERE status='claimed'` (was `IN ('claimed','running')`). **The nature of the rule has changed**: "finish off an **UNDELIVERED** task" (the owner died **before delivery**, at the render/claim phase), NOT "revive a zombie `running`". The **`dispatched` phase is NOT reclaimed** — after delivery the run is owned by the Soul; reclaiming a delivered one = a double apply.
> - **(d) Epoch-check on RESULT RECEIPT (fencing symmetry).** attempt-fencing becomes **two-sided**: (1) protection of **execution** in the Soul (`AcceptAttempt`, was in (g)) + (2) protection of result **RECEIPT** in the Keeper. `RunResult` carries an echo of `attempt` (proto **only-add field 4**, [ADR-012(c)](0012-keeper-soul-grpc.md#adr-012-keepersoul-grpc-contract-one-eventstream-with-oneof-keeper-side-render-forward-compat-only-add) forward-compat). `correlateRunResult` compares against `apply_runs.attempt`: `recvAttempt < rowAttempt` (and `!= 0`) → a result of a **stale** attempt → **stale-drop** (metric `keeper_runresult_stale_total`), state is **NOT committed**; `==` / `0` (forward-compat: an old Soul without the echo) / `>` (impossible, fail-safe + defensive warn-log) → commit. The result is accepted on **ANY** Keeper instance (Soul failback, [ADR-002](0002-transport-grpc-ha.md#adr-002-transport-keeper--souls--grpc-bidirectional-stream-over-mtls-ha-keeper-cluster)) — the authority for actuality is in the **shared PG** (`apply_runs.attempt`), not in an instance's memory. **Three orthogonal layers** of protection against double execution (replacing the "Three layers of protection" wording above, augmenting it with receipt): **execution fencing** (the Soul rejects a *smaller* attempt) / **SID-lease delivery dedup** ([ADR-006](0006-cache-redis.md#adr-006-cache-and-coordination--redis)) / **single-winner commit + receipt epoch-drop** (Keeper). The epoch-check on receipt is orthogonal to single-winner: epoch cuts off a *stale* attempt, single-winner — a *repeated terminal of the same* attempt.
> - **(e) Lease invariant WEAKENED.** recovery-enable **NO LONGER requires** `acolyte_lease > max-apply` and **does not require** Acolyte-lease-renew. It suffices that `acolyte_lease > max-**RENDER**` (the current default of **30s** — fine), because reclaim takes only `claimed` (the render/claim phase **BEFORE** delivery), not the whole apply: a live long-running apply sits in `dispatched`, which reclaim does not touch. This **removes** the old lease-invariant wording and **relaxes** the recovery-enable gate. The gate is now: **fencing-Soul rollout** (also needed for accepting the RunResult echo) + slices S2–S5 done. (The condition "`acolyte_lease > max-apply` OR Acolyte lease-renew" is dropped; the KNOWN GAP "Acolyte lease-renew missing" above becomes irrelevant to the recovery boundary.)
> - **(f) TWO KNOWN-GAPs (recorded explicitly so they are not "fixed" back).**
>   - **The old synchronous path without Reaper recovery.** With `acolytes:0` (the prod default; Acolyte is opt-in) tasks are written directly to `running`, and narrowing reclaim to `claimed` means the Reaper **does NOT recover** these `running` rows. This is **NOT a regression**: recovery of the old path is the in-memory run-goroutine of the owner instance (+`runTimeout`), not Reaper-reclaim; on the owner's death its run was not recovered anyway (a property of the pre-Acolyte model). **`reclaim_apply_runs` and `acolytes > 0` are a coupled pair: enabling reclaim with `acolytes:0` is FORBIDDEN** — on the non-fenced (old) path reclaim is itself unsafe (a double apply without epoch protection).
>   - **Cancel visibility of `dispatched`.** The `RequestCancel` guard **does NOT include** `dispatched` (by design in the pilot): to already-delivered Souls the Keeper **does NOT send** `CancelApply` (best-effort cancel of delivered runs is a deferred admin-API layer via `Outbound.SendCancel`). The barrier read (`SelectStatusesByApplyID` by `apply_id`) **does see** `dispatched` — it waits for the terminal correctly. Full closure = a separate sub-slice (`guard += 'dispatched'` **TOGETHER** with emitting `CancelApply` to the Soul + receiving `RunStatus.CANCELLED`), to be combined with Soul-reconcile (see (g)). **Amend (r) (NIM-972) keeps this for its own flag:** the Cancel it carries on the applying lock is deferred while a row is `dispatched` and none is `planned` or `claimed`, and acted on once none is `dispatched`. A Cancel that acts beside an undelivered row, or through the owning instance's local path, still closes `dispatched` rows.
> - **(g) Soul-also-dead (Keeper and Soul both dead after delivery).** A window that deliver-once itself **does not close**: `dispatched` will hang — `RunResult` will not arrive, and reclaim does not touch the row. **SOLUTION:** closure **post-MVP via Soul-reconcile** — on reconnect the Soul reports the `apply_id`s it is actually driving, the Keeper reconciles and terminates orphaned `dispatched`. In the **MVP** — a documented known-gap (the operator restarts the run manually). **We do NOT do a Reaper dispatched-timeout** (a terminal-by-timeout without confirmation from the Soul is unsafe). — **IMPLEMENTED 2026-05-25 (S6 Soul-reconcile), known-gap removed:** on (re)connect the Soul sends `WardRoster` (a ReplaceAll snapshot of driven `apply_id`+attempt; a new `FromSoul` only-add message, oneof field 8 — [ADR-012(k)](0012-keeper-soul-grpc.md#adr-012-keepersoul-grpc-contract-one-eventstream-with-oneof-keeper-side-render-forward-compat-only-add)) right after Hello; in `OrphanDispatched` the Keeper, via an epoch-fenced single-winner reconciliation, terminates the `dispatched` rows of this SID that are not in the set → a new terminal **`orphaned`** (migration 044; the barrier classifies it as fail → incarnation `error_locked`). The Soul's set is in-memory (active ∪ recently-finished ring TTL 30s; a Soul restart → empty → its dispatched are legitimately orphaned). An old Soul without `WardRoster` → sweep no-op (fail-safe; under the same fencing-Soul rollout gate as recovery-enable (e)).
> - **(h) Amendment (2026-05-25, multi-keeper guard).** The invariant is made **explicit**: the run-goroutine path (`acolytes:0`) is **single-keeper-only**; **N>1 Keeper instances require `acolytes>0`**. A live multi-keeper test confirmed the footgun: with `acolytes:0` an apply created on keeper-A with a Soul on keeper-B's stream runs on the host (`apply_runs=success`), but the incarnation **hangs in `applying` forever** — the in-memory owner on keeper-A does not observe the `RunResult` that went to keeper-B. The guard is **warn, not refuse** (without a new instance-registry entity): (1) a startup advisory with `acolytes:0`; (2) a targeted `WARN` in the run-goroutine dispatch path when the target Soul's SID-lease belongs to a **different KID** (the footgun fires exactly here). A refuse-startup-guard + **a registry of live Keeper instances** were **IMPLEMENTED 2026-05-25** (the registry = **Conclave**, see (k)): with `acolytes:0` + `Conclave.CountLive>1` Keeper refuses to start (explicit opt-out `allow_unsafe_single_path_multi_keeper` / env `KEEPER_ALLOW_UNSAFE_MULTI_KEEPER`); the dispatch-time WARN is kept as a runtime safety-net on top of refuse. The invariant is recorded in [docs/keeper/config.md](../keeper/config.md).
> - **(i) Amendment (2026-05-25, FINDING-01: apply_runs does not over-report non-targets).** On the Acolyte path (`acolytes>0`) `dispatchPlanned` writes an `apply_runs` row for the WHOLE incarnation roster BEFORE resolving `on:`/`where:` (resolution is per-host at claim); the barrier holds `wantHosts = len(roster)`. Previously a host for which `on:`/`where:` filtered out all tasks (0 tasks) was closed as `success` (no-op) → `apply_runs` falsely showed "success on all" (found by Phase 2 HA acceptance: a 9-host incarnation, `on:[cluster-a]` → actually 3 tasks, but 9× success). Fix: a non-target no-op host → a new terminal **`no_match`** (migration 045; `classify` counts `no_match` as a benign terminal on the success side — the barrier tallies up `wantHosts`, incarnation `ready`; `failed`/`cancelled`/`orphaned` alongside are still fail-closed). `apply_runs` is currently NOT exposed externally via the API (history = `state_history`), so the impact was LOW; `no_match` makes the record honest until a `/runs` endpoint appears. **A residual dialect** (NOT fixed by this slice): the old `acolytes:0` path does not materialize non-target rows at all (target-only), while the Acolyte path writes the whole roster (`success`+`no_match`); full unification of the row count between modes is a separate decision.

> - **Extension 2026-05-27 (Tide-spawn apply_runs — back-link to `tides`).** [ADR-040](0040-tide.md#adr-040-tide--invocation-time-scope-chunking--target-override) introduces a **second path** for materializing `apply_runs` rows that does not violate this ADR's invariants.
>
>   **Two paths for spawning apply_runs:**
>
>   - **Classic (single-run, `tide_id IS NULL`):** the scenario-runner, on dispatch `POST /v1/incarnations/.../scenarios/.../run` **without** the `wave` field, writes one `apply_run` per host in `planned` and sends a `Summons` — the Acolyte flow works as described in (a)–(j) above.
>   - **Tide path (`tide_id` + `surge_index` populated):** **TideWorker** (a separate pool, see below) per-Surge spawns N apply_run rows **in one PG transaction** with UPDATE `tides.current_surge_index=N` + `current_apply_id=Y` — the same-tx invariant [ADR-040 amendment 2026-05-27](0040-tide.md#adr-040-tide--invocation-time-scope-chunking--target-override). From there the Acolyte flow is indistinguishable from the classic one (Acolyte claim → render → dispatch → terminal): the Tide orchestrator knows about these `apply_run` rows **only** through the `current_apply_id` field and does not manage their lifecycle directly.
>
>   **`apply_runs.tide_id` / `surge_index` — nullable back-link:**
>
>   - `tide_id` — a nullable FK on `tides(tide_id)`; `surge_index` — an int (nullable, always together with `tide_id`).
>   - Classic single-run: both `NULL`.
>   - Tide-spawn: both populated; the composition `(tide_id, surge_index)` identifies a Surge within a Tide.
>   - **Reaper apply_runs cleanup (`purge_apply_runs` / `reclaim_apply_runs`) does NOT depend on `tide_id`** — the apply_run cycle is independent of the Tide cycle. A Surge's `apply_run` is cleaned up by its own rules (max_age from `finished_at`); the Tide itself lives on a separate cycle and is cleaned up by `reclaim_tides` (recovery of stale claims). There is no cascading `ON DELETE` — `apply_runs.tide_id` has no `ON DELETE` clause (default NO ACTION); deleting a `tides` row post-MVP (retention of `tides`) will require a separate decision on orphan apply_runs.
>
>   **TideWorker pool — separate from Acolyte:**
>
>   - **Not a shared pool** — deadlock prevention: with `acolytes: 1` + 1 Tide occupying the Acolyte slot, a Surge within the Tide would have nowhere to land. TideWorker and Acolyte compete only for PG connections, not for worker slots.
>   - Configuration — a separate block `keeper.yml::tide:` (recommendation — `tide_workers ≤ acolytes-1` per-instance). See [`docs/keeper/config.md`](../keeper/config.md).
>   - The worker cycle is simple: `claim → orchestrate → poll/sleep`. Tide operations are rare and large (one Tide = N Surges over minutes-hours), without the complex wake logic of the Acolyte path.
>
>   **ADR-027 invariants do not change:**
>
>   - apply_run lifecycle: `planned → claimed → dispatched → terminal` — the same for both paths (Tide-spawn lands in `planned` with `tide_id`/`surge_index` already set).
>   - The fencing epoch (`attempt`-fencing of execution + epoch-check of receipt) — works identically; the Tide orchestrator does not interfere with the Acolyte's attempt increment.
>   - Single-winner state-commit — `UPDATE incarnation … WHERE status='applying'` remains the root of protection; per-Surge state-commit is implemented by a separate SQL guard on the Tide-orchestrator side (commit-only under confirmed lease ownership via `FinalizeWithOwnership`, [ADR-040 amendment 2026-05-27](0040-tide.md#adr-040-tide--invocation-time-scope-chunking--target-override)).
>   - SID-lease + Soul-fencing for delivery dedup — also unchanged.

> **Amend (l): Voyage-orchestrator self-orphan-release of the applying-lock before re-run (2026-06-21).** Implemented (`keeper/internal/voyageorch` + `incarnation.ReleaseApplyingOrphan`), passed review + re-audit. Closes a hole in the Voyage path that `reclaim_apply_runs` structurally **does NOT cover**.
>
>   - **Problem.** The Voyage owner (a Keeper instance) died during a per-incarnation scenario-run: `incarnation.status='applying'` was committed (`lockRun`), but the run did not reach a terminal. After reclaim the Voyage is picked up by a new owner that wants to re-run this incarnation — but `lockRun` rejects it ("incarnation already applying"), and the Voyage **hangs forever**. `reclaim_apply_runs` **does not reach** here: it reclaims a stale `claimed` Ward into `planned` (the render phase BEFORE delivery), whereas the `incarnation`-lock is an **ownerless flag without epoch/owner/lease** on a separate `incarnation` row, not `apply_runs`. The `apply_run` itself may not **exist** at all by the time of re-run: it is ephemeral (a crash BEFORE the Insert after `lockRun`) or removed by the `purge_apply_runs` retention-purge (terminal >30d). ⚠️ The former attribution "reclaim_apply_runs cleaned up the orphaned apply_runs row" is **incorrect** — reclaim does not delete rows; the source of "the row is gone" is purge-retention OR a pre-Insert crash.
>
>   - **Detection.** Before spawning the re-run, the reclaimed VoyageWorker finds an orphan candidate by the **back-link `voyage_targets.apply_id`** of THIS Voyage from the **previous attempt**: an incarnation row in `running`/`awaiting` with a recorded `apply_id`. `MarkTargetRunning` writes the back-link UNDER the CAS `voyages.attempt=$attempt` AFTER the spawn; we are NOW BEFORE the spawn of our attempt — which means the recorded apply_id is from the previous pass. Another Voyage / a direct run with a different apply_id **do not have** a back-link under our voyage_id → their lock is not picked up by this seam (the protection rests on the FENCING-2/3 bundle, not on FENCING-1 alone).
>
>   - **Fencing (all mandatory before release).** (1) **no-live-rival** — there is no active (non-terminal) `apply_run` with a FOREIGN apply_id for the incarnation (a live direct run / another Voyage holding its own row → block), and, since amend (r), the lock's epoch names no other run — a live run between two steps holds no non-terminal row. (2) **reclaimed-attempt + VerifyOwnership** — we are the current Voyage owner with claim-epoch `run.Attempt`; if we ourselves were reclaimed (`ErrLeaseLost`) → we do not touch it. (3) **single-winner CAS** `applying → ready` under `FOR UPDATE` + the guard `status='applying'`: an honest RunResult from the previous owner that already took the row out of applying yields a no-op. `state` is NOT touched (last known-good = pre-run state, the orphan did not reach the state-commit).
>
>   - ★ **Residual double-apply class — the same acceptable one as `reclaim_apply_runs`.** A network partition: a live partitioned previous owner (still driving apply to hosts) + a re-run by the new owner → a double dispatch to a host. Protection — **gate-1 attempt-fencing RunResult** (the Soul rejects a smaller attempt at execution + the epoch-check on receipt) + **module idempotency**. The seam does NOT introduce a new risk class beyond the existing recovery.
>
>   - ★ **Always enabled together with `reclaim_voyages` (default-ON), NOT behind a separate opt-in.** A deliberate choice: `reclaim_voyages` is already default-ON; without the orphan-release seam Voyage recovery is **functionally broken** (a reclaimed Voyage hangs on the very first applying incarnation). A separate gate here would create a "recovery is enabled but does not work" mode.
>
>   - ★ **Coexistence window with `UpdateStateFromRun`.** `UpdateStateFromRun` (the run terminal) fences only the **status-CAS** (`WHERE status='applying'`), NOT attempt/apply_id — this is an existing property of **(j)**/W1. Consequence: an honest terminal from the old owner that **passed gate-1** can overwrite a re-run (both see `applying`, both are valid by the status-CAS). The seam **widens** their coexistence window (the re-run starts earlier — right after orphan-release, not after the natural finish of the old one). This is not a correctness regression: both outcomes are valid terminals of the same logical operation under gate-1; strengthening to attempt-fencing of the state-commit is tied to Phase 3 / W2, not now.

> **Amend (m): standalone-orphan reconcile via `incarnation` epoch columns + the Reaper rule `reconcile_orphan_applying` (2026-06-21).** A backstop foundation (slice S0 — schema + contract; the rule insertion and epoch write in `lockRun` — slices S1). Closes a hole in the **direct** `incarnation.run` (without Voyage), symmetric to (l), but which the (l) seam structurally does **NOT** cover.
>
>   - **Problem.** A direct `incarnation.run` (standalone, not under Voyage) sets `incarnation.status='applying'` (`lockRun`); if the Keeper owner of the run dies before a terminal — the lock hangs **forever**. The (l) seam does not reach here: it finds an orphan candidate by the back-link `voyage_targets.apply_id` of THIS Voyage — a direct run has **no** `voyage_targets` row, and the back-link is structurally unreachable. `reclaim_apply_runs` also does not reach (it reclaims a stale `claimed` Ward into `planned`, whereas the `incarnation`-lock is a separate flag on the `incarnation` row, not `apply_runs`). Root cause: the applying flag is an **ownerless bool without epoch / owner / lease**; it is impossible to distinguish "a live run is still going" from "the owner is dead, the lock is orphaned".
>
>   - **Solution — an epoch for the applying flag (4 NULLABLE `incarnation` columns).** `applying_apply_id` / `applying_attempt` / `applying_by_kid` / `applying_since` (migration 082, additive, without backfill — for existing rows NULL = "epoch unknown", fail-safe for the rule). `lockRun` writes them in the same tx as `status='applying'` (S1), and the run terminal clears them to NULL together with removing the applying status (S1). This turns the bare bool into an **inline-epoch**: the rule sees WHO holds the lock (`applying_by_kid`) and HOW LONG AGO (`applying_since`), without a separate table and without a back-link.
>
>   - **The rule `reconcile_orphan_applying` (name fixed by the user; default-ON + presence-gate; insertion — S1).** Two-phase:
>     - **(1) SQL candidates.** `SELECT … FROM incarnation WHERE status='applying' AND applying_since < NOW() - <stale_after>` (partial index `incarnation (status, applying_since) WHERE status='applying'`, migration 082 — parity with `apply_runs_claim_scan_idx`). `stale_after=90s` (parity with `mark_disconnected`).
>     - **(2) presence check.** For a candidate with a non-empty `applying_by_kid`: whether the owner is alive in Conclave (`InstanceAlive(applying_by_kid)`, ADR-006(e)). Alive → skip (the run is really going). Dead → orphan.
>     - **(3) fenced single-winner.** `applying → ready` under `FOR UPDATE` + the guard `status='applying'` (reusing the idempotent `ReleaseApplyingOrphan` already introduced by (l)); an honest terminal from the real owner that managed to remove applying yields a no-op. `state` is NOT touched (the orphan did not reach the state-commit, last known-good = pre-run state).
>   - **Default — ON with a presence-gate (the user's decision).** No-op without a live Conclave (the presence check is fail-safe: on a Redis error / an empty `applying_by_kid` — it does not reclaim, so as not to disrupt a live run with an unknown epoch). The release audit-event — `reaper.reconcile_orphan_applying.executed` (name fixed; registration/emission — S1).
>
>   - **Fencing (all mandatory before release, S1 insertion).** (1) **FENCING-1 no-live-rival** — there is no active `apply_run` with a different apply_id for the incarnation (a live direct run / another Voyage holding its own row → block), as with (l)/`reclaim_apply_runs`. (2) **presence-death of the owner** — `InstanceAlive(applying_by_kid)=false` (phase 2). (3) **single-winner CAS** `applying→ready` (phase 3). The residual double-apply class — **the same acceptable one** as with (l) and `reclaim_apply_runs` (a network partition of a live partitioned owner + a re-run); protection — gate-1 attempt-fencing `RunResult` + module idempotency. The seam introduces no new risk class.
>
>   - **Coexistence with the Voyage path (l).** Both converge on **one** idempotent CAS `ReleaseApplyingOrphan` (`applying→ready` under `FOR UPDATE` + a status-guard). (l) detects an orphan by the `voyage_targets` back-link (the Voyage path), (m) — by the `incarnation` epoch columns (the standalone path); the release is a shared function. There is no conflict: if both rules target one row (theoretically impossible — a Voyage incarnation has a `voyage_targets` row, a standalone one does not), the second CAS is a no-op.

> **Amend (m-S1): epoch write in `lockRun`, clearing in terminals, the Reaper rule `reconcile_orphan_applying` (2026-06-21).** Implementation of slice S1 on top of the S0 foundation (migration 082 + `Conclave.InstanceAlive` + `ReleaseApplyingOrphan` from (l)). The normative wordings below fix the S1 behavior; on divergence from the rule description in (m) above, the source of truth is this block (it details, it does not override (m)).
>
>   - **Atomicity of the epoch write.** `lockRun` writes ALL 4 columns (`applying_apply_id`/`applying_attempt`/`applying_by_kid`/`applying_since`) in the SAME PG-tx and the SAME `UPDATE` as `status='applying'` (via `updateStatus` in `keeper/internal/scenario/state.go`). There is no "applying without epoch" window — a crash before commit rolls back the whole `UPDATE`. `applying_by_kid` = the KID of this Keeper instance (the same source as the lease-holder/Voyage-claim); `applying_apply_id` = the `apply_id` of the run; `applying_attempt` = an echo of the current `apply_runs.attempt` (at the moment of `lockRun` there is no `apply_runs` row yet — this is the run's initial attempt); `applying_since=NOW()`. The run terminal (`UpdateStateFromRun` success + lock-fail + abort) clears all 4 to `NULL` atomically with removing applying.
>
>   - **FromLocked/rerun-create-start writes the epoch.** FromLocked/rerun-create-start writes the epoch via the same `lockApplyingWithEpoch` (the `spec.FromLocked` branch of `lockRun`) — the applying row gets a non-empty `applying_by_kid`/`apply_id`/`since` and falls under `reconcile_orphan_applying`. The residual micro-window between the UnlockForRerun-tx and the lockRun-tx (applied in two different txs of one request) degrades into the existing NULL-epoch known-gap (no worse than the current one) — full atomicity for this rare recovery-over-recovery class is not required.
>
>   - **NULL-epoch = known-gap.** The rule's candidate SQL filters `AND applying_by_kid IS NOT NULL` (in addition to `status='applying' AND applying_since < NOW()-stale_after`). A NULL-epoch (legacy/pre-082, or applying not via the S1 `lockRun`) is **NOT** reclaimed by the rule — a documented known-gap, fixed by a manual `Unlock` by the operator. A separate path for NULL-epoch is NOT introduced (without `applying_by_kid` there is no presence witness of death — a weaker fencing class, rejected, symmetrically to the presence invariant of amend (n)).
>
>   - **Reuse of `ReleaseApplyingOrphan` WITHOUT a signature change.** The rule calls the existing `ReleaseApplyingOrphan(ctx, pool, name, orphanApplyID, historyID)` as-is. `orphanApplyID` = the candidate's `incarnation.applying_apply_id` (non-empty by the filter + the atomic write; the `empty orphan apply_id` guard is unreachable; the Reaper additionally defensive-skips an empty one with a warn). `historyID` = `audit.NewULID()`, generated by the Reaper before the call (identically to the Voyage adapter). The `ReleaseApplyingOrphanByEpoch` wrapper is NOT introduced.
>
>   - **The standalone-path fencing set (normative).** (1) **presence-death** — `InstanceAlive(applying_by_kid)=false` (phase 2 of the rule; direct proof of death in Conclave, replacing the Voyage FENCING-3 `VerifyOwnership` — a standalone has no Voyage-claim, so do NOT call `voyage.VerifyOwnership`). (2) **FENCING-1 no-live-rival** — there is no active `apply_run` with `apply_id ≠ orphanApplyID` (inside `ReleaseApplyingOrphan`). (3) **single-winner CAS** `applying→ready` under `FOR UPDATE` + `status='applying'` (inside `ReleaseApplyingOrphan`). The Voyage analogue reclaimed-attempt (`run.Attempt>orphan`) does NOT apply — the Reaper has no re-run moment with an increased attempt; the witness of death = presence.
>
>   - **`applying_attempt` is NOT read for standalone release** (it is redundant: presence proves death, FENCING-1 fences by `apply_id`). The column is STILL written in `lockRun` atomically (parity with `apply_runs.attempt`, groundwork for a post-MVP epoch-check of `RunResult` receipt) — it is NOT a dead write.
>
>   - **The rule `reconcile_orphan_applying` — default-ON + presence-gate.** Enabled by default (path-defaulting, like `reclaim_voyages`), BUT a no-op without a live Conclave client (graceful, like `mark_disconnected` without Redis). `stale_after=90s` (parity with `mark_disconnected`). Phases: (1) SQL candidates via `incarnation_applying_scan_idx` (`status='applying' AND applying_since < NOW()-stale_after AND applying_by_kid IS NOT NULL`); (2) presence — `InstanceAlive(applying_by_kid)`, alive→skip; (3) defensive-skip of an empty `applying_apply_id`/`applying_by_kid` (warn+metric, unreachable with a correct `lockRun`); (4) release — `ReleaseApplyingOrphan` as-is. Metrics `keeper_reaper_*{rule="reconcile_orphan_applying"}`; the audit-event `reaper.reconcile_orphan_applying.executed` (area `reaper.*`, `source: keeper_internal`, payload `{incarnation, prev_kid, apply_id}`) is emitted on a successful release (per-row, like `voyage.reclaimed`).
>
>   - **Residual double-apply** — the same acceptable class as (l) and `reclaim_apply_runs`: a network partition of a live partitioned owner (presence holds → the rule does NOT touch it, fail-safe). Protection — gate-1 attempt-fencing `RunResult` + module idempotency.

> **Amend (n): presence-gated force-release of the SID-lease on a detected-crash reconnect (2026-06-21).** A backstop foundation (slice S0 — the server-side lease function + the presence primitive; the insertion into `acquireSoulLease` — slice S2). Extends the SID lease mechanics ([ADR-006(b)](0006-cache-redis.md#adr-006-cache-and-coordination--redis)).
>
>   - **Problem.** After a SIGKILL of the Keeper owner, the SID-lease (`soul:<sid>:lock`, [SoulLease](../keeper/storage.md)) lives until TTL (`defaultSoulLeaseTTL=60s`): the graceful `Release` did not get to run (crash). A reconnect of the SAME SID to a new Keeper gets `AcquireSoulLease@ErrLeaseTaken` → the stream is closed with `code.AlreadyExists`, and `handleWardRoster` (Soul-reconcile (g)) is **unreachable** for ~60s — the Souls are invisible for a window of almost a minute after the crash.
>
>   - **Why NOT a blind `DEL`.** Blindly removing someone else's lease undermines the SID-lease delivery dedup: with a network partition of a **live** holder (it still holds the stream to the Soul, it is just temporarily invisible to the reconnect-Keeper), a `DEL` + re-acquire produce **two** owners of one SID stream → double delivery of `ApplyRequest` / splitting of `RunResult`. The lease dedup rests on "one key — one owner"; a blind DEL breaks it.
>
>   - **Solution — a presence-gated CAS re-acquire.** On `AcquireSoulLease@ErrLeaseTaken`: `SoulLeaseOwner(sid)` → `prevKID`; `InstanceAlive(prevKID)` (Conclave, ADR-006(e)):
>     - **dead in Conclave** → `ForceAcquireSoulLease(sid, prevKID, myKID, ttl)` — a Lua-atomic CAS-**by-prev-holder**: re-acquire ONLY if the key is still `== prevKID`. If the key changed in a race (another Keeper already re-acquired / the Soul reconnected to a third) — a normal fail → `AlreadyExists`.
>     - **alive** (or a Redis error of the presence check, or a partition in which the Conclave presence of a live holder still holds) → we do NOT remove it, `AlreadyExists` as now (fail-safe toward preserving the current owner).
>   - **Boundary of the effect.** The invisibility window is reduced from the SID-lease TTL (`60s`) to the **Conclave-presence TTL of the dead holder** (`DefaultConclaveTTL=30s`) — NOT to zero: presence-death is detected only after the Conclave key of the crashed owner expires. This is a deliberate trade-off against split-brain (presence is the only reliable sign that "the owner is really dead, not partitioned").
>
>   - **Boundaries of S0 (this slice).** S0 provides only the server-side `ForceAcquireSoulLease` (Lua CAS-by-prev-holder) + the presence primitive `InstanceAlive` — **WITHOUT** the insertion into the `acquireSoulLease` handler (the presence-gated call on `ErrLeaseTaken` — slice S2). The release audit-event — `eventstream.lease_force_released` (name fixed; emission — S2).

> **Amend (o): a pre-flight assert gate BEFORE entering `applying` (2026-06-23, form A). Pilot.** Jointly with the [ADR-009](0009-scenario-dsl.md#adr-009-scenario--the-full-destiny-task-dsl-the-boundary-with-destiny-is-a-recommendation) amendment of the same date. Introduces a new **synchronous run phase BEFORE the apply_runs lifecycle** — it wedges into the request path BEFORE any mutation, without changing the apply_runs machine itself (`planned → claimed → dispatched → terminal`).
>
>   - **Where in the lifecycle.** The full `create` run chain: request `POST /v1/incarnations` → sync RBAC → sync `ValidateInput` (input schema) → **★ pre-flight assert (the new gate)** → `incarnation.Create` (commit the row) → `Runner.Start` (async) → `lockRun` (`status='applying'` + epoch, amend (m-S1)) → render → dispatch (`planned`→…). Pre-flight stands BETWEEN `ValidateInput` and `incarnation.Create`: the incarnation does NOT exist yet, the `applying` lock is NOT taken yet, and there is not a single `apply_runs`/`state_history` row yet.
>   - **What it does.** Synchronously evaluates the `create` scenario's `assert:` predicates ([ADR-009](0009-scenario-dsl.md#adr-009-scenario--the-full-destiny-task-dsl-the-boundary-with-destiny-is-a-recommendation)) in the full scenario-CEL context (the roster of connected-souls by the incarnation Coven = `soulprint.hosts`). Any `false` → **HTTP 422 `assert-failed`** to the operator (NOT `error_locked`): the incarnation is NOT created, `applying` is NOT set, the run does not start. This is a "fail at the model stage" — a rejection BEFORE entering the lifecycle, not a post-factum `error_locked` via an async render-abort.
>   - **Why it does NOT break ADR-027 invariants.** The gate does not touch the work-queue: it works on the request path BEFORE `Runner.Start`, before `lockRun`, before the apply_runs spawn. Single-winner state-commit (j)/(m), epoch-fencing (d)/(g), recovery (i)/(l)/(m) — all DOWNSTREAM, pre-flight does not touch them. On a pre-flight failure there remains neither an orphaned `applying` lock (amend (m): there was none) nor a hanging `apply_run` (amend (i): there was none) — the rejection is clean by construction (no mutation). Pre-flight is read-only to PG (a roster-query + a service-snapshot Load), without writing.
>   - **The render-assert fail-safe is preserved (TOCTOU).** Pre-flight validates the roster at the moment of CREATION; between it and the start of the scenario-goroutine the roster could change. The render `assert:` branch at run start remains a safeguard: its failure = `error_locked` via the same async-abort described originally in ADR-009. Pre-flight = the main UX (422, frequent), render-assert = the fail-safe (a rare `error_locked`).
>   - **The pilot scope — only the `create` path.** `incarnation.run` (on an existing one) / `destroy` / Voyage-spawn — follow-up; for them the render-assert fail-safe is so far the only gate. **★ Superseded for `incarnation.run` 2026-07-28 ([ADR-009 amendment / NIM-270](0009-scenario-dsl.md#amendment-2026-07-28-nim-270-the-pre-flight-gate-moves-to-where-the-roster-is-real)):** the gate now also stands on the explicit-run request path, between `ValidateInput` and `Runner.Start` — the ONE place a topology assert can actually be answered, since the incarnation exists there and its roster is bound. Same lifecycle argument as the create-path bullets above, one step later: before `lockRun`, before the apply_runs spawn, read-only to PG, so a rejection leaves neither an `applying` lock nor a hanging `apply_run`. `destroy` / Voyage-spawn remain follow-ups. Implementation — `keeper/internal/scenario` (`Runner.PreflightAssert`), `keeper/internal/render` (`Pipeline.EvalAsserts`, a shared eval with the render branch), `keeper/internal/api/handlers/incarnation_typed.go` (`CreateTyped`), `keeper/internal/api/problem` (`TypeAssertFailed` 422).
>   - **★ Narrowed 2026-07-28 (NIM-235): at this point in the chain the roster does not exist.** "The roster of connected-souls by the incarnation Coven" in **What it does** was true while `souls.coven[]` carried `incarnation.name`; [ADR-008 amendment 2026-07-17 (NIM-124)](0008-coven-stable-tags.md#amendment-2026-07-17-nim-124-incarnationname-is-not-a-coven--membership-is-a-first-class-relation) moved membership to a relation that FKs the incarnation row — the row this gate deliberately stands **before**. So the gate sits at the one point in the chain where `soulprint.hosts` is structurally unavailable, and a topology predicate there rejected every create rather than measuring anything. Roster-reading asserts are therefore deferred to the render fail-safe (the bullet above), and the gate keeps only the asserts it can answer — those reading `input.` / `essence.` / `incarnation.`. The lifecycle position of the gate is UNCHANGED, as is everything in **Why it does NOT break ADR-027 invariants** (it stays read-only to PG; it now issues one existence check in addition to the roster query). Full reasoning and the follow-up that restores the promise on the run path — [ADR-009 amendment 2026-07-28](0009-scenario-dsl.md#amendment-2026-07-28-nim-235-a-roster-reading-assert-has-no-pre-flight-point-at-create).

> **Amend (p): the work-queue learns steps — one `apply_runs` row per step per host (linear dispatch, NIM-960, 2026-10-06). Forks (c) and (d) decided by the user 2026-10-06: (c)(ii) and (d)(ii).** [draft-scenario-linear-barrier](draft-scenario-linear-barrier.md) makes every multi-step run write one row per step per host (`passage` = the step index), and decision NIM-945 (option A) restores this path for linear runs before linear dispatch is enabled (that ADR's item 7). Today the run goroutine takes the path only for a one-Passage run of the staged model (`keeper/internal/scenario/run.go:684`, `staged` at `:451`) — a linear run never, one step included, until NIM-961 renders a step at claim time — so the queue has never held a second row for a host. (The Oracle enqueuer writes a `planned` row for any scenario, with no run goroutine at all — (f).) The schema already carries the triple — the PK is `(apply_id, sid, passage)` since migration 078 — and on the receive side the terminal, the failure record, the notices and the `RunResult` correlation already address it (`updateStatusSQL` in `keeper/internal/applyrun/crud.go`, `keeper/internal/grpc/events_runresult.go:76`). The claim side did not; it is listed below, as it was before NIM-960 and as NIM-960 builds it. Code that NIM-960 changed is cited by symbol, the rest by line. This binds the ADR-056 amendment above ("the exact binding — slice S4 of ADR-056"), which ADR-056 never built, and narrows its "the model does not change": under (c) either the Soul's fencing key or the meaning of `attempt` changes, and under (d)(i) a linear run's rows take statuses of their own.
>
>   - **(a) Invariant: at most one non-terminal row per `(apply_id, sid)`.** The run goroutine writes step *k+1*'s rows only after step *k*'s barrier has closed, as `dispatchPlanned` writes Passage 0 today and then waits on it (`keeper/internal/scenario/dispatch.go:263-288`). Everything below leans on it: the claim needs no "current step" filter, the epoch in (c)(ii) is well defined, and (e) holds. The dispatch loop that writes step rows (NIM-961) must keep it and pin it with a guard test of its own; the queue's guards assume it. One obligation follows for the barrier: `classify` returns on the first failed host while that step's other rows may still be live (`keeper/internal/scenario/dispatch.go:845-856`) — safe today only because the run then aborts. Under `on_failure: host` the step barrier must wait for every row of the step to be terminal before the next step's rows are written (NIM-948), or (a) breaks.
>
>   - **(b) Five statements, and the claim path that calls them, were keyed by the pair; NIM-960 keys them by the triple.** They live in `keeper/internal/applyrun/crud.go`, `keeper/internal/reaper/purger.go` and `keeper/internal/scenario/claim.go`; each item says what the code did and what it does now.
>     1. **`claimNextSQL`.** The inner `SELECT` picked pairs and the outer `UPDATE` had no status filter, so with step 0 `success` and step 1 `planned` on one host both rows moved to `claimed`. The pair-keyed mark (2) then moved both to `dispatched`, saw two rows where it expects one and reported `ErrApplyRunNotClaimed`: nothing was sent, step 0's `success` was gone, and the barrier waited out the run. Re-keying the mark alone would have been worse: both claimed rows scanned as step 0, so one of them would go out, on the step-0 row. `RETURNING` did not carry `passage` and `scanClaimedRow` did not read it, so every status the claim path wrote landed on the step-0 row. Now the pick returns the triple, the `UPDATE` matches it **and** `status = 'planned'` — either filter alone keeps step 0 out, so each covers the other — and `RETURNING` and the scan carry `passage`. The pick is a `MATERIALIZED` CTE joined by `UPDATE … FROM`: written as `IN (subquery)` with the triple and the status filter, the batch limit stopped holding — a batch of 2 claimed 5 (`TestIntegration_ClaimNext_BatchLimit`) — consistent with the planner re-running the locking pick per row, each run skipping the rows the statement had already updated.
>     2. **`markDispatchedSQL`** and its probe: the triple, and the claim's `attempt`. The filter was `status = 'claimed'` alone, a hole that predates steps: an Acolyte whose Ward was reclaimed and re-claimed by another one (attempt 2) still marked the row it no longer owned and sent attempt 1; the new owner's mark then failed and it sent nothing; the Soul ran attempt 1, and the receive check dropped its result as stale (`keeper/internal/grpc/events_runresult.go:103-114`). The row stayed `dispatched` with no result coming, and the barrier waited out the run. Now a mark at another attempt is refused as `ErrWardLost`, so only the current owner hands the task off. Reachable only with `reclaim_apply_runs` enabled (default off).
>     3. **`selectCancelRequestedSQL`**: the triple. `QueryRow` over two rows read either, and a terminal step-0 row holds `false` — `RequestCancel` flags non-terminal rows only — so a Cancel issued during step 1 could read as "not requested" and step 1 was sent.
>     4. **`reclaimApplyRunsSQL`**: the same shape as the claim. It returned to `planned` every row of the pair, terminals of earlier steps included, and the next claim executed them again. Now the triple, and `status = 'claimed' AND claim_expires_at < NOW()` on the outer `UPDATE`. The outer filter also closes a race that predates steps: the inner `SELECT` locks nothing, so a row that a `MarkDispatched` committed after the reclaim statement took its snapshot is re-checked only against the outer condition — which did not look at the status — and a `dispatched` row went back to `planned`, to be sent again (`TestIntegration_ReclaimApplyRuns_RowDispatchedMidStatementStays`).
>     5. **`insertPlannedSQL`** did not write `passage`, so every planned row was step 0. It writes `run.Passage`.
>     6. **The claim path's own writes and its request.** Its status writes went through `updateStatusSQL` with no epoch: an Acolyte that lost its Ward and then failed a slow render wrote `failed` over the new owner's row — even a `dispatched` one the Soul was applying — and the host's real result became a no-op. Now they go through `UpdateWardStatus`: the step row, the claim's `attempt`, and a live claim phase — `claimed`, or `dispatched` for the write after a failed send — with `ErrWardLost` for "fenced out", which `UpdateStatus` would report as "already terminal". The status filter is needed beside `attempt` because reclaim keeps `attempt` (`keeper/internal/reaper/purger.go:343-347`), so a reclaimed row not yet re-claimed still carries the stale owner's epoch. No row is left open by the fence: a fenced-out writer has lost the row — it is `planned` again, and the next claim renders it once more, or a newer owner holds it — and the run's abort sweep (`keeper/internal/scenario/run.go:1558-1581`) stays unfenced. Like (2), reachable only with `reclaim_apply_runs` on. The `ApplyRequest` it built set no `Passage`, so the Soul echoed 0 and step *k*'s `TaskEvent`s and `RunResult` landed on the step-0 row and closed nothing; it sets `run.Passage`.
>
>     Unchanged, and why: `updateStatusSQL`, `recordTaskFailure`, `appendRunNotices`, `SelectIncarnationByApplyID` already take the triple; `orphanDispatchedSQL` — (e); `selectByApplyIDSQL` is pair-keyed, but only tests call it. **`requestCancelSQL` is not the queue's to fix, and not fine either.** It flags `planned`/`claimed`/`running` rows: `dispatched` is out by design (amend GATE-1 (f)), and between two steps a host has no non-terminal row at all. A Cancel that reaches an instance other than the run's owner in that gap flags nothing, `Runner.RequestCancel` answers "not found" (`keeper/internal/scenario/runner.go:149-168`), and the Cancel is lost. Staged runs have the same gap between Passages today; linear dispatch gives it to every run on both paths, so it belongs to the linear loop (NIM-944). Closed by amend (r) (NIM-972): the Cancel is flagged on the run's applying lock as well.
>
>   - **(c) The fencing epoch across steps — decided: (ii) (user, 2026-10-06).** The Soul fences by `apply_id` alone: `AcceptAttempt` rejects `attempt < lastSeenAttempt[apply_id]` and the rejected request is dropped with no `RunResult` (`soul/internal/runtime/applyrunner.go:233-255`, `soul/cmd/soul/main.go:1269`). Each step row starts at `attempt = 0`, and before NIM-960 its first claim made it 1. So once step *k* was reclaimed and delivered as attempt 2, step *k+1*'s first delivery (attempt 1) would be dropped, and its barrier would wait out the run (`scenario_timeout`, 24h by default, in a linear run since NIM-949; five minutes in a staged one, `keeper/internal/scenario/scenario.go:141`). Only `reclaim_apply_runs` returns a row to `planned`, so this needs the rule on (default off) — which is the point of restoring the queue. The receive check is not the problem — it already compares against the row's own `attempt` (`events_runresult.go:76`, `:103-114`).
>     - **(i) The Soul fences by `(apply_id, passage)`.** `ApplyRequest` already carries `passage` (`proto/keeper/v1/apply.proto:300`), so the proto does not change; `lastSeenAttempt` is re-keyed and `ActiveSet` (`applyrunner.go:297-340`) still reports one entry per `apply_id`. An older Soul keeps fencing by `apply_id` and drops steps, so this needs a **new capability bit** (a name — propose-and-wait), and a host without it cannot take queued steps after the first — the run is refused, or sent inline. The blast radius is the one §Before merge item 8 of the linear ADR names: one old Soul takes its whole run off the queue. `attempt` keeps its meaning, "how many times this row was claimed".
>     - **(ii) The Keeper keeps `attempt` monotonic per `(apply_id, sid)` across steps.** The claim sets `attempt = (SELECT MAX(h.attempt) FROM apply_runs h WHERE h.apply_id = r.apply_id AND h.sid = r.sid) + 1` instead of `r.attempt + 1`. Under (a) the host's earlier rows are terminal when step *k+1* is claimed, so its first attempt is above every epoch the Soul has seen for this `apply_id`; a re-claim of the same row still grows it. The Soul does not change, and every Soul in the field already fences correctly. The subquery reads the PK prefix — no new index. Price: on a step row `attempt` stops meaning "claims of this row" and means "this host's epoch in this run" — the runs API exposes it, and its description says so (`RunHostStatusEntry.Attempt`, `shared/api/wire/incarnation.go`). `GREATEST(r.attempt, …)` floors the `MAX`, which reads the statement's snapshot even when a concurrent claim and reclaim of the row force a re-check. A step sent inline carries `attempt = 0`, which the Soul accepts without recording (`applyrunner.go:235-237`), so mixing inline and queued steps in one run is safe. Built in `claimNextSQL`; `TestIntegration_Steps_FirstClaimOutranksEveryEarlierAttempt` pins it.
>
>   - **(d) Keeping a Keeper that does not know steps off the queue — decided: (ii) (user, 2026-10-06).** During a rolling upgrade, or a rollback, an older Keeper's Acolyte claims any `planned` row (`claimNextSQL` before (b)) and renders the host's whole scenario (`RenderForHost`, `keeper/internal/scenario/claim.go:120`): it would send every task of a linear run in one message — silently, the very thing item 15 of the linear ADR forbids. If it is the Reaper leader with `reclaim_apply_runs` on, its pair-keyed reclaim reopens earlier steps' terminals.
>     - **(i) Statuses the older SQL does not select.** A linear run's rows take two new non-terminal statuses for the waiting and the claimed phase. One is not enough: an older Reaper leader returns any expired `claimed` row to `planned`. Cost: a migration (drop and recreate the `CHECK`, as 040/044/045 did) and a partial index for the new claim scan (025's `apply_runs_claim_scan_idx` covers `planned`/`claimed`/`running`); every reader of the status learns them — `ValidStatus` (`keeper/internal/applyrun/applyrun.go:86-88`), the barrier's `classifyExcept` (`dispatch.go:834-857`), the abort's terminal sweep (`keeper/internal/scenario/run.go:1558-1581`, whose `default: continue` would leave the new rows open for good), `AggregateRunStatus` (`keeper/internal/applyrun/runsview.go:143`), and through it the Voyage awaiter (`keeper/cmd/keeper/daemon.go:5953-5965`), the source-status guard of `updateStatusSQL`, `requestCancelSQL`, and the web UI; two new names (propose-and-wait); and the same phase is spelled two ways depending on the run's model. `dispatched` and the terminals stay shared, so an older Keeper that receives a step's `RunResult` commits it correctly — it correlates by the triple since ADR-056 S1. In any version mix an older Keeper never claims, renders or reclaims a step row; what it still cannot do is flag one for Cancel — its `requestCancelSQL` does not know the new statuses.
>     - **(ii) The Conclave says what each instance can do, and the queue is used only when every live one can.** An instance's Conclave record was `{started_at, kid}` — no version, no capability. It now carries a list, `capabilities`, and `conclaveMeta` writes `step_queue` into it (`keeper/cmd/keeper/daemon.go:2954-2968`; names chosen by the user, 2026-10-06); an older instance's record lacks it — as does a bare-KID record, the marshal fallback — and reads as "cannot". `AllLiveHaveCapability` (`keeper/internal/redis/conclave.go:287`) reads every live record and answers true only when each lists the capability — false for an empty registry and, with the error, when Redis does not answer. Before writing a step's rows the run goroutine asks it — that call, with the choice of which steps go through the queue, is NIM-961's — and if the answer is no, that step goes inline — the path staged and `serial:` runs take today, on the same clusters. That path is declared single-keeper-only (`keeper/internal/scenario/dispatch.go:594-600`, `:629-637`); NIM-945 §3 holds the declaration stale but unverified, and NIM-961's HA e2e settles it. The fallback inherits that open question, as (c)(i)'s does. Checked per step, not once per run, so an older instance that appears mid-run keeps the run's later steps off the queue for as long as it is live. No migration, no status. Residual: an older instance that registers after the check can claim that step's rows and, if it holds the Reaper lease with reclaim on, reopen the host's earlier rows, for as long as the step lasts; a live instance whose presence key lapsed for a moment (30s TTL, renewed every 10s) is invisible to the check; and an instance with no Redis never registers in the Conclave at all (`keeper/cmd/keeper/daemon.go:2833-2836`) yet still runs Acolytes by polling (`:5215-5234`) — invisible for good. An HA cluster with one Redis-less instance is already broken (the SID lease, delivery), but nothing refuses it. A refusal at startup instead of the per-step check would forbid rolling upgrades of an HA cluster outright. `step_queue` is written from NIM-960 on but means the whole step path, rendering a step on claim (NIM-961) included; nothing built between the two ships, since the release train reaches `main` only at NIM-952.
>
>     One fact bears on both: an older Keeper cannot start against a schema with a migration it does not know — golang-migrate refuses an unknown database version (`no migration found for version N`) and the daemon exits (`keeper/cmd/keeper/daemon.go:744-747`). So once a migration is applied — (i)'s own, or any other the release carries — a rollback brings in no new older instance, and what remains is the older instances still running during the rolling upgrade itself. Under (ii) that holds only if the release carries a migration.
>
>   - **(e) Soul-reconcile stays keyed by `apply_id`.** `orphanDispatchedSQL` (`keeper/internal/applyrun/crud.go`) orphans a host's `dispatched` rows whose `apply_id` the Soul did not declare. The Soul executes one `ApplyRequest` at a time — its apply worker runs them in order, off the receive loop since NIM-949 (`soul/cmd/soul/applyworker.go:276`), and tracks the run by `apply_id` (`applyrunner.go:427-430`) — and under (a) a host has at most one `dispatched` row per run, so the `apply_id` names it. `TestIntegration_Steps_OrphanDispatchedTouchesOnlyTheOpenStep` pins it: step 0 `success` and step 1 `dispatched` on one host; a roster without the `apply_id` orphans step 1 only, a roster with it orphans nothing. **Known gap:** the Soul keeps a finished `apply_id` declared for 30s (`recentlyFinishedTTL`, `applyrunner.go:151`), so if a Keeper dies between marking step *k+1* `dispatched` and sending it (window W-a, amend GATE-1 (b)) and the Soul reconnects within 30s of finishing step *k*, the undelivered step is not orphaned on that reconnect. Closed by NIM-949: `ActiveApply` carries `passage`, a Soul declares each message by it, and the sweep spares only the rows named; an older Soul's entry, without one, still claims the whole `apply_id`.
>
>   - **(f) Not in this amendment.** Rendering a step on claim and deciding which steps go through the queue (NIM-961); a push host (still refused on this path, `dispatch.go:257-259`); a run surviving its own Keeper (Phase 3 / W2). The barrier and the run's terminal stay in the run goroutine, as in Phase 1. **The Oracle path** writes one `planned` row for any scenario, with no run goroutine, no barrier and no step loop (`keeper/cmd/keeper/oracle_enqueuer.go:96-113`), and `RenderForHost` knew no step (it does since amend (q)). Under linear dispatch an Oracle reaction would send a multi-step scenario in one message — what (d) keeps an older Keeper from doing — and nothing would write its next step. Before enabling, the path either refuses a multi-step scenario or gets a step loop (NIM-961; moved to NIM-977 by amend (q)). Defects the review of this amendment found outside the queue, owned elsewhere: the Voyage awaiter reports success once every *existing* row is benign (`keeper/cmd/keeper/daemon.go:5953-5965`), and the runs API reports the run `success` with `finished_at` set (`runsAggregateSelect`, `keeper/internal/applyrun/runsglobal.go:119`; `AggregateRunStatus` at `runsview.go:143`), and on the Voyage path (amend (l), `keeper/cmd/keeper/daemon.go:5903`) FENCING-1 of `ReleaseApplyingOrphan` looks for a non-terminal row of another run of the incarnation (`keeper/internal/incarnation/crud.go:1355-1361`), so between one step's barrier and the next step's rows a run reads as finished, and on that path a live run's `applying` lock can be released as an orphan's (the standalone rule of amend (m) is not exposed: it excludes the lock holder's own run and acts only on a dead owner) — whether the step is queued or inline, as a staged run does between Passages today (NIM-944) — the awaiter, the runs API and FENCING-1 are closed by amend (r) (NIM-972); the per-host history timeline lists one entry per step under one id (`keeper/internal/soul/history.go:139-146`, NIM-936).

> **Amend (q): a linear run's step goes through the queue (NIM-961, 2026-10-08). Two choices decided by the user 2026-10-08.** This discharges what amend (p) left to NIM-961: rendering a step at claim time, choosing which steps are queued, and the guard of (p)(a). Code is cited by symbol.
>
>   - **The run goroutine decides a step's hosts (user: option (i)).** The goroutine renders every step anyway, because a step's `when:` and its post-module predicates are settled on the Keeper ([draft-scenario-linear-barrier](draft-scenario-linear-barrier.md), decision 4). So it settles the hosts before it writes anything:
>     - a host the step does not target gets no row;
>     - a host whose tasks are all skipped, or that failed before dispatch, is closed by the goroutine as on the inline path;
>     - only a host with something to send gets a `planned` row (`Runner.dispatchStepPlanned`) — since NIM-949 only once its agent stream is there: the claim sends at once, so a host with no stream waits in the goroutine, up to `soul_timeout`, before its row is queued ([settings.md §2.2](../scenario/settings.md); user, 2026-10-08).
>
>     The rejected option (ii) wrote `planned` rows for the whole roster at every step and let each claim close an untargeted host as `no_match`, as the one-Passage path does (`Runner.dispatchPlanned`). Its cost was T×N claims, each rendering the full roster; a per-step run view that differs by path; and `no_match` rows that `tolerate: "N%"` (NIM-948) would have to place in or out of its denominator. Under (i), a claim whose render disagrees with the goroutine's refuses the host instead (below), so a step row is not closed `no_match` by a disagreement. The claim's NIM-56 branch still closes a host in status `destroyed` as `no_match`, but nothing has written that status since NIM-761.
>   - **The claim reproduces the goroutine's render rather than deciding again.** A step row's recipe carries `step` (`applyrun.RecipeStep`). It holds four things: the run's roster as SIDs; the default blocks' held hosts (`render.HeldTargets`, NIM-942); the plan-index → register-name map the goroutine used to read the earlier steps' registers; and the plan indices of the tasks the run decided to send this host. These are host identifiers, names and indices only, nothing rendered, so invariant A (f) holds. The recipe's `ServiceRef.Ref` is the commit the run loaded, so the service repo cannot hand a later step a different plan when its branch moves mid-run.
>     - `RenderForHost` with a `step` renders the step's pass: the step shape from `config.LinearPassage`, `ActivePassage` set to the row's `passage`, and the registers the earlier steps wrote (`loadRegisterByHostUpToPassage`). Its roster is the run's: the incarnation's members whatever their presence (`topology.Resolver.LoadIncarnationMembers`), narrowed to the recorded SIDs. A host that lost its lease is still in it, as it is in the run's roster until the next refresh boundary, and a host that joined since is not, so it cannot take a `run_once:` the run gave another host.
>     - The claim then settles its own host as the goroutine does (`ClaimRunner.settleStep`: `settleHosts`, with the cross-step requisite gate over the audit log). **It sends only if it arrives at exactly the tasks the row names.** Otherwise it refuses the host as `failed`, sends nothing, and names both task lists in the summary. The case is two renders that disagree on which tasks the host is sent: a `run_once:` or a `where:` that moved because a host was revoked or removed since, a fact that moved, or a destiny on a branch that changed shape (next item). Failing closed puts no task on a host that the run did not decide. Such a refusal breaks the step's barrier at once, as a host that fails on the Soul does. The records of the tasks the host is not sent are written after `MarkDispatched`, which is the fence.
>     - What the check does not see: content. A destiny resolved from a branch is not pinned; every claim resolves it again. If it changes without moving a plan index, the claim sends the new content. The roster's facts — membership, covens, Voice role, soulprint — are read at claim time too: a host revoked since drops out of `soulprint.hosts` without changing which tasks are sent, and that change goes through. The check compares plan indices only, so it cannot tell a grouped child sent running from its `when: false` copy; no group reaches the queue today (a group carries `serial:`), and distributed serial (Phase 3) has to extend the check before one does. The claim also renders without the run's seal set (`Sealed`, `SecretStateFields`), so its error text is masked by the vault and regex layers only, as the one-Passage claim path does. The claim's `vault()` memo is also its own, because NIM-934's run memo lives on the goroutine's instance. A queued step therefore reads the earlier steps' secrets from Vault again, once per claim. A secret that is deleted or rotated outside the run fails that claim, where the inline path would still serve the remembered value.
>     - A row without `step` (a staged run's, or the Oracle's) renders the whole scenario, as before.
>   - **Which steps are queued (`Runner.queuesStep`).** A step is queued only when all four hold: this instance runs Acolytes; the step carries no `serial:` (distributed serial is Phase 3); it sends to no `transport: ssh` host; and every live instance lists `step_queue` (asked per step, (p)(d)(ii)). Otherwise that step goes inline, and the next step asks again. `Deps.StepQueue` is that question, and without Redis there is no one to ask. **A step that sends to a push host goes inline as a whole (user, 2026-10-08).** It is not split between two paths under one barrier, and it is not refused: refusing would regress multi-step runs with push hosts, which go inline today. A linear run never takes the one-Passage branch, so that branch's push-host refusal (`keeper/internal/scenario/run.go:697-702`) keeps applying to staged runs only.
>   - **(p)(a) is kept and pinned.** The goroutine writes step *k+1*'s rows only after step *k*'s barrier closes. A host the Keeper failed before sending does not break that barrier until the hosts queued beside it finish, as in one inline wave. `TestIntegration_LinearRunStepsAcrossInstances` runs one instance that owns a three-step run and two others that claim its rows, sharing nothing with it but PG; it fails if a step is sent while the step before it still has a live row.

> **Amend (r): a run between its steps is read from its applying lock (NIM-972, 2026-10-08). The user chose 2026-10-08 to carry the Cancel on the lock, with a migration.** Closes what (p)(b) and (p)(f) left to the linear loop. A run's rows do not say that it is alive. Before its first row (artifact load, first render, gates) it has none, and between one step's barrier and the next step's rows every row it has is terminal. A keeper step holds a `running` row of its own (`sid = keeper`, `keeper/internal/scenario/keeper_dispatch.go:75-80`), so that window is render, gates and roster refresh. The applying lock is held for the whole run: `lockRun` writes `applying_apply_id` in the same `UPDATE` as `status = 'applying'` (`lockApplyingWithEpochSQL`, `keeper/internal/scenario/state.go`), and the run's single terminal clears it (amend (m-S1)). Three readers now read it.
>
>   - **(a) The Cancel.** Migration 121 adds `incarnation.applying_cancel_requested` and a partial index on `applying_apply_id`. `Runner.RequestCancel` flags the lock (`incarnation.RequestRunCancel`, matching `applying_apply_id = $1 AND status = 'applying'`) beside the rows, whose flag the Acolyte still reads before it sends; `found` is true when either was flagged. The owner reads both in every barrier poll — `waitBarrierExcept` (`keeper/internal/scenario/dispatch.go`) for a staged run, `Runner.waitStep` (`keeper/internal/scenario/failure_policy.go`, NIM-948) for a linear one, inline or queued; both defer the lock's flag as described below — and at each step's boundaries (`stepCancelRequested`, `dispatch.go`): before its keeper tasks, before its hosts are sent it, and, for a linear run, at its end — a linear step that goes through the queue (amend (q)) included, since `dispatchStepPlanned` is reached through `dispatchPassage`; on the one-Passage work-queue path, before the keeper tasks and before `dispatchPlanned`. The barrier defers the lock's flag while a row of the run is `dispatched` and none is `planned` or `claimed` (`onlyDispatchedOpen`; a work-queue run holds no `running` row while its barrier polls, and since NIM-949 neither does an inline linear step, whose rows are written `dispatched` with the send — so a Cancel of a linear run waits for its step's hosts on either path): acting there, the abort would close the `dispatched` rows as `cancelled` while their Souls apply them and drop their results — what GATE-1(f) keeps out until the Keeper can send `CancelApply`. Once none is `dispatched`, the next poll acts on it: the delivered rows keep their results, and the run stops instead of committing. With a row not yet delivered (`planned`/`claimed`) it acts at once, which is what a row flag always did: a Cancel landing while the work-queue path writes its rows leaves them unflagged, and deferring would let an Acolyte send them after the Cancel was reported found. The abort's sweep is the base one — on a Cancel it closes `planned`/`claimed`/`dispatched` rows and leaves `running` ones — so a Cancel that acts beside an undelivered row still closes the `dispatched` rows and drops their results, as before. So does the local fast path: `Runner.Cancel` on the owning instance cancels the run's context, which the sweep does not take for an operator Cancel, and `running` rows are failed too — unless a barrier poll read the flag first. Before, a Cancel of a run whose rows were all `dispatched` flagged nothing and the run committed. The flag means something only while the lock names the run. `lockRun` resets it and the release paths do not, because a Keeper older than migration 121, still running during a rolling upgrade, releases the lock without knowing the column. No operator surface calls `Runner.RequestCancel` today — neither HTTP, MCP nor the Voyage cancel — so this makes the mechanism correct for the surface that will.
>   - **(b) The run status.** `AggregateRunStatus(statuses, lockHeld)`: a run whose lock is held is `applying` whatever its rows say, and has no `finished_at`. Each fold reads the rows and the lock in one statement, through a join on `incarnation` (`runLockHeldSQL`, `keeper/internal/applyrun/runsview.go`): the global list and its counters (`runsAggregateSelect`), the incarnation's run list, the run detail, and `SelectRunStatus`, which the Voyage awaiter polls instead of folding `SelectStatusesByApplyID` (`pollOutcome`, `keeper/cmd/keeper/daemon.go`). One statement, because two reads let a run finish between them: rows read between steps, then a lock already released, would fold to `success` a run whose later step failed.
>   - **(c) The outcome of a run aborted between steps.** A Cancel, a render failure, a gate refusal or a roster refresh failure there left only the earlier steps' `success` rows, so once the lock was released the run read `success` to the runs API and to the Voyage. `ensureTerminalApplyRun` now writes the run sentinel row (`render.RunSentinelSID`, as for an early abort) whenever no row would carry the abort (`carriesAbort`, `keeper/internal/scenario/run.go`) — which also covers a Cancel that leaves `running` rows to finish and to report `success`. The abort writes the rows before it releases the lock (`lockIncarnation`): released first, the run read `success` until the sentinel landed. The sentinel is inserted with `finished_at` set (`insertSQL`), or the run read unfinished forever and `purge_apply_runs` never removed it — true of an early abort's sentinel before.
>   - **(d) FENCING-1 of (l).** `ReleaseApplyingOrphan` reads `applying_apply_id` under its `FOR UPDATE`; a lock that names another run is that run's, and the release is refused. The row check stays, for a lock with no epoch (legacy, or the `UnlockForRerun` → `lockRun` window) and for a rival that has rows and no lock (the Oracle path). The standalone rule of (m) releases with the lock's own `apply_id`, so the new check never refuses it.
>   - **(e) Not covered.** A `destroy` run holds `destroying`, which carries no epoch (`lockRun`, and the invariant "not applying ⇒ epoch NULL" in `UpdateStateFromRun`): between its steps the runs API still reads it by its rows, and a Cancel of it in that window is lost — a known gap, by the user's decision of 2026-10-08. Under linear dispatch it is lost during a step as well while the step's open rows are all `dispatched` — a stream host's on either path since NIM-949 — since the row flag skips `dispatched`: a Cancel of a linear `destroy` run then flags nothing until the step ends. A push host's `running` row is flagged, and the Cancel acts at once. No surface calls `RequestCancel` yet; this matters once one does and the run executes linearly (`keeper.yml` `scenario.execution_model: linear`, NIM-950; the default from NIM-952). A run whose Keeper dies between steps reads `applying` until `reconcile_orphan_applying` releases its lock, and `success` after, since the release writes no row. A lock with no epoch is read by rows, as before. A run whose own terminal write failed (`lockIncarnation` or the success commit on a PG error) keeps its lock with a live owner, so it reads `applying` and its Voyage target waits until the owner restarts and the lock is reclaimed — the incarnation itself is locked for that long anyway; the rows used to say `failed` or `success` and let the Voyage move on to an incarnation it could not run. `found` from `RequestCancel` means "recorded": a request landing after the owner's last read of the lock is not acted on. Two narrow windows stay: the Acolyte reads its row's flag only, so a Cancel landing between the owner's last check and the rows' insert can still be sent by an Acolyte whose `dispatched` mark lands before the barrier acts — the barrier then stops the run once that row has its result, which the row keeps — unless the barrier's poll saw a row not yet delivered, that row itself included, in which case the abort closes the row as `cancelled` while its Soul applies it; and the abort decides on the sentinel from rows read before its sweep, so a row whose result lands in between can leave no row carrying the abort. If reading the rows or writing the sentinel fails (logged), the abort still releases the lock and a run aborted between steps reads `success` — holding the lock instead would leave the incarnation `applying` under a live owner. `UpdateStateFromRun`, the terminal that clears the epoch, matches on the status and not on `applying_apply_id` (amend (m)'s residual): an owner that lost its lock in a split brain and then aborts clears the lock of the run that took it, and every reader here then takes that run for finished.
>   - **Guards.** `keeper/internal/scenario/between_steps_integration_test.go` holds a linear run between its steps, and before its first row, and asks each reader there, with the Cancel sent from an instance that does not own the run; the work-queue path and a stale flag left by an older Keeper have their own.
