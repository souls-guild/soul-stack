# ADR-033. Errand — pull-ad-hoc exec outside a scenario.

**Context.** The pull stack (ADR-002, ADR-012) can apply a scenario to an incarnation; the push stack (ADR-032) can do ad-hoc multi-host destiny over SSH. **Pull-ad-hoc exec of a single command through an already-running Soul agent** (uptime / cat /proc/… / status of a specific service / one-off shell fix) falls outside both branches: the incarnation/scenario scaffolding is redundant here and semantically wrong (incarnation.state is not mutated), and push over SSH requires credentials and bypasses the already-trusted mTLS channel. We need a **separate pull-ad-hoc path**: "invoke a single module on a specific SID through EventStream and get the result back."

**Decision.**
1. **Entity — `Errand`** (transl. "an errand / a one-off task"). Operator → Keeper → a specific Soul → a single module with a restricted input → result back. **NOT a scenario, NOT an apply, NOT incarnation-bound.** The name is fixed via propose-and-wait.
2. **Module whitelist — capability + list.** The Soul-side Errand runner calls `SoulModule.Apply` **only** if the module satisfies one of:
   - the hard-coded list `core.cmd.shell` / `core.exec.run` (verb modules, by design they do not mutate incarnation.state);
   - exact state `core.http.probe` (the read-only state of a mixed module; its sibling `request` mutates and is default-deny);
   - implements the marker interface `ErrandReadSafe` in sdk/module/ (by analogy with PlanReadSafe from ADR-031(f), default-deny).
   Any other module → reject BEFORE the call with error code `errand_module_not_allowed`.
3. **Sync/Async — hybrid.** POST /v1/souls/{sid}/exec blocks up to timeout_seconds (default 30s, server-cap 300s). On cap → 202 + errand_id + Location: /v1/errands/{errand_id} + continuation in a background goroutine. GET /v1/errands/{errand_id} — async polling.
4. **State invariant.** **Errand does NOT mutate incarnation.state.** Structurally: (a) whitelist (shell/exec do not write to state; ErrandReadSafe modules declare read-safe semantics); (b) the Errand runner does NOT send a RunResult (instead — a separate ErrandResult), and since [ADR-0084](0084-explicit-state-capture.md) retired the `state_changes` aggregate the write point is a keeper-side `core.state.<verb>` task, which an Errand never dispatches — it runs host-side modules only; (c) the Incarnation is not touched at all (no apply_id in apply_runs, no state-commit by the Keeper).
5. **RBAC — its own area `errand.*`.** Permissions: `errand.run` / `errand.cancel` (post-MVP) / `errand.list`. Selectors: `host=<sid>` / `coven=<label>`; bare — unrestricted scope.

**Contract.**

| Endpoint | Method | Body | Response |
|---|---|---|---|
| `/v1/souls/{sid}/exec` | POST | `{module, input, timeout_seconds?, dry_run?}` | sync: 200 + ErrandResult; async escalation: 202 + {errand_id} + Location: |
| `/v1/errands/{errand_id}` | GET | — | 200 + ErrandResult or 202 + {status: running} |
| `/v1/errands` | GET | filter `sid=`/`status=`/`started_after=` | 200 + {items[]}, RBAC filter |

- `module` — fully-qualified `<ns>.<name>.<state>` (core.cmd.shell / core.exec.run / other read-safe ones).
- `input` — a JSON object, validated against the module's input_schema (the input-validation phase, templating.md).
- `timeout_seconds` — `1..300`, default 30.
- `dry_run` — bool, only for modules with `PlanReadSafe`. A **verb-shell** module (`core.cmd.shell` / `core.exec.run`) is refused by Keeper with `400 malformed-request`, naming the module, before dispatch (Amendment 2026-08-08). Any other module lacking `PlanReadSafe` — `core.http.probe` included — Keeper admits and the Soul answers `FAILED errand_dry_run_unsupported` per target, because whether a given module is on that host and carries that marker is not knowledge Keeper has. The target must also announce the `dry_run` Soul-capability, else Keeper refuses with `409 soul-capability-unsupported` before dispatch (Amendment 2026-08-06).

**proto-only-add.** File `proto/keeper/v1/errand.proto`:
- `ErrandRequest{errand_id, module, input(Struct), timeout_seconds, dry_run}` — only-add to `FromKeeper.oneof`.
- `ErrandResult{errand_id, status, exit_code, stdout, stderr, stdout_truncated, stderr_truncated, duration_ms, error_message, output(Struct)}` — only-add to `FromSoul.oneof`.
- `CancelErrand{errand_id}` — only-add to `FromKeeper.oneof` (slice E5, field 11).
- `ErrandStatus` enum: UNSPECIFIED(0) / RUNNING(1) / SUCCESS(2) / FAILED(3) / TIMED_OUT(4) / CANCELLED(5) / MODULE_NOT_ALLOWED(6).

**PG table `errands`** (see the migration schema).

**Cross-keeper routing — reuse of infra.**
- Request: outbound:<sid> pub/sub (existing).
- Reply: errand events go through the sharded applybus channel `events:shard:<n>` ([ADR-006](0006-cache-redis.md) c.1); the forward loop filters out foreign applyIDs by `envelope.ApplyID`. The TODO-rename `apply:<errand_id>` → `events:*` was done in S2 (the per-applyID channel was collapsed to a fixed set of shards).

**Audit events.** `errand.invoked` / `errand.completed` / `errand.failed` / `errand.timed_out` / `errand.cancelled` — the last one is written both when an operator initiates a cancel (`source: api`/`mcp`, slice E5) and when the terminal `ErrandResult{CANCELLED}` is received from the Soul (`source: soul_grpc`); the UI groups by `correlation_id=errand_id`.

**Reaper rule `purge_old_errands`** (TTL 7 days, configured via `reaper.errands.ttl`).

**Render context for Errand input.** Available: `vault(...)`. Not available: `register.*`, `incarnation.state.*`, `essence.*`, `soulprint.self.*`, `soulprint.hosts` (an Errand has no scenario/incarnation/cross-host runtime).

**Invariants.** Errand does NOT mutate incarnation.state; the whitelist is enforced Soul-side (defense-in-depth); sync-first, async escalation; output cap 64 KiB / channel; secret-masking of output.

**Rejected alternatives.** (a) reuse ApplyRequest (drift), (b) everything through an RBAC selector (a soft boundary), (c) pure async (redundant for uptime), (d) a separate gRPC RPC (breaks ADR-012).

**Deferred.** per-module Errand mapper; Errand for keeper-side core.

**Amendment 2026-05-27. Errand E5 closure — slice complete.** The CancelErrand RPC is implemented: a new `CancelErrand{errand_id}` message in `proto/keeper/v1/errand.proto`, added to `FromKeeper.oneof` (field 11, only-add); `DELETE /v1/errands/{errand_id}` with permission `errand.cancel` (selector NoSelector — the SID is known only after the row lookup); MCP tool `keeper.errand.cancel` (catalog count 58 → 59); soulctl `errand cancel <id>`. Cancel flow: the Keeper-side `errand.Dispatcher.Cancel` reads the row, checks `status='running'` (409 `errand-not-cancellable` on a terminal state), sends CancelErrand to the Soul via `Outbound.SendCancelErrand`/`PublishCancelErrand` (local/remote depending on the lease), writes audit `errand.cancelled` (initiated). The Soul-side `errandrunner.Runner` maintains `active map[errand_id]→cancel-fn`; on receiving CancelErrand it calls Cancel(id) → ctx.Cancel → Run returns `ErrandResult{CANCELLED}` over the same EventStream channel, and the applybus receiver moves the row to `status=cancelled` via MarkTerminal. Series E1–E5 is closed. Deferred: L3a/L3b/L3c cancel-test in the Vigil harness (requires a cancel helper after the M2.5 harness extension).

**Amendment 2026-05-29 (Voyage `command`-kind reuses the Errand infra).** [ADR-043](0043-voyage.md#adr-043-voyage--unified-batch-run) (Voyage) `kind=command` **reuses** the whitelist and marker interface of this ADR: the hard-coded list `core.cmd.shell` / `core.exec.run` + `ErrandReadSafe` (the Soul-side per-Errand defense-in-depth is preserved). The state invariant (does NOT mutate `incarnation.state`) carries over into Voyage unchanged. **Single-SID `/v1/souls/{sid}/exec` remains sugar** — a short form for a one-off exec on a single host, without the Voyage/`runs` scaffolding (as Errand used to be without an ErrandRun). Multi-target — through `kind=command` Voyage. RBAC for `command`-kind = `errand.run` ([ADR-043](0043-voyage.md#adr-043-voyage--unified-batch-run) item 6).

**Amendment 2026-07-28 (NIM-197. The allow-list bounds the module, not the command line).** Item 2's hardcoded list (`core.cmd.shell` / `core.exec.run`) admits two modules whose *declared input is an arbitrary command line*. So the Soul-side allow-list answers "may an Errand call this module", and nothing was answering "may this operator run an arbitrary command as root" — `errand.run`, written in item 5 for "one named module with declared params", reached a shell on its own. Two changes:

- **The list moved to [`shared/coremanifest`](../../shared/coremanifest/verbshell.go)** (`IsVerbShell` / `VerbShellModules`). `errandrunner` now reads it instead of holding a private copy, and the Keeper reads the same one for the gate below. Behaviour of the allow-list is unchanged; it just stopped being knowledge only one binary had.
- **A verb-shell module additionally requires `soul.console`** at every Errand choke-point — REST `POST /v1/souls/{sid}/exec`, MCP `keeper.soul.errand.run`, a `kind=command` [Voyage](0043-voyage.md), a `kind=command` [Cadence](0046-cadence.md) recipe and its spawn. `errand.run` stays necessary; it is no longer sufficient. The reasoning, the deprecation window (`console.errand_shell_gate`) and the per-surface selectors are in [ADR-0074 → Amendment 2026-07-28](0074-interactive-console-pty.md). **`ErrandReadSafe` modules are untouched** — an ordinary Errand does not acquire a console requirement, and item 5's three permissions keep their meaning for it.

**Amendment 2026-08-06 (NIM-456. `dry_run` is gated on the target's announced capability).** `dry_run` in the contract table promises a pure read — the Soul calls `SoulModule.Plan` instead of `Apply` ([ADR-031(b)/(c)](0031-scry-drift.md)). Nothing was enforcing that the target can keep the promise. A Soul predating the flag reads `ErrandRequest` by the keys it knows, misses `dry_run`, and runs `Apply`; for the modules item 2 admits that means a shell command executed for real, inside an operation that advertised a read. The capability existed for exactly this (`dry_run` in [`shared/config/soul_capability.go`](../../shared/config/soul_capability.go)) and its only reader was the check-drift gate on the scenario path, which left with the drift circuit (NIM-446) — Errand, the sole remaining producer of a `dry_run` request, never had one. The defect is pre-existing; removing check-drift exposed it rather than causing it.

- **Keeper refuses a `dry_run` dispatch whose target did not announce `dry_run`**, before the request leaves the process ([`keeper/internal/errand/soulcompat.go`](../../keeper/internal/errand/soulcompat.go)) — the single-host sibling of the roster gate in `keeper/internal/scenario`, same axis and same shape as `soul_passage_unsupported` ([ADR-0076(i)](0076-engine-compat-window.md)). Fail-closed on all three edges: a missing announcement, no presence source at all, and a failed check all refuse. Surfaced as `409 soul-capability-unsupported` on REST and `soul-capability-unsupported` on MCP, with `detail` distinguishing "that binary is too old" from "support could not be confirmed" — the fixes differ, so the message must too.
- **The refusal precedes the `errands` row and the `errand.invoked` audit event.** A refused request invoked nothing; a row plus an `invoked` event would claim otherwise and leave an operator explaining a failure that never reached a host.
- **Only `dry_run: true` pays for the check.** An ordinary Errand consults nothing, so the gate adds no round-trip to the common path and no new way for a presence outage to break plain exec.
- **Superseded in this ADR:** the contract line said a verb module under `dry_run` yields `400 errand_dry_run_unsupported`. Keeper never implemented that check — the Soul returns `ErrandResult{FAILED, errand_dry_run_unsupported}` and the HTTP reply is `200` carrying that terminal status. The line is left describing the Soul-side refusal (which is real); the missing keeper-side 400 is tracked separately and is not what this amendment adds. **Since Amendment 2026-08-08 the keeper-side refusal exists** — for the verb-shell half of "verb module", which is the half Keeper can decide.

**Amendment 2026-08-07 (NIM-488. The runner now implements the `dry_run` contract row; admission is per-path).** Item 2 governs **Apply** ("the Soul-side Errand runner calls `SoulModule.Apply` **only** if …"); the contract row for `dry_run` governs **Plan** ("only for modules with `PlanReadSafe`"). The runner asked item 2's condition on both paths: a `dry_run` request first had to clear `ErrandReadSafe`, and only then was `PlanReadSafe` consulted. The two marker sets do not intersect — `ErrandReadSafe` is carried by `core.http` and `core.noop`, `PlanReadSafe` by `core.file` and 12 others — so **every** `dry_run: true` Errand was terminal with `errand_module_not_allowed` and no module in the tree could reach a `Plan` through Errand. Nothing in this ADR ever asked for that; the flag documented here, declared in OpenAPI/MCP and fenced by the amendment above had no reachable subject at all.

- **[`errandrunner.IsAllowed`](../../soul/internal/runtime/errandrunner/whitelist.go) takes the path as an argument** and answers the condition that belongs to it: `dry_run: false` → item 2 unchanged (verb-shell by name, else `ErrandReadSafe`, else `errand_module_not_allowed`); `dry_run: true` → `PlanReadSafe`, else `FAILED errand_dry_run_unsupported`. The two markers are independent, not ordered: neither implies the other, and neither is consulted on the path it does not describe.
- **This grants nothing.** `ErrandReadSafe` remains the sole marker that opens `Apply`, so `core.file` is still refused for ad-hoc write — under an explicit `dry_run: false` and under an omitted field alike (proto3 bool zero value). A holder of `errand.run` gains the ability to ask a `PlanReadSafe` module *what it would change*, not to change it. Rejected in the process: handing `core.file` the `ErrandReadSafe` marker, which reads like a label but is a rights extension — arbitrary ad-hoc file writes outside any scenario, with no `state_changes`. What it does widen is reading: a `Plan` reports whether a path exists with the requested content/mode, so `errand.run` gains a file oracle it did not have through this route. That is accepted as dominated, not as harmless — the same permission already admits `core.cmd.shell` by name, and `errand.run` has no module dimension to scope it with ([`keeper/internal/rbac/catalog.go`](../../keeper/internal/rbac/catalog.go) offers `host=` / `coven=` selectors only), so any holder able to ask `core.file` what it would change can already read the file outright.
- **Verb-shell and probe keep no by-name pass here.** `core.cmd.shell` / `core.exec.run` / `core.http.probe` have no pure-read `Plan`, so `dry_run` on them still answers `errand_dry_run_unsupported`, exactly as the contract row states.
- **The capability gate of the amendment above is untouched** and still runs first: Keeper refuses a `dry_run` dispatch to a Soul that did not announce the capability, before any of this is reached.

**Amendment 2026-08-08 (NIM-489. The keeper-side `400` the contract row promised, for the half Keeper can decide).** The `dry_run` row has said since this ADR was written that a verb module under `dry_run` is refused; only the Soul-side half was ever built. An operator asking to preview `core.cmd.shell` got `200` carrying `FAILED errand_dry_run_unsupported` — a request that cannot succeed on any host, in any fleet, at any version, answered as if it had been a legitimate attempt. On the [Voyage](0043-voyage.md) path it was worse and differently wrong: the flag never reached the host at all (NIM-559, fixed in the same change), so the pair was answered `202` and the command line then ran for real on every resolved host. Threading the flag is what turns that into one identical, unavoidable failure per host — which is the case this refusal exists to catch, at creation rather than per host.

- **One keeper-side rule, and it is narrow** ([`keeper/internal/errand/dryrunshell.go`](../../keeper/internal/errand/dryrunshell.go)): `dry_run: true` + a module in [`coremanifest.VerbShellModules`](../../shared/coremanifest/verbshell.go) → refused. Those two names are a Keeper-side constant (Amendment 2026-07-28 moved them there), they take an arbitrary command line, and they have no pure-read `Plan` anywhere — so the pair is a fact about the **request**, and is answered at the request.
- **Everything else stays a per-target answer**, deliberately. Whether an arbitrary module exists on a given Soul and whether its `Plan` is declared `PlanReadSafe` lives on the far side of the isolation boundary ([ADR-011](0011-go-layout.md)) and differs per host; Keeper does not know it and must not start guessing. `core.http.probe`, named as a verb module in the row above but absent from the verb-shell constant, is exactly this case: admitted by Keeper, refused by the runner with `errand_dry_run_unsupported`. Rejected: keying the refusal on the module catalogue's `errand_safe` flag — that flag describes the **Apply** path and, since the amendment above, marks very nearly the *complement* of what `dry_run` admits, so it would reject the thirteen `PlanReadSafe` modules the flag exists for while still admitting the shell.
- **`400 malformed-request`, not a `409` capability type.** No state of the cluster, the target or the agent binary can make this pair work, so telling the operator "capability unsupported" would send them to upgrade an agent that would refuse it too. MCP mirrors it as `malformed-request`. The refusal names the module and says what to do instead — drop `dry_run` and run for real, or preview a module whose `Plan` is pure-read. Unlike the capability refusals, "without `dry_run`" *is* the right advice here.
- **Ahead of the capability gate, and ahead of the `errands` row and the `errand.invoked` audit event.** A stale agent is not the operator's mistake on this pair, and no announcement could rescue it, so the impossible-pair refusal is reported first and pays for no presence round-trip.
- **Two entry points, one validator.** [`Dispatcher.Dispatch`](../../keeper/internal/errand/dispatcher.go) covers REST `/v1/souls/{sid}/exec` and the MCP tool at once; Voyage `kind=command` creation calls the same function at create time ([ADR-043 → Amendment 2026-08-08](0043-voyage.md)) so the two surfaces cannot answer differently. Cadence recipes carry no `dry_run`, so there is no third.

**Amendment 2026-08-08 (NIM-608. A mixed read/mutate module cannot carry a module-wide read-safe marker).** `core.http` gained state `request`, whose POST/PUT/PATCH/DELETE Apply is mutating by definition. The sdk `ErrandReadSafe` interface marks a Go module implementation, not one state, so leaving it on `core.http.Module` would admit `core.http.request` through Errand and violate this ADR's state invariant. The marker is removed from that module. On the Apply path `errandrunner.IsAllowed` admits the exact full address `core.http.probe`; `core.http.request`, an unknown/future `core.http.*` state, and every other unmarked module fall through to `errand_module_not_allowed`. The comparison is exact and is pinned against the real `core.http.Module` by `TestIsAllowed_CoreHTTPStateBoundary`. The catalog likewise publishes only `probe` in `ErrandSafeStates`. This is a narrowing-by-construction for the new state and preserves the existing probe contract.
